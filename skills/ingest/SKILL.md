# 자료 처리 (ingest)

> **먼저 읽는다** — 이 스킬을 불러오면 표시되는 기본 디렉터리(`Base directory for this skill`) 기준으로 `../../rules/principles.md`(제품 원칙)와 `../../rules/user-decisions.md`(사용자 결정 원본)를 읽는다. 이 문서의 규칙이 그 둘과 다르면 그 둘이 맞다. 같은 세션에서 이미 읽었으면 다시 읽지 않는다. **둘 중 하나라도 읽지 못하면(파일 없음·읽기 실패) 이 스킬의 작업을 시작하지 않는다** — 어떤 파일을 어느 경로로 찾았는지와 "원칙 문서를 읽지 못해 멈췄다"를 첫 줄에 알리고 끝낸다. 원칙 없이 기억이나 이 문서만으로 대신 진행하지 않는다.
>
> **한국어로 말한다** — 사용자에게 하는 모든 말(질문·선택지·중간 안내·끝 보고)은 한국어로 쓴다(원칙 → Target Users). 스크립트 출력·에이전트 보고·영어 자료를 옮길 때도 한국어로 풀어 쓴다. 기술 이름·코드·파일 경로·고유명사만 원래 표기. 사용자가 다른 언어를 요청했을 때만 바꾼다. 격리 실행(개인 설정 없음)에서 끝 보고가 영어로 나온 적이 있다(10-10).

> 사용자에게 말할 때는 `start` 스킬의 "사용자에게 쓰는 말" 표를 따른다. facts·outline·슬롯 같은 내부 이름을 채팅에 그대로 쓰지 않는다.

사용자가 준 자료에서 **포트폴리오에 쓸 사실**을 뽑아 `portfolio/facts/<slug>.md`에 병합한다.
사실 파일의 형식과 태그는 `interview` 스킬의 "사실 파일 형식"을 그대로 따른다.

## 절대 규칙

1. **자료에 적힌 것만 기록한다.** 자료가 암시만 하는 내용, 행간에서 읽히는 내용은 사실로 기록하지 않는다. 필요하면 사용자에게 확인할 질문으로 남긴다.
2. **수치는 원문 그대로 옮긴다.** 반올림, 단위 변환, 배수·퍼센트를 대신 계산하지 않는다.
3. **기존 사실을 덮어쓰지 않는다.** 값이 다르면 두 값을 모두 남기고 `충돌`로 표시한다.
4. **사실 파일에 쓰기 전에 사용자 확인을 받는다.** 추출 결과를 먼저 보여주고, 승인된 것만 병합한다.
5. **원본을 보관한다.** 모든 사실은 `portfolio/sources/`의 파일 하나를 출처로 가리켜야 한다. 기록의 수치는 출처 태그가 가리키는 원본에 글자로 있어야 한다 — `facts_lint`가 대조한다(D-TXT-6). 그래서 원본은 요약하지 않고 받은 그대로 저장하고, 출처 태그는 수치가 실제로 있는 파일로 단다. 이미지에서 읽은 수치는 대조할 수 없어 경고로 남으니 사용자에게 한 번 확인받는다. 그 줄은 이미지 태그만 단다 — 글자 태그(interview·글자 자료)와 섞으면 글자 원문으로 대조해 ERROR가 난다. `sources/interview-log.md`는 훅이 쓰는 사용자 말 기록이라 손대지 않는다.

## 받을 수 있는 자료와 읽는 법

| 자료 | 읽는 법 | 보관 |
|---|---|---|
| 붙여넣은 텍스트 | 그대로 | `sources/pasted-<YYYYMMDD>-<n>.md`로 저장 |
| 로컬 md / txt / pdf / html | `Read` (pdf가 길면 페이지 범위를 나눠 읽는다. html은 본문 텍스트만 본다) | `sources/`에 복사 |
| 스크린샷 (측정 리포트, 대시보드 등) | `Read`로 이미지 확인 | `sources/`에 복사 |
| URL (블로그 등) | `WebFetch` | 본문을 `sources/web-<slug>.md`로 저장하고 맨 위에 URL과 가져온 날짜를 적는다 |
| GitHub PR / 이슈 | `gh` CLI가 있으면 `gh pr view <n> --repo <owner/repo> --comments`, 없으면 `WebFetch` | `sources/gh-<repo>-<n>.md` |
| Notion 페이지 | Notion MCP 도구가 연결돼 있으면 그것으로 읽는다(`notion-fetch` 등). 공개 페이지(`*.notion.site`)는 `WebFetch`도 시도한다. 둘 다 안 되면 아래 "읽지 못한 자료" 규칙 | `sources/notion-<slug>.md` (맨 위에 URL과 날짜) |
| 폴더 (개인 위키, 노트, 기존 포트폴리오 폴더) | 아래 "자료 묶음" 절차 | 고른 파일만 `sources/<폴더명>-<파일명>`으로 복사 |
| docx / hwp 등 | 직접 읽지 않는다 | 사용자에게 PDF나 텍스트로 변환해서 달라고 요청한다 |

- **읽지 못한 자료**: 접근이 안 되는 자료(비공개 레포, 로그인이 필요한 페이지, 렌더링 안 되는 페이지)는 우회하지 않는다. **그 턴에 바로** 사용자에게 알리고 내용을 붙여넣거나 PDF로 내보내 달라고 한다. 빌드가 끝날 때까지 미뤄서 최종 보고에서 "읽지 못함"으로 처음 알리지 않는다. 사용자가 안 주면 `빈칸`에 "<자료> — 읽지 못함, 붙여넣기 요청함"으로 남긴다.
- 보관 파일 이름이 곧 출처 태그다: `[src: doc:pasted-20261007-1.md]`

## 자료 신뢰 순위

같은 사실에 대해 자료끼리 말이 다를 때 기준으로 쓴다. 순위가 높은 쪽이 맞다고 **단정하지는 않는다**. 충돌로 기록하고, 사용자에게 보여줄 때 이 순위를 함께 알린다.

1. **원본 측정·코드**: 부하 테스트 리포트, 대시보드 스크린샷, 실행 계획(EXPLAIN) 출력, PR diff, 커밋
2. **당시 기록**: 이슈, PR 설명, 장애 보고서, 회의록
3. **사후 서술**: 블로그 글, 회고, 발표 자료, **기존 포트폴리오·이력서**

사후 서술은 시간이 지나면서 기억이 압축되므로 수치나 인과가 바뀌어 있을 수 있다. 사후 서술에만 있는 수치는 `근거없음`으로 표시하고, 원본 측정이 있는지 사용자에게 묻는다.

## 이미지 (`portfolio/images/`)

이미지는 사용자가 **채팅으로 직접 준다**(D-IMG-5). 사용자에게 폴더에 넣으라고 하지 않는다. 받은 이미지를 열어 보고 **무엇인지 확인받은 뒤** 기록한다. 이미지 내용을 짐작으로 기록하지 않는다.

0. **받기**: 사용자가 파일을 터미널로 끌어다 놓으면 채팅에 경로가 들어온다. 그 파일을 `portfolio/images/<slug>/`로 `cp` 한다(원본 이름 유지, 같은 이름이 있으면 `-2`). 이미지 URL이면 `curl -L -o`로 받는다. 사용자가 붙인 말("dms 로고")이 있으면 그 프로젝트 폴더로, 없으면 `portfolio/images/`에 두고 2번에서 프로젝트를 묻는다.
   - 클립보드로 붙여넣은 이미지(`[Image #1]`처럼 경로 없이 보이는 것)는 파일이 없어 복사할 수 없다. 보이는 내용은 확인에 써도 되지만, PDF에 넣으려면 "캡처를 파일로 저장해서 끌어다 놓아 줘"라고 다시 요청한다.
   - 사용자가 예전처럼 폴더에 직접 넣었다고 하면 그것도 받는다.
1. **목록과 크기**: `python3 <build 스킬의 scripts>/image_info.py portfolio/images`. 이미 `facts/*.md`의 `## 이미지`에 있는 파일은 건너뛴다.
2. **열어 보기**: 새 파일마다 `Read`로 연다. 화면에 보이는 것만으로 아래를 추정한다.
   - 종류: `로고` / `서비스 화면`(프로젝트를 대표하는 화면, 캡처·목업 모두) / `화면 캡처`(그 밖의 UI) / `사진` / `측정 화면`(Gatling·부하 테스트·대시보드·EXPLAIN 결과 등) / `다이어그램`(직접 그린 구조도)
   - 프로젝트: `images/<slug>/` 폴더에 있으면 그 프로젝트다. 폴더 밖에 있으면 화면 내용으로 추정
   - 측정 화면이면 개선 전·후인지 본다. 전·후 짝이면 캡션에 "개선 전"/"개선 후"를 붙여 확인받는다. design이 같은 쪽에 나란히 둔다
   - 서비스 화면 후보가 여러 장이면 프로젝트를 가장 잘 보여주는 한 장을 `서비스 화면`으로, 나머지는 `화면 캡처`로 둔다(AI가 정함)
   - 프로젝트: 화면의 서비스 이름·내용으로 추정. 모르면 "모름"
   - 캡션 후보: 화면에 **보이는 것**만으로 한 문장(예: "학생이 새벽자습을 신청하는 앱 화면"). 기능의 효과나 수치는 캡션에 넣지 않는다
   - 개인정보: 실명·학번·전화번호·얼굴이 보이면 표시한다
3. **한 번에 확인**: 채팅에 표로 보여주고 한 메시지로 확인받는다. 사용자는 틀린 칸만 고친다.
   ```
   | 파일 | 크기 | 종류 | 프로젝트 | 캡션 후보 | 주의 |
   | apply.png | 390×844 세로형 | 화면 캡처 | DMS | 학생이 새벽자습을 신청하는 앱 화면 | 학생 이름이 보임 → 가릴지? |
   | gatling-after.png | 1600×900 | 측정 화면 | DMS | 학생 목록 조회 부하 테스트 결과 (개선 후) | |
   ```
   - 개인정보가 보이면 쓸지, 가린 버전을 다시 넣을지 묻는다. 하네스가 이미지를 편집하지 않는다.
4. **기록**
   - 모든 확인된 이미지는 해당 프로젝트 `facts/<slug>.md`의 `## 이미지`에 `- <파일> | <종류> | <캡션> [src: interview]`로 쓴다.
   - **측정 화면은 근거 자료이기도 하다.** `sources/`에 복사하고(`sources/img-<파일명>`), 화면에 보이는 수치·측정 조건·측정 시각을 이 문서의 "추출" 규칙대로 뽑아 기존 기록과 대조한다(신규/동일/구체화/충돌). 사용자가 말로 준 수치와 다르면 `충돌`이다.
   - 다이어그램 이미지는 화면에 보이는 박스·화살표를 그대로 옮겨 적고 확인받는다. build가 다시 그리지 않고 이미지를 그대로 쓴다.
5. **필수 이미지 확인**: 기록을 쓴 뒤 프로젝트마다 `로고`와 `서비스 화면`이 있는지 본다. 빠진 게 있으면 같은 메시지 끝에 "dms는 로고가 아직 없어. 이미지 파일을 이 창으로 끌어다 놓아 주거나, 없으면 없다고 말해줘"를 붙인다.
6. 쓰지 않기로 한 이미지는 `## 이미지`에 `| 사용 안 함 |`으로 남겨 다음에 다시 묻지 않는다.

## 자료 묶음 (폴더·위키·기존 포트폴리오)

파일이 여러 개인 자료는 전부 읽기 전에 **후보를 고르게 한다.** 다 넣으면 확인할 양이 너무 많아지고, 일부만 보면 좋은 사례를 놓친다.

1. **목록 파악**: 목차 파일(`index.md`, `README.md`, `SUMMARY.md`)이 있으면 그것부터 읽는다. 없으면 파일 이름과 각 파일의 제목·첫 몇 줄로 파악한다. 폴더에 `CLAUDE.md` 같은 규칙 파일이 있으면 구조 설명으로만 참고하고, 그 폴더를 수정하지 않는다.
2. **후보 표**: 포트폴리오에 쓸 만한 파일을 골라 채팅에 표로 보여준다.
   | 파일 | 프로젝트 | 담긴 것 | facts에 이미 있음 |
   |---|---|---|---|
   | rabbitmq-retry-storm.md | DMS | 트러블슈팅 · 수치(약 7분 다운) | 아니오 |
   - "담긴 것"은 `트러블슈팅`(상황→원인→해결→결과) / `측정 수치` / `기술 선택` / `회고` / `개념 정리` 중에서 적는다.
   - 순서: 트러블슈팅+측정 수치 > 트러블슈팅 > 기술 선택(대안 비교) > 나머지. `개념 정리`(특정 프로젝트 경험이 아닌 일반 지식)는 후보에서 뺀다.
   - 지금 facts에 없는 프로젝트가 나오면 따로 표시한다. 기존 포트폴리오에 있던 프로젝트가 빠지는 일을 막기 위해서다.
3. **고르기**: `AskUserQuestion`(multiSelect)으로 고르게 한다. 선택지는 4개까지이므로, 표에서 추천 상위 3개를 선택지로 두고 나머지는 "표에서 번호로 추가"(Other)로 받는다. 한 번에 최대 10개 파일까지 처리하고, 남은 후보는 `빈칸`에 "추가 후보: <파일들>"로 남긴다.
4. **원본 따라가기**: 위키·노트는 대개 다른 자료를 정리한 **사후 서술**이다. 파일이 원본(`raw/` 파일, PR·이슈 링크, 측정 스크린샷)을 가리키면 그 원본도 읽고 함께 보관한다. 수치는 원본에서 확인한 것을 우선 출처로 단다. 원본이 없으면 신뢰 순위 3으로 처리한다.
5. 고른 파일마다 아래 처리 절차 3~4를 하고, **5단계 확인은 파일을 모두 처리한 뒤 한 메시지로** 한다.

## 처리 절차

### 1. 대상 확인
- 어느 프로젝트에 대한 자료인지 정한다. 기존 `portfolio/facts/*.md`의 프로젝트명과 대조하고, 애매하면 `AskUserQuestion`으로 묻는다.
- 해당 프로젝트 파일이 아직 없으면, 사용자 확인을 받고 `interview` 형식의 frontmatter로 새로 만든다. 이때 frontmatter 중 자료에 없는 값은 비워둔다.
- 여러 프로젝트가 섞인 자료(예: 기존 이력서)는 프로젝트별로 나눠서 처리한다.

### 2. 민감 정보 확인
회사 프로젝트이거나 내부 문서로 보이면, 추출을 시작하기 전에 묻는다. 고객사명, 내부 지표(매출, 사용자 수), 내부 시스템명을 포트폴리오에 공개해도 되는지 확인한다.
- 공개 불가로 답한 항목은 추출하지 않거나, 사용자가 정한 대체 표현(예: "B2B 고객사")으로 기록한다.
- 토큰, 비밀번호, 내부 IP 같은 값은 facts와 보관 파일에서도 `[REDACTED]`로 지운다. `sources/interview-log.md`(사용자 말 원문, 훅이 씀)는 예외로 비밀값도 원문 그대로 둔다(R-EVD-6, U-12).

### 3. 추출
자료를 읽고 사실 후보를 뽑는다. 후보마다 다음을 붙인다.

- **들어갈 섹션**: 개요 / 역할 / 기술 선택 / 작업 / 회고
- **원문 인용**: 근거가 되는 문장을 그대로 짧게 인용한다. 스크린샷이면 화면에 보이는 값을 그대로 적는다
- **위치**: 문서의 섹션·페이지, 또는 이미지의 어느 부분인지
- **종류**: 사실 / 수치 / 인과 / 의견·회고

종류별 주의점:
- **수치**: 측정 조건(도구, 동시 사용자 수, 데이터량, 측정 시각)이 자료에 있으면 함께 뽑는다. 없으면 "조건 없음"이라고 적는다. 스크린샷에 측정 시각이 보이면 반드시 기록한다. 개선 전후가 같은 환경에서 측정됐는지 판단하는 근거가 된다.
- **인과**: 자료가 "A 때문에 B"라고 **명시한 경우만** 인과로 기록한다. A와 B가 나란히 적혀 있기만 하면 각각 따로 사실로 기록한다.
- **역할**: 자료에 "우리 팀", "저희가"처럼 주체가 팀이면 `역할 미확인`으로 표시한다. 본인 몫이 무엇인지는 사용자에게 묻는다.
- **여러 작업이 한 문단에 섞인 경우**: 이슈 번호나 날짜, 대상(어느 API, 어느 쿼리)이 다르면 별도 작업 항목으로 나눈다.
- **의견·회고**: `## 회고 (원문 유지)` 섹션에 인용 그대로 넣는다. 요약하지 않는다.

### 4. 기존 사실과 대조
후보마다 해당 프로젝트 파일의 기존 내용과 비교해 분류한다.

| 분류 | 처리 |
|---|---|
| 신규 | 추가 |
| 동일 | 기존 항목의 출처 태그에 이 자료를 덧붙인다 (`[src: interview, doc:...]`) |
| 구체화 | 기존 항목이 비어 있던 필드(원인 확인 방법, 측정 조건 등)를 채운다 |
| 충돌 | 두 값을 모두 적고 `충돌`로 표시한다. 각 값의 출처와 신뢰 순위를 함께 남긴다 |

### 5. 사용자 확인
쓰기 전에 아래 형식으로 보여준다. 항목이 많으면 섹션별로 나눠 보여준다.

```
[신규]  작업 > 검색 API 개선 > 결과: 평균 309ms
        원문: "평균 응답 시간 309ms" (gatling-after.png, 상단 표)
        측정 조건: 10 requests, 2026-08-12 14:02 GMT / 동시 사용자 수: 자료에 없음
[충돌]  개요 > 월 사용자: 인터뷰 "약 500명" vs blog-2026.md "300명"
        신뢰 순위: 둘 다 사후 서술 → 원본 지표가 있는지 확인 필요
[확인]  역할 > "저희 팀이 Redis 캐시를 도입" → 본인이 직접 한 부분은?
```

- **확인은 한 메시지로 끝낸다.** `[신규]`·`[동일]`·`[구체화]`는 개수와 대표 항목 몇 개만 보여주고 "이대로 반영"을 한 번에 받는다. 사용자가 개별 판단해야 하는 건 `[충돌]`과 `[확인]`뿐이다. 이 둘은 같은 메시지에서 한꺼번에 묻는다.
- 수정 요청이 있으면 반영한 뒤 병합한다. `[확인]`에 답이 없으면 `빈칸` 섹션에 남긴다.

### 6. 병합과 보고
1. 승인된 항목을 사실 파일에 쓴다. `interview` 형식의 태그 규칙(`src`, `status`)을 지킨다.
2. 처리 결과를 한 줄로 보고한다: 신규 n / 구체화 n / 충돌 n / 미확인 n
3. `portfolio/interview-state.md`가 있고 stage가 `done`이 아니면, 인터뷰로 돌아가 **자료로 채워지지 않은 필드만** 질문을 이어간다.

## 하지 않는 것
- 자료를 요약해서 포트폴리오 문장으로 만들지 않는다. 그건 build 단계에서 한다.
- 자료에 없는 측정 조건을 "아마 ~였을 것"으로 채우지 않는다.
- 자료끼리의 충돌을 자체 판단으로 해소하지 않는다. 해소는 사용자가 한다.
