# 디자인 설정 (design)

> **먼저 읽는다** — 이 스킬을 불러오면 표시되는 기본 디렉터리(`Base directory for this skill`) 기준으로 `../../rules/principles.md`(제품 원칙)와 `../../rules/user-decisions.md`(사용자 결정 원본)를 읽는다. 이 문서의 규칙이 그 둘과 다르면 그 둘이 맞다. 같은 세션에서 이미 읽었으면 다시 읽지 않는다. **둘 중 하나라도 읽지 못하면(파일 없음·읽기 실패) 이 스킬의 작업을 시작하지 않는다** — 어떤 파일을 어느 경로로 찾았는지와 "원칙 문서를 읽지 못해 멈췄다"를 첫 줄에 알리고 끝낸다. 원칙 없이 기억이나 이 문서만으로 대신 진행하지 않는다.

> 사용자에게 말할 때는 `start` 스킬의 "사용자에게 쓰는 말" 표를 따른다. facts·outline·슬롯 같은 내부 이름을 채팅에 그대로 쓰지 않는다.

## 역할

이 스킬은 포트폴리오의 **디자인 시스템과 페이지 구성**을 결정한다.

본문 내용을 새로 작성하지 않는다.

다음 두 가지를 결정한다.

1. 전체 포트폴리오가 공유하는 디자인 시스템
2. 각 콘텐츠에 가장 적합한 페이지 레이아웃

디자인 시스템은 일관되어야 하지만, 모든 페이지가 같은 레이아웃을 반복해서는 안 된다.

# 디자인 철학

이 서비스의 사용자는 주로 학생이며, 주요 취업 대상은 스타트업이다.

따라서 포트폴리오는 단순히 "예쁜 결과물"이 아니라 다음을 빠르게 보여줘야 한다.

- 이 사람이 무엇을 만들었는가
- 실제로 어떤 문제를 발견했는가
- 본인이 무엇을 했는가
- 어떤 판단을 했는가
- 어떤 결과를 만들었는가
- 무엇을 배웠는가

포트폴리오를 처음 보는 채용 담당자가 짧은 시간 동안 훑어도 사용자의 가장 강한 경험과 성과가 보이도록 한다.

디자인의 목적은 콘텐츠를 장식하는 것이 아니라 **콘텐츠의 중요도를 시각적으로 전달하는 것**이다.

# 기본 디자인 시스템

## 모든 스타일이 같이 지키는 뼈대 (사용자 결정 D-DES-1)

사용자마다 겉모습(전체 스타일·강조색·글꼴·제목 모양)은 다르고, **레퍼런스가 없으면 사용자가 시안을 보고 고른다**(D-DES-15). 그러나 다음 읽기·사실 규칙은 어떤 스타일에서도 바꾸지 않는다.

> **레퍼런스가 있으면 이 뼈대와 아래 디자인 규칙(레이아웃 선택, 이야기 모양, 색, 타이포그래피, 여백과 그리드, 쪽 구성)을 쓰지 않는다**(D-DES-16). 레퍼런스대로 만든다 — "1-A"를 따른다. 내용 규칙(지어내지 않음, 기록에 있는 수치만, 측정 조건, 하네스 용어 금지)은 그대로다.

- 프로젝트 블록 순서, 1쪽 구성, 쪽마다의 레이아웃 키(`layouts`)
- 글자 역할과 크기 범위(`fontScaleRange`), 8pt 하한, 여백 50% 상한
- 흰 종이 바탕(인쇄물), 본문·보조·강조색의 흰 바탕 대비 4.5:1 이상. 고른 전체 스타일의 머리 띠(1쪽 머리·프로젝트 첫머리)만 면 색을 쓸 수 있고, 띠 위 글자도 4.5:1 이상(`make_theme.py`가 검사)
- before → after 공용 부품(`components.css`)과 측정 조건 표시

## 전체 스타일 (look, 사용자 결정 D-DES-15)

`variants.json`의 `looks`에서 고른다. 미니멀 하나로 고정하지 않는다 — 2026-10-10 실사용 테스트에서 강조색만 다른 같은 문서가 나와 사용자가 "폰트·색상·배치에 관여하고 싶다"고 했다.

| look | 모양 |
|---|---|
| `minimal` | 흰 종이, 선과 여백으로만 구분 (아래 미니멀 원칙) |
| `editorial` | 굵은 제목과 검은 가는 선, 1쪽 머리·프로젝트 첫머리 아래를 선으로 닫음. 세리프·명조 제목 글꼴과 잘 맞음 |
| `color-band` | 1쪽 머리와 프로젝트 첫머리를 강조색 띠로 (종이 위·좌우 끝까지) |
| `dark-header` | 같은 자리를 어두운 띠로 |

첫 PDF는 `minimal`로 만들고, 첫 PDF가 검사를 통과하면 아래 "디자인 고르기"에서 사용자가 고른다.

### 미니멀일 때의 원칙 (Minimalism & Swiss Style)

`minimal`을 고르면 Minimalism & Swiss Style을 바탕으로 한다. 다른 look도 머리 띠·제목 장식을 뺀 본문은 아래를 따른다.

다만 "Swiss"는 모든 페이지를 똑같이 만드는 템플릿이 아니다.

유지해야 하는 것은 다음이다.

- 흰 배경
- 넓고 일관된 여백
- 명확한 그리드
- 산세리프 중심의 타이포그래피
- 제한된 강조색
- 그림자와 그라디언트 없음
- 장식보다 정보의 위계 우선
- 왼쪽 정렬
- 인쇄물로서 안정적인 구성

페이지별 레이아웃은 콘텐츠에 따라 달라질 수 있다.

다음과 같은 장식은 사용하지 않는다.

- 의미 없는 도형이나 선
- 장식 목적의 아이콘 남용
- 카드마다 반복되는 둥근 모서리와 테두리
- 모든 콘텐츠를 카드에 넣는 구성
- 의미 없는 배경색 블록 (고른 look의 머리 띠는 예외)
- 장식 목적의 그라디언트
- 과도한 강조색
- 시각적 효과를 위한 그림자

시각적 요소를 추가하려면 정보 전달, 콘텐츠 구분, 시선 유도 중 하나의 명확한 목적이 있어야 한다.

# 파일

| 파일 | 내용 |
|---|---|
| `portfolio/design.json` | 디자인 설정 + 이미지 자리 + 페이지별 레이아웃 |
| `portfolio/theme/tokens.css` | 색·폰트·글자 크기·간격 CSS 변수 (`make_theme.py`가 만든다) |
| `portfolio/theme/components.css` | before → after 수치 등 공용 부품 (원본 그대로 복사) |
| `portfolio/theme/style.css` | 제목 글꼴·제목 모양·레퍼런스 장식 (`make_theme.py`가 만든다) |
| `portfolio/theme/extra.css` | 레퍼런스의 배치·장식을 담는 파일 (레퍼런스가 있을 때만, 제한 없음) |

이 파일들 말고는 쓰지 않는다. `theme/`의 세 CSS는 손으로 쓰지 않고 `make_theme.py`로 만든다.

특히 다음 파일은 수정하지 않는다.

- `out/index.html`
- `out/portfolio.pdf`

디자인 변경을 PDF에 반영하는 것은 build를 다시 실행하는 것이다.

본문 콘텐츠, facts, 인터뷰 결과, 프로젝트 설명을 이 스킬에서 수정하지 않는다.

디자인을 위해 콘텐츠를 줄이거나 재작성해야 한다고 판단되면 임의로 수정하지 말고, 필요한 사항을 build 또는 콘텐츠 담당 단계에 전달한다.

# 테마 정하기 (사용자 결정 D-DES-1, 2026-10-09)

원본은 이 스킬 디렉터리의 `theme/`에 있다: `tokens.css`(기본 토큰), `components.css`(공용 부품), `variants.json`(고를 수 있는 전체 스타일·강조색·글꼴·제목 모양·서비스 화면 배치), `variants/heading-*.css`, `variants/look-*.css`, `design.base.json`.

## 0. 레퍼런스를 묻는다 (한 번만)

`portfolio/design.json`에 `style`이 이미 있으면 묻지 않고 그대로 쓴다(사용자가 "디자인 다시 해줘"·"레퍼런스 바꿀래"라고 하면 다시 묻는다). 없으면 `AskUserQuestion` 한 번으로 묻는다.

> 참고하고 싶은 포트폴리오 디자인이 있어? 있으면 배치·색·글꼴까지 그대로 따라서 만들게. 없으면 첫 PDF를 만든 뒤 시안을 보여주고 고르게 할게.
> - 있어 — 파일 경로(PDF·이미지·HTML)나 URL을 알려줘
> - 없어 — 알아서 정해줘

## 1-A. 레퍼런스가 있을 때 — 레퍼런스 그대로 (사용자 결정 D-DES-16)

**레퍼런스대로 만든다.** 배치, 쪽 구성, 블록 순서, 색, 글꼴, 글자 크기, 여백, 장식을 레퍼런스에서 가져오고 하네스의 디자인 조건(뼈대, 레이아웃 키·이야기 모양, 대비 4.5:1, 글자 범위·8pt 하한, 여백 50% 상한, 흰 종이, 머리 띠 규칙)은 생각하지 않는다. "레퍼런스와 다른 점"을 만들지 않는다. 사용자에게 디자인을 다시 묻지 않는다(시안 고르기도 없다).

1. 레퍼런스를 연다. 이미지·PDF는 `Read`(PDF는 모든 쪽), HTML은 파일을 읽어 CSS 값을 그대로 가져온다. URL은 가져올 수 있으면 가져오고, 못 가져오면 "열지 못했다"고 말하고 스크린샷이나 파일을 달라고 한다. 열지 못한 레퍼런스를 본 것처럼 정하지 않는다.
2. 쪽마다 무엇이 어디에 어떤 크기로 있는지 적는다: 쪽 크기(A4·연속), 1쪽 구성, 프로젝트 쪽의 블록 순서와 배치(열 수, 이미지 위치·크기), 제목·본문·캡션 글자 크기와 굵기, 색(면 색 포함), 글꼴, 구분선·라벨·칩 같은 장식, 여백. 이것을 `style.referenceLayout`(쪽별 서술, 문자열 배열)에 남긴다. build가 이것과 레퍼런스 원본을 보고 HTML을 쓴다.
3. `style`을 쓴다(`source: "reference"`, `reference`에 경로·URL).
   - `accent`·`colors`: 레퍼런스의 색 그대로(#rrggbb). 대비를 맞추려고 바꾸지 않는다.
   - `font`: `variants.json`에 같은 글꼴이 있으면 그 키, 없으면 `{"imports": [...], "body": "...", "display": ...}`. 한글을 지원하는 웹폰트를 쓴다. 같은 글꼴을 못 구하면 가장 비슷한 것을 쓰고 보고에 "OO 대신 OO"라고 적는다(글꼴을 구하지 못한 것만 적는다).
   - `heading`: 가장 가까운 `plain`/`bar`/`rule` (실제 모양은 `extraCss`가 덮어도 된다).
   - `fontScale`(선택): 레퍼런스의 글자 크기 그대로. 범위 제한 없음.
   - `extraCss`: 레퍼런스의 배치·장식을 `portfolio/theme/extra.css`에 제한 없이 쓴다(글자 크기, 쪽 구조, 면 색, 그리드 모두 가능).
   - `why`: "레퍼런스 그대로" 한 줄.
4. `pagePlan`은 레퍼런스의 쪽 구성대로 쓴다. 레이아웃 키(`layout`)·이야기 모양은 정하지 않아도 된다. `imageSlots`는 레퍼런스에서 이미지가 있는 자리에 맞춰 정한다(기록된 이미지를 어디에 둘지는 레퍼런스의 비슷한 자리를 따른다. 레퍼런스에 이미지 자리가 없으면 쓰지 않아도 된다).
5. 내용은 바꾸지 않는다. 레퍼런스에 있는 칸(예: 수상 목록)이 기록에 없으면 비워 두거나 칸을 뺀다 — 레퍼런스에 맞추려고 내용을 지어내지 않는다. 기록에 있는데 레퍼런스에 맞는 자리가 없는 내용은 레퍼런스의 비슷한 블록 모양으로 넣는다.

## 1-B. 레퍼런스가 없을 때 — 첫 PDF용 기본값 (나중에 사용자가 고른다)

`python3 <이 스킬 디렉터리>/scripts/make_theme.py --list`로 선택지를 본다. 첫 PDF는 묻지 않고 아래로 만든다. 사용자는 첫 PDF 뒤 "디자인 고르기"에서 실제 쪽 시안을 보고 바꾼다.

- `look`: `minimal`

- `accent`: 첫 프로젝트 로고(`Read`로 연다)의 주된 색에 가장 가까운 `accents` 값. 로고가 흑백·없음이면 `--auto <이름>`의 값.
- `font`·`heading`: `make_theme.py --auto <이름>`의 추천을 쓴다(사람마다 갈리게 이름 해시로 정한 값). 내용상 분명히 안 맞는 이유가 있을 때만 바꾸고 `why`에 적는다.
- `source: "auto"`, `reference: null`, `why`: "로고 파란색 → blue" 같은 한 줄.

## 1-C. 디자인 고르기 — 첫 PDF 뒤 (사용자 결정 D-DES-15)

build가 첫 PDF의 스크립트 검사를 통과시킨 뒤, 디자인 리뷰 루프 **전에** 이 절차를 부른다. `style.source`가 `user`이거나 `reference`(레퍼런스 그대로, D-DES-16)면 하지 않는다(사용자가 "디자인 다시"라고 하면 다시 한다).

1. 시안을 만든다. 사용자의 실제 1·2쪽을 스타일마다 렌더한다.
   ```bash
   python3 <이 스킬 디렉터리>/scripts/make_previews.py portfolio --vary look
   python3 <이 스킬 디렉터리>/scripts/make_previews.py portfolio --vary font --pages 1
   python3 <이 스킬 디렉터리>/scripts/make_previews.py portfolio --vary accent --values <후보1>,<후보2>,<후보3> --pages 2
   ```
   강조색 후보는 로고에서 뽑은 색(대비 4.5:1이 안 되면 같은 색상에서 어둡게) 1~2개 + `accents`에서 어울리는 것 1~2개. 마지막 실행의 비교 페이지가 `portfolio/review/looks/index.html`을 덮어쓰므로, 세 번 돌린 뒤 사용자에게는 시안 폴더(`portfolio/review/looks/`)와 각 `page-N.png`를 알려준다.
2. 시안을 직접 연다(`Read`로 page-1·2.png). 띠가 종이 끝에 닿는지, 띠 위 글자가 보이는지, 넘침이 없는지 확인하고 깨진 시안은 선택지에서 뺀다.
3. 채팅 본문에 시안 경로와 각 시안의 차이(한 줄씩)를 먼저 쓰고, `AskUserQuestion` 한 번(4문항)으로 묻는다.
   - 전체 스타일: `looks` 4개 (label + 무엇이 달라 보이는지)
   - 강조색: 후보 2~3개 (이름·hex·어디서 뽑았는지). 직접 입력은 "기타"로 받는다
   - 글꼴: 5개 중 4개를 선택지로, 나머지는 설명에 적고 "기타"로 받는다
   - 서비스 화면 배치: `screenLayouts`의 `wide`(크게) / `side`(옆에). **세로형·정사각형 서비스 화면이 있는 프로젝트가 있을 때만 묻는다**(`image_info.py`로 비율 확인). 가로형 화면은 옆에 두면 작아지고 쪽이 비어서 항상 크게 둔다 — 선택지 설명에 "가로형인 <프로젝트> 화면은 어느 쪽이든 크게 둔다"를 적는다
4. 답을 `style`에 쓴다: `source: "user"`, `look`, `accent`(대비만 통과하면 팔레트 밖 색도 된다), `font`, `why`에 "사용자 선택"과 고른 이유. 서비스 화면 배치는 `design.json`의 `layoutPrefs.screen`에 쓴다. 제목 모양(`heading`)은 묻지 않고 look에 맞춰 AI가 정한다(editorial → `plain`, 나머지는 기존 값).
5. `make_theme.py`로 테마를 다시 만들고 build로 돌아간다. build는 HTML을 다시 렌더하고 검사·디자인 리뷰 루프를 돈다.

## 2. 테마 파일을 만든다

```bash
python3 <이 스킬 디렉터리>/scripts/make_theme.py portfolio/design.json portfolio/theme
```

`tokens.css`·`components.css`·`style.css`가 생긴다. "테마 검사 실패"가 나오면 그 항목(대비, 글자 범위, 허용 안 된 값)을 고쳐 다시 돌린다. 이 파일들을 손으로 고치지 않는다.

`theme/design.base.json`을 `portfolio/design.json`의 바탕으로 사용한다. 다음 항목을 채운다.

- `style`
- `imageSlots`
- `pagePlan`
- `updated`

`design.base.json`의 기존 필드와 구조를 유지한다.

- 쓸 수 있는 레이아웃은 `design.base.json`의 `layouts`에 있는 키다. 키 목록의 원본은 그 파일이고, 아래 "콘텐츠 유형별 레이아웃 선택"의 표가 유형과 키를 1:1로 대응시킨다. `layout_check.py`도 같은 파일을 읽는다. 키를 더하거나 빼면 그 파일, 아래 표, build "레이아웃 구현", `components.css` 부품, `layout_check.py`의 부품 표를 함께 고친다.
- `imageSlots`와 `pagePlan`의 항목 구조는 `design.base.json`의 `schemas`를 따른다.

실제 파일에 정의되지 않은 필드나 레이아웃을 임의로 만들지 않는다. 새 레이아웃이 필요하면 `layouts`에 먼저 추가하고(설명 한 줄), build의 "레이아웃 구현"에 같은 키로 구현을 적는다.

# 색

색은 `style`(강조색·`colors`)로 정하고 `make_theme.py`가 흰 바탕 대비(4.5:1)를 검사한다(레퍼런스가 있으면 검사하지 않고 레퍼런스 색 그대로). 레퍼런스가 없을 때 기본 본문·보조·구분선 색은 `#16181d`·`#5b616e`·`#e2e8f0`이다. 대비만 따로 보려면 `python3 <이 스킬 디렉터리>/scripts/contrast.py <색> #ffffff`.

## 색 사용 규칙

- 배경은 기본적으로 흰색을 유지한다.
- 본문은 읽기 쉬운 어두운 색을 사용한다.
- 보조색은 메타데이터, 부가 설명 등에 사용한다.
- 구분선은 콘텐츠를 구분하는 데 필요한 경우에만 사용한다.
- 강조색은 중요한 수치, 핵심 키워드, 링크 등 제한된 대상에 사용한다.
- 강조색을 넓은 면적의 배경으로 남용하지 않는다. 예외는 사용자가 고른 look의 머리 띠(1쪽 머리·프로젝트 첫머리) 하나뿐이다.
- 색상만으로 정보의 의미를 전달하지 않는다.

같은 의미를 가진 요소에는 같은 색상 규칙을 적용한다.

예를 들어 강조색이 링크를 나타낸다면, 다른 페이지에서 같은 역할을 하는 요소에도 동일한 규칙을 사용한다.

# 타이포그래피

## 기본 원칙

글자 크기는 장식이 아니라 정보 위계를 나타낸다.

모든 텍스트를 크게 만들거나 굵게 만드는 방식으로 중요도를 표현하지 않는다.

다음 순서로 위계를 구분한다.

1. 페이지 제목
2. 섹션 제목
3. 핵심 메시지
4. 본문
5. 메타데이터와 부가 설명

글자 크기, 굵기, 여백을 조합해 위계를 표현한다.

## 기본 글자 크기

기본 디자인 시스템의 글자 크기는 다음을 따른다.

| 요소 | 크기 |
|---|---:|
| 이름 | 36pt |
| 페이지 제목 | 24pt |
| 섹션 제목 | 18pt |
| 부제목 | 14pt |
| 본문 | 11pt |
| 메타데이터 | 10pt |
| 캡션 | 9pt |
| 코드 | 9.5pt |

이 값은 기본값이며, 실제 적용은 기존 `tokens.css`의 정의를 따른다.

CSS 토큰에 정의된 크기와 이 문서의 값이 다르다면 임의로 CSS 토큰을 수정하지 않는다.

필요한 경우 실제 적용 결과를 검토하고, 토큰 변경이 필요하다고 판단되면 사용자 요청 또는 디자인 시스템 변경 절차에 따라 처리한다.

## 강조 규칙

- 본문과 같은 크기의 굵은 글씨를 우선 사용한다.
- 강조색은 필요한 부분에만 사용한다.
- 본문 전체를 굵게 처리하지 않는다.
- 한 문단에서 여러 표현을 동시에 강조하지 않는다.
- 측정된 before → after 수치(측정 조건이 있는 것)는 개수 제한 없이 강조한다. 그 쪽의 핵심 수치는 부제목 크기로, 보조 수치는 본문 크기 굵게로 쓴다. 측정 결과가 아닌 수치(개수, 기간, 사용자 수)는 부제목 크기로 키우지 않는다.
- 중요한 숫자와 결과는 주변 문장보다 먼저 눈에 들어오도록 배치한다.
- 강조 요소가 많아져 중요도 차이가 사라지지 않도록 한다.

## 가독성 규칙

- 본문은 충분한 줄 간격을 유지한다.
- 긴 문장은 적절한 길이의 문단으로 구분한다.
- 글자가 작아지는 방식으로만 콘텐츠를 한 페이지에 넣지 않는다.
- 캡션과 메타데이터는 보조 정보로만 사용한다.
- 본문을 캡션 크기로 축소해 페이지를 맞추지 않는다.
- 코드와 표는 실제 인쇄 크기에서 읽을 수 있는지 확인한다.

콘텐츠가 많다면 먼저 레이아웃을 변경하거나 페이지를 추가할 수 있는지 검토한다.

# 여백과 그리드

## 기본 원칙

모든 페이지는 동일한 디자인 시스템을 공유하지만, 콘텐츠의 배치 방식은 달라질 수 있다.

그리드는 요소를 기계적으로 정렬하기 위한 것이 아니라 정보의 관계를 명확하게 만드는 기준이다.

다음 규칙을 따른다.

- 페이지마다 좌우 기준선을 일관되게 유지한다.
- 제목과 본문 사이의 관계를 명확하게 한다.
- 서로 관련된 요소는 가까이 배치한다.
- 관련이 없는 요소 사이에는 충분한 간격을 둔다.
- 페이지 가장자리와 콘텐츠 사이에 안정적인 여백을 확보한다.
- 텍스트와 이미지가 불필요하게 겹치지 않도록 한다.
- 요소를 배치하기 위해 여백을 무조건 채우지 않는다.

## 여백 사용

여백은 낭비되는 공간이 아니다.

여백은 콘텐츠의 그룹을 구분하고 중요한 요소를 돋보이게 한다.

빈 공간이 있다는 이유만으로 장식 요소를 추가하지 않는다.

반대로 여백이 지나치게 많아 핵심 콘텐츠가 작아지거나 페이지가 비효율적으로 사용된다면 레이아웃을 다시 검토한다.

## 페이지 밀도

페이지의 시각적 밀도는 콘텐츠의 성격에 따라 달라질 수 있다.

- 표지와 소개 페이지는 여백을 충분히 확보하되, 위 50% 상한 안에서 확보한다.
- 문제 해결 과정은 문제, 접근, 결과가 명확히 구분되도록 한다.
- 아키텍처 페이지는 구조를 이해하는 데 필요한 공간을 확보한다.
- 텍스트가 많은 페이지는 읽기 흐름과 문단 구분을 우선한다.
- 성과를 보여주는 페이지는 핵심 수치와 그 근거를 함께 배치한다.

모든 페이지의 밀도를 동일하게 만들지 않는다.

**단, 마지막 쪽을 뺀 모든 쪽은 여백이 50%를 넘으면 안 된다**(사용자 결정 2026-10-09). 채움(내용 영역 중 글자·이미지·상자가 차지하는 세로 높이)이 50% 미만이면 `export.py`가 실패시킨다. 1쪽도 예외가 아니다. `pagePlan`을 짤 때 한 쪽에 내용이 너무 적게 배정되지 않게 하고, 모자라면 build가 다음 쪽 블록을 당기거나 쪽을 합친다.

# 페이지 구성 원칙

## 기본 원칙

페이지 구성은 콘텐츠를 기준으로 결정한다.

모든 프로젝트를 동일한 템플릿에 끼워 넣지 않는다.

페이지 레이아웃을 선택할 때 다음 질문을 고려한다.

- 이 페이지에서 가장 중요한 정보는 무엇인가?
- 독자가 가장 먼저 봐야 하는 요소는 무엇인가?
- 텍스트와 이미지 중 무엇이 핵심 정보를 더 잘 전달하는가?
- 문제와 해결 과정이 한눈에 연결되는가?
- 결과를 뒷받침하는 근거가 충분히 보이는가?
- 페이지를 읽기 위해 불필요한 시선 이동이 필요한가?

레이아웃은 콘텐츠를 돋보이게 해야 하며, 콘텐츠가 레이아웃에 맞춰 왜곡되어서는 안 된다.

## 첫 페이지

첫 페이지에는 다음 정보를 배치한다.

1. 이름
2. 한 줄 소개
3. 자기소개
4. 연락처
5. 기술 스택
6. 활동 (교내·대회·기업 프로젝트·동아리 등, 기간 또는 날짜와 함께)
7. 수상 및 자격 정보 (날짜와 함께)

첫 페이지에는 프로젝트 목록을 배치하지 않는다.

프로젝트 내용은 두 번째 페이지부터 시작한다.

첫 페이지의 목적은 지원자를 빠르게 파악할 수 있게 하는 것이다.

다음 규칙을 따른다.

- 이름을 가장 먼저 인식할 수 있도록 한다.
- 한 줄 소개에서 지원자의 핵심 정체성이 드러나도록 한다.
- 연락처는 쉽게 찾을 수 있도록 배치한다.
- 기술 스택은 읽기 쉬운 텍스트 형태로 구성한다.
- 활동과 수상 및 자격 정보는 실제 보유한 정보만 사용하고, 항목마다 날짜(기간)를 오른쪽에 맞춰 보여준다(D-P1-4). 기록에 "활동 없음"이면 활동 줄을 두지 않는다.
- 모든 요소를 같은 크기로 배치하지 않는다.
- 불필요한 장식이나 과도한 자기소개 문구를 추가하지 않는다.

첫 페이지를 채우기 위해 본문에 없는 정보를 만들어내지 않는다.

정보가 적어도 여백이 50%를 넘지 않게 한다. 블록 간격, 기술 분류별 나열, 수상·자격증의 기관·내용 한 줄로 채우고, 그래도 모자라면 build가 사용자에게 1쪽에 넣을 내용을 묻는다.

## 프로젝트 페이지

**프로젝트는 항상 이 순서로 설명한다** (사용자 결정 2026-10-09, `export.py`가 순서를 검사해 어기면 실패).

| 순서 | 블록 | 내용 | 없을 때 |
|---|---|---|---|
| 1 | 로고·이름·기간 | 로고 → 프로젝트 이름, **같은 줄 오른쪽에 기간**("2026.03 ~ 운영 중") | 필수 |
| 2 | 한 줄 소개 | 무슨 서비스인지 한 문장 | 필수 |
| 3 | 팀원 | 팀 구성 + 본인 역할 | 필수 (개인 프로젝트면 "개인 프로젝트") |
| 4 | 사용 기술 | 이 프로젝트에서 쓴 기술, 분류별 쉼표 목록 | 필수 |
| 5 | 기능 소개 | 주요 기능 3~5개. 서비스 화면을 여기 옆이나 위에 둔다 | 기록에 없으면 생략 |
| 6 | 주요 성과 | 측정된 before → after(크게) + 측정 없는 성과(실사용 시작, 사용자 수, 구현 규모 등, 본문 크기) | 기록에 없으면 생략 |
| 7 | 세부 설명 | 트러블슈팅, 인프라 전환, 기술 결정 등 실제로 한 일. 섹션마다 콘텐츠에 맞는 레이아웃 | 필수 |
| 8 | 전체 회고 | 작업별 회고를 모두 여기로 모은다. 작업 이름을 라벨로 단다. 원문 그대로 | 사용자가 말한 회고가 없으면 생략 |

- 1~6은 프로젝트 첫 쪽(`project-overview`)에 둔다. 7은 **작업마다** 그 작업의 이야기 모양에 맞는 레이아웃으로 이어지고(아래 "작업의 이야기 모양", D-DES-13), 8은 프로젝트 마지막(`retrospective`)이다.
- 작업 회고를 그 작업 섹션 아래에 두지 않는다. 모두 8로 모은다.

프로젝트 페이지는 프로젝트의 개수보다 각 프로젝트에서 전달할 핵심 경험을 기준으로 구성한다.

가능하면 다음 정보를 독자가 쉽게 찾을 수 있게 한다.

- 프로젝트의 목적
- 해결하려던 문제
- 본인이 수행한 작업
- 기술적 판단과 선택
- 결과와 측정 근거
- 회고 또는 배운 점

순서는 위 표로 고정이고, 각 블록을 어떤 형식(목록·표·카드 등)으로 보여줄지는 콘텐츠에 맞게 정한다.

실제 콘텐츠에 존재하는 정보만 사용한다.

근거가 없는 성과나 기술적 판단을 새로 추가하지 않는다.

## 페이지 분리

한 페이지에 콘텐츠가 지나치게 많이 들어간다면 페이지 분리를 검토한다.

특히 다음과 같은 경우 분리를 고려한다.

- 문제와 해결 과정이 한 페이지에서 명확하게 구분되지 않는 경우
- 아키텍처 다이어그램과 설명을 함께 배치하기 어려운 경우
- 핵심 수치가 다른 텍스트에 묻히는 경우
- 이미지나 코드가 읽을 수 없을 정도로 작아지는 경우
- 서로 다른 주제가 하나의 페이지에서 경쟁하는 경우

단순히 페이지 수를 줄이기 위해 가독성을 희생하지 않는다.

반대로 페이지 수를 늘리기 위해 하나의 짧은 내용을 불필요하게 분리하지 않는다.

페이지 레이아웃은 콘텐츠의 성격에 따라 선택한다.

아래 유형은 `design.base.json`의 `layouts` 키와 이렇게 대응한다. `pagePlan`에는 키를 쓴다.

|---|---|
| 1. 프로젝트 개요 | `project-overview` |
| 2. 문제 해결 | `problem-solving` |
| 3. 성능 비교 | `metric-compare` |
| 4. 아키텍처와 시스템 구조 | `architecture` |
| 5. 기술적 의사결정 | `decision` |
| 6. 코드와 구현 설명 | `code` |
| 7. 회고와 배운 점 | `retrospective` |
| 8. 텍스트 중심 콘텐츠 | `text` |
| 9. 이미지와 스크린샷 | `image-feature` |
| 10. 시간 순 사건 | `timeline` |
| 11. 흐름을 바꾼 기능 | `flow-compare` |
| 12. 처리 단계 | `process-flow` |
| (첫 페이지) | `profile` |

## 작업의 이야기 모양 (사용자 결정 D-DES-13, 2026-10-10)

세부 설명의 **작업 하나하나**에 레이아웃 키를 정한다. 쪽 단위가 아니라 작업 단위다. 기준은 "이 작업이 어떤 이야기인가"다. 모든 작업을 상황·원인·해결·결과 라벨 행으로 그리면, 내용이 달라도 모든 쪽과 모든 사람의 포트폴리오가 같은 형식으로 보인다(2026-10-10, 디자인만 다르게 4번 만든 결과가 한눈에 같은 문서로 보였다). 원칙도 "모든 프로젝트가 이 구조를 따를 필요는 없다, 가장 자연스러운 구조를 고른다"고 한다.

키를 고르는 것으로 끝나지 않는다. **키마다 독자가 정보를 이해하는 방식이 다르다.** 아래 "시각 구조"와 "가장 먼저 보이는 것"이 지켜지지 않으면 키를 바꿔도 결과는 같아 보인다(예: `timeline`인데 제목과 설명을 세로로 나열만 함). 시각 구조는 `components.css`의 부품으로 구현돼 있고, `layout_check.py`가 섹션 안에 그 부품이 있는지 검사한다.

| 이야기 모양 | 기록에서 보이는 신호 | 키 | 시각 구조 (부품) | 가장 먼저 보이는 것 |
|---|---|---|---|---|
| 수치가 단계적으로 바뀐 개선 | 측정된 before → after, 중간 단계 수치("1차 600ms") | `metric-compare` | 섹션 맨 위에 대표 수치를 크게(`.ba.ba-lead`), 그 아래 단계 카드를 가로로 나란히(`.stage-cards`) — 왼쪽에서 오른쪽으로 수치가 바뀌는 순서 | 개선 결과 수치 |
| 시간 순으로 벌어진 일 | 기간·날짜·"N일 동안", 발견 → 원인 → 수정 순서, 장애·버그 | `timeline` | 왼쪽 세로 시간축 + 점, 항목마다 시점 → 한 일 → 설명(`.timeline`). 마지막 점(해결)만 채운 점 | 사건이 진행된 과정 |
| 사람·업무 흐름을 바꾼 기능 | 기존 절차와 바뀐 절차, 역할(학생·선생님·관리자)별 행동 | `flow-compare` | 좌우 두 열: 기존 흐름(회색 상자)과 바뀐 흐름(강조 상자)을 같은 높이에서 단계 상자 + 아래 화살표로(`.flow-compare`). 단계 수 차이가 한눈에 보인다 | 무엇이 달라졌는지 |
| 처리 단계가 핵심인 기능 | 파이프라인(업로드 → 분할 → 임베딩 → 검색 → 답변), 요청 처리 순서 | `process-flow` | 번호 붙은 단계 상자를 가로로 잇고 화살표로 연결(`.process-flow`), 아래에 설계 포인트 | 시스템이 동작하는 순서 |
| 구조를 바꾼 작업 | 구성 요소를 없애거나 합침, 구조도 전·후 | `architecture` | 구조도를 본문 폭으로 먼저(전·후면 같은 크기 틀로 나란히), 구성 요소 설명은 그 아래 1~2열 | 구성 요소 간 관계 |
| 대안 중에 고른 선택 | 기술 선택의 이유·대안·트레이드오프 | `decision` | 채택 카드(강조 면 + 왼쪽 강조선)에 선택 → 이유, 카드 아래쪽 흐린 글자로 대안·안 고른 이유(`.decision-card`). 선택이 여럿이면 카드 여러 장 | 무엇을 왜 골랐는지 |
| 원인을 파고든 분석 | 가설·확인·원인이 이야기의 중심이고 위 신호가 약함 | `problem-solving` | 라벨이 붙은 단계 목록(`.steps`). 라벨은 일반적인 "상황·원인·해결"이 아니라 기록의 실제 분석 단계("가설", "EXPLAIN 확인", "발견", "원인")로 단다 | 어떻게 원인을 찾았는지 |
| 위 어디에도 안 맞는 설명 | — | `text` | 단일 열 본문, 소제목 | — |

- **콘텐츠에 가장 맞는 키가 먼저다.** 다양성은 그다음이다. 신호가 비슷하게 맞는 키가 둘이면, 이미 쓴 키와 다른 쪽을 고른다.
- 같은 키가 콘텐츠에 맞으면 다시 써도 된다(예: 측정된 성능 개선이 둘이면 둘 다 `metric-compare`). 그 섹션에 `repeatReason`을 한 줄 적는다(build가 `data-layout-repeat`로 옮긴다). 같은 키를 피하려고 맞지 않는 키를 고르지 않는다.
- **범용 형식이 절반을 넘으면 안 된다.** `problem-solving`(라벨 행)과 `text`는 어떤 작업에도 쓸 수 있어서, 이게 많아지면 모든 작업이 같은 형식으로 보인다(2026-10-10 실제로 그랬다). 세부 설명이 3개 이상인 프로젝트에서 이 둘이 각각 절반을 넘으면 `layout_check.py`가 실패시킨다. 다른 키의 섹션 안에 라벨 행을 넣어도 실패한다.
- 한 작업에 신호가 여럿이면 독자가 **가장 먼저 봐야 할 것**으로 고른다. 예: 성능 개선은 수치가 먼저(`metric-compare`), 46일 반복 장애는 시간 흐름이 먼저(`timeline`).
- 모양을 고르려고 기록에 없는 내용을 만들지 않는다. 타임라인의 시점, 흐름의 단계, 단계 카드의 수치는 기록에 있는 것만 쓴다. 신호가 기록에 없으면 그 모양을 고르지 않는다.
- 기술 선택이 여러 개면 한 `decision` 섹션에 카드 여러 장으로 모은다.

## 1. 프로젝트 개요

적합한 콘텐츠:

- 프로젝트 소개
- 개발 목적
- 사용 기술
- 팀 구성
- 담당 역할

구성 원칙:

- 프로젝트 이름과 목적을 명확하게 보여준다.
- 기술 스택과 역할은 빠르게 훑을 수 있도록 구성한다.
- 프로젝트의 핵심 특징이 있다면 한눈에 보이도록 한다.
- 개요 정보가 지나치게 많은 영역을 차지하지 않도록 한다.

## 2. 문제 해결

적합한 콘텐츠: 원인을 파고든 분석 자체가 이야기의 중심인 작업(가설 → 확인 → 원인). 성능 개선·장애·버그라도 수치가 먼저면 `metric-compare`, 시간 흐름이 먼저면 `timeline`이 맞다(위 "작업의 이야기 모양"). 한 프로젝트에 한 번이 기본이다.

구성 원칙:

- 문제와 해결 방법이 명확하게 구분되어야 한다.
- 작업의 과정과 결과가 시각적으로 연결되어야 한다.
- 중요한 측정 수치가 있다면 비교하기 쉽게 배치한다.
- 수치가 있다면 측정 조건과 대상을 확인할 수 있도록 한다.
- 결과만 강조하고 문제나 해결 과정을 생략하지 않는다.

문제 해결 과정이 핵심이라면 단순한 기술 스택 나열보다 문제와 해결의 관계를 우선한다.

## 3. 성능 비교

적합한 콘텐츠:

- 최적화 전후 응답시간
- 쿼리 성능 비교
- 부하 테스트 결과
- 리소스 사용량 변화

구성 원칙:

- 비교 대상과 비교 기준이 명확해야 한다.
- 전후 상태가 혼동되지 않아야 한다.
- 수치의 단위가 명확해야 한다.
- 핵심 수치가 주변 텍스트에 묻히지 않아야 한다.
- 측정 조건이 결과 해석에 중요하다면 함께 표시한다.
- 그래프는 실제 데이터와 일치해야 한다.

실제 데이터가 없으면 임의의 그래프나 수치를 생성하지 않는다.

수치의 의미를 과장하는 시각화를 사용하지 않는다.

## 4. 아키텍처와 시스템 구조

적합한 콘텐츠:

- 서비스 아키텍처
- 모듈 간 관계
- 데이터 흐름
- 요청 처리 흐름
- 외부 시스템 연동

구성 원칙:

- 구성 요소 간 관계가 명확해야 한다.
- 화살표는 실제 흐름과 일치해야 한다.
- 중요한 구성 요소가 시각적으로 구분되어야 한다.
- 연결선이 불필요하게 교차하지 않도록 한다.
- 각 요소의 설명은 해당 요소와 가까이 배치한다.
- 실제 구조에 없는 구성 요소를 추가하지 않는다.

아키텍처 다이어그램을 단순히 화려하게 만드는 것보다 독자가 구조를 이해할 수 있도록 하는 것이 우선이다.

## 5. 기술적 의사결정

적합한 콘텐츠:

- 기술 선택 이유
- 대안 비교
- 아키텍처 결정
- 트레이드오프
- 설계 변경

구성 원칙:

- 문제 상황과 선택의 관계가 명확해야 한다.
- 선택한 방법과 대안이 혼동되지 않아야 한다.
- 판단 기준이 있다면 읽기 쉽게 보여준다.
- 선택의 결과와 한계가 있다면 구분해서 표현한다.

근거가 없는 장단점이나 비교 결과를 새로 작성하지 않는다.

## 6. 코드와 구현 설명

적합한 콘텐츠:

- 핵심 코드
- 알고리즘
- 구현 방식
- 기술적 해결책

구성 원칙:

- 코드 전체를 그대로 나열하지 않는다.
- 콘텐츠에서 중요한 코드 부분이 무엇인지 분명해야 한다.
- 코드가 실제 인쇄 크기에서도 읽을 수 있어야 한다.
- 코드 설명과 코드의 관계가 명확해야 한다.
- 긴 코드를 작은 글씨로 축소해 한 페이지에 넣지 않는다.

기존 콘텐츠에 코드가 없다면 디자인 단계에서 임의로 코드를 작성하지 않는다.

## 7. 회고와 배운 점

적합한 콘텐츠:

- 프로젝트 회고
- 시행착오
- 설계의 한계
- 개선 방향
- 학습한 내용

구성 원칙:

- 회고의 핵심 문장을 쉽게 찾을 수 있어야 한다.
- 본문과 보조 설명의 위계를 구분한다.
- 여러 회고 항목이 있다면 서로 구분되도록 배치한다.
- 불필요한 인용구나 장식적인 문구를 추가하지 않는다.

회고 내용을 새로 작성하거나 기존 의미를 변경하지 않는다.

## 8. 텍스트 중심 콘텐츠

적합한 콘텐츠:

- 긴 설명
- 문제 분석
- 상세한 구현 과정
- 기술적 배경

구성 원칙:

- 문단의 논리적 흐름을 유지한다.
- 소제목으로 내용을 구분한다.
- 본문을 읽기 어려울 정도로 좁게 배치하지 않는다.
- 글자 크기를 무리하게 줄이지 않는다.
- 불필요한 카드와 테두리를 추가하지 않는다.

텍스트가 많다는 이유만으로 무조건 두 개 이상의 열로 나누지 않는다.

내용의 읽기 순서가 명확해지는 경우에만 다단 레이아웃을 사용한다.

## 9. 이미지와 스크린샷

적합한 콘텐츠:

- 서비스 화면
- 실제 동작 화면
- 모니터링 결과
- 테스트 결과
- 구현 결과물

구성 원칙:

- 이미지가 전달하는 정보가 무엇인지 명확해야 한다.
- 이미지와 설명을 가까이 배치한다.
- 이미지의 원본 비율을 유지한다.
- 중요한 내용이 잘리지 않도록 한다.
- 불필요하게 큰 이미지로 본문을 밀어내지 않는다.
- 이미지에 포함된 텍스트가 읽을 수 있는지 확인한다. 단, 측정 화면은 예외다(아래).

**측정 화면** (Gatling·대시보드·EXPLAIN 결과 등, `kind: measure`)은 증빙이다. 개선 전·후 두 장은 **항상 같은 쪽에 나란히**, 각각 본문 폭의 절반 이하, 묶음 높이는 쪽의 30% 이하로 작게 둔다. 수치는 이미지가 아니라 바로 위 before → after 줄이 전달한다. 안의 글자가 읽히게 하려고 키우거나 두 쪽으로 나누지 않는다(사용자 결정 2026-10-09).

이미지를 단순한 장식으로 사용하지 않는다.

이미지의 내용이 불분명하다면 임의로 의미를 부여하지 않는다.

# 이미지 자리 설정

`portfolio/design.json`의 `imageSlots`에는 이미지가 들어갈 위치와 목적을 기록한다.

필드 구조는 `design.base.json`의 `schemas."imageSlots[]"`를 따른다(`id`, `file`, `kind`, `project`, `placement`, `size`).

## 프로젝트 필수 이미지 (사용자 결정 2026-10-08)

프로젝트마다 다음 두 장은 반드시 자리를 만든다.

| 이미지 | `kind` | 위치 |
|---|---|---|
| 프로젝트 로고 | `logo` | 프로젝트 첫머리, 이름 왼쪽. 높이는 이름 글자 높이 정도(약 28~36px), 원본 비율 유지 |
| 서비스 화면 (캡처·목업 모두 가능) | `screen` | 프로젝트 첫 쪽, 첫머리 바로 아래나 옆. 가로형은 본문 폭의 60~100%, 세로형은 오른쪽 열 45~60mm |

- 기록(`facts/<slug>.md`의 `## 이미지`)에 로고·서비스 화면 파일이 있으면 그 파일로 자리를 만든다.
- 사용자가 "없음"이라고 확인해 기록에 `로고 없음`·`서비스 화면 없음`이 있으면 그 자리만 만들지 않는다.
- 파일도 "없음" 기록도 없으면 design에서 자리를 지어내지 않는다. build가 PDF를 만들기 전에 사용자에게 요청한다.

## 이미지 자리 선정 원칙

이미지는 다음 조건 중 하나 이상을 만족할 때 사용한다.

- 서비스의 실제 결과물을 보여준다.
- 시스템 구조를 이해하는 데 도움이 된다.
- 구현 결과를 시각적으로 증명한다.
- 측정 결과나 테스트 결과를 명확하게 전달한다.
- 텍스트만으로 이해하기 어려운 정보를 보완한다.

다음과 같은 목적으로 이미지를 추가하지 않는다.

- 페이지가 비어 보인다는 이유
- 장식적인 균형을 맞추기 위한 목적
- 포트폴리오를 화려하게 보이게 하려는 목적
- 콘텐츠와 관계없는 분위기 연출

## 이미지 자리 지정 규칙

이미지 자리를 지정할 때 다음을 고려한다.

- 어떤 콘텐츠와 관련되는가?
- 이미지가 전달해야 하는 정보는 무엇인가?
- 페이지에서 어느 위치에 있어야 하는가?
- 어느 정도의 크기가 필요한가?
- 이미지가 없어도 콘텐츠가 이해되는가?

이미지 자리가 필요하지 않다면 억지로 만들지 않는다.

실제 이미지 파일이 존재한다고 가정하지 않는다.

**파일이 없는 빈 이미지 자리는 만들지 않는다.** 빈 자리는 PDF에서 빠져 그만큼 쪽이 비어 보이고, build는 빈 자리를 발견하면 design을 다시 부른다. 넣으면 좋을 이미지가 있으면 `imageSlots`가 아니라 끝 보고에 "넣으면 좋을 이미지"로 적는다.

# 페이지 계획

`portfolio/design.json`의 `pagePlan`에는 각 페이지의 구성 계획을 기록한다.

필드 구조와 허용되는 레이아웃 식별자는 `theme/design.base.json` 및 실제 빌드 파이프라인의 규칙을 따른다.

임의의 필드나 레이아웃 식별자를 만들지 않는다.

## 페이지 계획 원칙

각 페이지는 명확한 목적을 가져야 한다.

페이지 계획을 작성할 때 다음을 확인한다.

- 페이지의 핵심 주제가 무엇인가?
- 어떤 콘텐츠가 포함되는가?
- 어떤 레이아웃이 적합한가?
- 가장 먼저 보여야 할 정보는 무엇인가?
- 이전 페이지와 어떻게 연결되는가?
- 다음 페이지와 어떤 관계를 갖는가?

페이지 계획은 콘텐츠를 재작성하기 위한 것이 아니다.

기존 콘텐츠를 어떤 순서와 레이아웃으로 보여줄지 결정하는 것이다.

## 페이지 간 흐름

전체 포트폴리오는 하나의 문서처럼 읽혀야 한다.

다음 원칙을 따른다.

- 첫 페이지에서 지원자를 파악할 수 있어야 한다.
- 프로젝트 페이지는 핵심 경험을 전달해야 한다.
- 서로 관련된 페이지는 읽기 흐름이 이어져야 한다.
- 서로 다른 프로젝트는 시각적으로 구분할 수 있어야 한다.
- 모든 페이지가 동일한 구성으로 반복되지 않도록 한다.
- 레이아웃의 차이가 디자인 시스템의 일관성을 깨뜨리지 않도록 한다.

페이지를 구분하기 위해 매번 배경색을 바꾸거나 장식 요소를 추가하지 않는다. 고른 look의 머리 띠는 프로젝트 첫머리마다 같은 모양으로 반복되는 것이라 예외다.

제목, 여백, 그리드, 콘텐츠 구성만으로도 충분히 구분할 수 있는지 먼저 검토한다.

---

# 페이지 간 일관성

페이지마다 레이아웃은 달라질 수 있지만, 기본 디자인 규칙은 유지해야 한다.

다음 항목은 문서 전체에서 일관되게 유지한다.

- 글꼴 체계
- 색상 체계
- 제목과 본문의 위계
- 좌우 여백
- 정렬 기준
- 구분선 사용 방식
- 강조색 사용 방식
- 메타데이터 표현 방식
- 페이지 번호의 위치와 형식

다음 항목은 콘텐츠에 따라 달라질 수 있다.

- 열의 개수
- 텍스트와 이미지의 배치
- 수치와 그래프의 크기
- 다이어그램의 배치
- 콘텐츠 그룹의 개수
- 페이지의 시각적 밀도

일관성이란 모든 페이지가 똑같아 보이는 것이 아니다.

**같은 디자인 시스템 안에서 각 페이지가 자신의 목적을 가장 잘 수행하도록 구성하는 것**이다.

# 디자인 결정 절차

다음 순서로 진행한다.

## 1. 기존 설정 확인

다음 파일을 확인한다.

- `theme/design.base.json`
- `theme/variants.json`
- 기존 `portfolio/design.json` (특히 `style` — 있으면 레퍼런스를 다시 묻지 않는다)
- 기존 `portfolio/theme/`

파일 경로는 실제 스킬 디렉터리와 프로젝트 구조를 기준으로 확인한다.

파일이 존재하지 않는다면 존재한다고 가정하지 않는다.

## 2. 콘텐츠 파악

프로젝트의 기존 결과물에서 페이지 구성에 필요한 정보를 확인한다.

예를 들어 다음 파일이 존재한다면 활용할 수 있다.

- `outline`
- 프로젝트 설명
- facts
- 이미지 목록
- 기존 페이지 계획

실제 경로와 형식은 프로젝트의 기존 규칙을 따른다.

이 단계에서는 콘텐츠의 사실관계를 새로 판단하거나 본문을 수정하지 않는다.

## 3. 레이아웃 선택

각 콘텐츠의 성격을 기준으로 레이아웃을 선택한다. **세부 설명은 작업마다 위 "작업의 이야기 모양" 표로 키를 정해 `pagePlan`의 그 섹션(`sections[].layout`)에 적는다.** 쪽 `layout`을 물려받게 두지 않는다.

- 문제 해결은 문제와 해결 과정을 중심으로 구성한다.
- 성능 비교는 비교 대상과 수치가 잘 보이도록 구성한다.
- 아키텍처는 시스템의 관계와 흐름을 중심으로 구성한다.
- 회고는 핵심 문장과 설명의 위계를 중심으로 구성한다.
- 텍스트 중심 콘텐츠는 읽기 흐름을 우선한다.

적절한 레이아웃이 없다면 기존 레이아웃 중 가장 적합한 것을 선택한다.

빌드 시스템이 지원하지 않는 레이아웃을 임의로 만들지 않는다.

## 4. 이미지 자리 지정

이미지가 필요한 콘텐츠에 한해 이미지 자리를 지정한다.

로고·서비스 화면 외의 이미지는, 이미지가 없어도 충분히 이해할 수 있다면 요구하지 않는다. 로고·서비스 화면은 위 "프로젝트 필수 이미지"를 따른다.

## 5. 페이지 계획 작성

전체 페이지의 순서와 구성을 결정한다.

첫 페이지는 앞에서 정의한 구성을 유지한다.

프로젝트 콘텐츠는 두 번째 페이지부터 배치한다.

페이지별 목적과 콘텐츠가 명확하게 구분되는지 확인한다.

## 6. 설정 파일 작성

`theme/design.base.json`을 바탕으로 `portfolio/design.json`을 작성한다.

위 "테마 정하기"대로 `style`을 채우고 `make_theme.py`로 `portfolio/theme/`를 만든다.

기존 스키마를 유지한다.

## 7. 설정 검증

작성한 파일을 다시 읽어 다음을 확인한다.

- JSON 문법이 올바른가?
- 기존 스키마를 유지했는가?
- 필요한 페이지 계획이 들어 있는가?
- 이미지 자리가 실제 콘텐츠와 연결되는가?
- 지원되지 않는 레이아웃을 지정하지 않았는가?
- 세부 설명 작업마다 `sections[].layout`이 있고, 한 프로젝트 안에서 같은 키가 반복되면 `repeatReason`이 있는가? 한 키가 세부 설명의 절반을 넘지 않는가?
- `make_theme.py --check portfolio/design.json portfolio/theme`가 "테마 최신: 일치"인가?
- 기존 콘텐츠의 의미를 변경하지 않았는가?

검증할 수 없는 항목은 검증했다고 주장하지 않는다.

# 재실행 규칙

이 스킬은 다음 상황에서 다시 실행될 수 있다.

- 인터뷰가 끝난 뒤
- 디자인 설정이 없는 경우
- build가 디자인 설정의 갱신이 필요하다고 판단한 경우
- 사용자가 디자인 변경을 요청한 경우
- 사용자가 "디자인 다시 해줘"라고 요청한 경우

## 기존 설정이 있는 경우

기존 설정을 무조건 삭제하고 처음부터 작성하지 않는다.

먼저 기존 설정을 확인한다.

유효한 설정 중 유지할 수 있는 항목은 유지하고, 현재 콘텐츠와 맞지 않는 부분만 다시 결정한다.

단, 사용자가 전체 디자인을 다시 요청했다면 페이지 구성과 이미지 자리를 다시 검토한다.

## 디자인 변경 범위

사용자가 특정 요소의 변경을 요청했다면 해당 범위만 변경한다.

예:

- 특정 페이지의 레이아웃 변경
- 이미지 자리 변경
- 페이지 순서 변경
- 전체 페이지 구성 재검토
- 색상 변경 요청

디자인에는 두 층이 있다. 요청이 어느 층인지 먼저 가른다(D-DES-13).

| 층 | 무엇 | 바꾸는 곳 |
|---|---|---|
| 테마 | 색, 글꼴, 제목 모양, 레퍼런스 장식 | `style` → `make_theme.py` |
| 레이아웃 | 작업별 형식(이야기 모양 키), 쪽 나누기, 열 구성, 수치의 크기와 위치, 이미지와 글의 관계, 시선 흐름 | `pagePlan`(`layout`·`sections[].layout`) → build |

- **"디자인 다시 해줘", "다르게 해줘", "비슷해 보여"** → 두 층을 모두 다시 본다. 테마만 바꾸고 끝내지 않는다. 겉모습이 같아 보이는 이유는 대개 레이아웃이다(2026-10-10: 테마만 다른 4장이 한눈에 같은 문서로 보였다). 작업마다 이야기 모양 표로 키를 다시 고르고, 신호가 비슷하게 맞는 키가 둘이면 지난번과 다른 쪽을 고른다.
- **색·글꼴·제목 모양만 말한 요청** → 테마만 바꾼다. 레이아웃은 건드리지 않는다.
- **특정 쪽·작업의 레이아웃 요청** → 그 섹션의 키만 바꾼다.

색상 변경 요청은 `style`의 `accent`·`colors`만 바꾸고 `make_theme.py`를 다시 돌린다. 레퍼런스가 있는 테마라면 `source`는 그대로 둔다.

특정 페이지의 레이아웃 변경 요청이 전체 디자인 시스템 변경을 의미한다고 추측하지 않는다.

# 금지 사항

다음 작업은 수행하지 않는다.

1. 본문 내용을 새로 작성하는 작업
2. facts의 수치나 내용을 수정하는 작업
3. 근거가 없는 이미지나 그래프를 만드는 작업
4. `style`에 정한 것과 다른 색·글꼴을 쓰는 작업
5. `portfolio/theme/`의 CSS를 손으로 고치는 작업(`make_theme.py`로만 만든다)
6. `out/index.html` 수정
7. `out/portfolio.pdf` 수정
8. 빌드 결과물을 직접 편집해 디자인을 맞추는 작업
9. 지원되지 않는 레이아웃을 임의로 추가하는 작업
10. 모든 페이지를 같은 레이아웃으로 강제하는 작업
11. 페이지를 채우기 위한 장식 요소 추가
12. 글자 크기를 과도하게 줄여 페이지 수를 줄이는 작업
13. 실제로 존재하지 않는 이미지나 데이터를 있는 것처럼 취급하는 작업
14. 디자인을 위해 기존 콘텐츠의 의미를 변경하는 작업
15. 스키마를 확인하지 않고 `design.json`의 필드를 임의로 추가하는 작업

# 최종 원칙

이 스킬의 목적은 포트폴리오를 장식하는 것이 아니다.

**콘텐츠의 성격에 맞는 레이아웃을 선택하고, 일관된 디자인 시스템 안에서 지원자의 경험과 성과가 빠르게 읽히도록 만드는 것**이다.

디자인 시스템은 일관되게 유지한다.

페이지 레이아웃은 콘텐츠에 맞게 달리한다.

본문은 수정하지 않는다.

근거가 없는 콘텐츠를 만들지 않는다.

설정 파일만 작성하고, 실제 렌더링과 PDF 생성은 build 단계에 맡긴다.
