# 디자인 설정 (design)

> **먼저 읽는다** — 이 스킬을 불러오면 표시되는 기본 디렉터리(`Base directory for this skill`) 기준으로 `../../rules/principles.md`(제품 원칙)와 `../../rules/user-decisions.md`(사용자 결정 원본)를 읽는다. 이 문서의 규칙이 그 둘과 다르면 그 둘이 맞다. 같은 세션에서 이미 읽었으면 다시 읽지 않는다. **둘 중 하나라도 읽지 못하면(파일 없음·읽기 실패) 이 스킬의 작업을 시작하지 않는다** — 어떤 파일을 어느 경로로 찾았는지와 "원칙 문서를 읽지 못해 멈췄다"를 첫 줄에 알리고 끝낸다. 원칙 없이 기억이나 이 문서만으로 대신 진행하지 않는다.

> 사용자에게 말할 때는 `start` 스킬의 "사용자에게 쓰는 말" 표를 따른다. facts·outline·슬롯 같은 내부 이름을 채팅에 그대로 쓰지 않는다.

## 역할과 범위

이 스킬은 **설정 파일만** 쓴다: `portfolio/design.json`(테마 `style`, 이미지 자리 `imageSlots`, 쪽 계획 `pagePlan`)과 `make_theme.py`로 만든 `portfolio/theme/`. 디자인의 목적과 판단 기준(채용 담당자가 짧게 훑어도 가장 강한 경험과 성과가 보일 것, 수치는 본문에 묻히지 않게, 과장 금지)은 `principles.md`가 원본이다 — 여기서 다시 쓰지 않는다.

하지 않는 것: 본문·기록(facts)·회고를 쓰거나 고치기, `out/index.html`·`out/portfolio.pdf`를 고치기(디자인을 PDF에 반영하는 것은 build를 다시 도는 것), `theme/`의 CSS를 손으로 쓰기, 기록에 없는 이미지·그래프·수치를 있는 것처럼 다루기, 스키마(`design.base.json`)에 없는 필드·레이아웃 키를 만들기. 디자인 때문에 내용을 줄이거나 바꿔야 한다고 판단되면 고치지 말고 build에 넘긴다.

## 과거에 생긴 문제와 지금 규칙

규칙을 줄이거나 바꾸기 전에 이 표를 본다. 각 줄은 실제 실행에서 생긴 문제다(위키 `portfolio-harness-plugin`).

| 생긴 문제 | 원인 | 지금 규칙 (이 문서 위치) |
|---|---|---|
| 테마만 바꾼 4장이 한눈에 같은 문서 (10-10) | 모든 작업이 상황·원인·해결·결과 라벨 행. 차이가 강조색뿐 | 세부 설명은 작업마다 이야기 모양 키를 고른다. "다시 해줘"는 테마와 레이아웃 두 층을 다 본다 (작업의 이야기 모양, 다시 할 때) |
| 키만 `timeline`으로 바꾸고 모양은 세로 나열 그대로 | 키를 고르는 것과 그 모양을 그리는 것이 따로 | 키마다 정해진 부품(`components.css`)을 쓰고, `layout_check.py`가 섹션 안에 부품이 있는지 본다 |
| "같은 키 반복 금지" 때문에 맞지 않는 키를 고름 | 다양성 규칙이 적합성을 이김 | 콘텐츠 적합이 먼저. 반복은 `repeatReason` 한 줄로 허용, 절반 상한은 범용 형식(`problem-solving`·`text`)에만 |
| 미니멀 스위스 고정 → "AI 돌린 느낌", 레퍼런스를 줘도 강조색만 옮겨짐 | 고를 수 있는 축이 강조색 하나 | 레퍼런스가 있으면 그대로(D-DES-16), 없으면 사용자가 실제 쪽 시안을 보고 고른다(D-DES-15) |
| 레퍼런스로 PDF만 줬는데 같은 폴더의 HTML에서 CSS를 읽음 | 받은 것 밖을 열어 봄 | 사용자가 준 파일·URL만 연다 (1-A) |
| 빈 이미지 자리가 실측에 섞여 넘친다고 오판 → 자리를 1쪽으로 옮겨 1쪽이 빔 (2차) | 파일 없는 자리를 계획에 넣음 | 파일 없는 빈 자리를 만들지 않는다. 넣으면 좋을 이미지는 끝 보고로 (이미지 자리) |
| 폴더에 있던 로고를 묻지 않고 등록하고 출처까지 지어냄 | 파일이 있다는 것만으로 용도를 정함 | 기록(`## 이미지`)에 사용자가 확인한 것만으로 자리를 만든다 (이미지 자리) |
| 가로형(16:9) 서비스 화면을 옆 열에 두자 2쪽 35%가 빔 | 가로형이 오른쪽 열에서 작아짐 | 옆 배치는 세로형·정사각형만, 배치 질문도 그런 화면이 있을 때만 (1-C) |
| 전·후 구조도 크기가 다름 (222×290 / 175×195) | 짝 규칙이 측정 화면에만 있었음 | 전·후 이미지는 종류와 상관없이 같은 크기 틀 (이미지 자리) |
| 측정 화면을 글자가 읽히게 키워 쪽이 갈림 | 증빙과 본문을 구분 안 함 | 측정 화면은 증빙: 같은 쪽 나란히, 작게 (이미지 자리) |
| AI가 제안한 다이어그램 절반이 틀림 | 기록에 없는 구성 요소·화살표 | 구조도는 기록에 있는 구성 요소와 흐름만 (키별 주의) |
| 강조색 위 흰 글자용 `--accent-text`를 글자색으로 써서 안 보임 — 테스트 81개 통과 상태에서 렌더를 보고서야 발견 | 글자색=바탕색 검사가 없음 | 시안·첫 PDF는 쪽 이미지를 직접 열어 본다 (1-C, 완료 기준) |

| 기술 스택을 칩으로 나열 | 장식이 정보보다 앞섬 | 기술은 분류별 쉼표 목록 (디자인 시스템) |

| 문서마다 레이아웃 키 목록이 달랐음 | 키 목록을 여러 곳에 적음 | 키의 원본은 `design.base.json`의 `layouts` 하나 |
| 강조색이 "좋아진 값"으로 굳어 약점 점수(3.93)를 강조할 수단이 없음 | — | **미해결**(규칙 없음). 강조색은 측정된 개선 결과·핵심 키워드·링크에 쓴다. 약점을 강조할 일이 생기면 끝 보고에 적는다 |

## 파일

| 파일 | 내용 |
|---|---|
| `portfolio/design.json` | `style`, `imageSlots`, `pagePlan`, `layoutPrefs` (바탕은 `theme/design.base.json`) |
| `portfolio/theme/tokens.css` | 색·글꼴·글자 크기·간격 변수 (`make_theme.py`가 만든다) |
| `portfolio/theme/components.css` | before → after, 이야기 모양 부품 (원본 그대로 복사) |
| `portfolio/theme/style.css` | 제목 글꼴·제목 모양·전체 스타일 (`make_theme.py`가 만든다) |
| `portfolio/theme/extra.css` | 레퍼런스의 배치·장식 (레퍼런스가 있을 때만, 제한 없음) |

원본은 이 스킬 디렉터리의 `theme/`에 있다: `tokens.css`, `components.css`, `variants.json`(전체 스타일·강조색·글꼴·제목 모양·서비스 화면 배치), `variants/heading-*.css`, `variants/look-*.css`, `design.base.json`.

# 테마 정하기 (D-DES-1, D-DES-15, D-DES-16)

## 0. 레퍼런스를 묻는다 (한 번만)

`portfolio/design.json`에 `style`이 이미 있으면 묻지 않고 그대로 쓴다(사용자가 "디자인 다시 해줘"·"레퍼런스 바꿀래"라고 하면 다시 묻는다). 없으면 `AskUserQuestion` 한 번으로 묻는다.

> 참고하고 싶은 포트폴리오 디자인이 있어? 있으면 배치·색·글꼴까지 그대로 따라서 만들게. 없으면 첫 PDF를 만든 뒤 시안을 보여주고 고르게 할게.
> - 있어 — 파일 경로(PDF·이미지·HTML)나 URL을 알려줘
> - 없어 — 알아서 정해줘

## 1-A. 레퍼런스가 있을 때 — 레퍼런스 그대로 (D-DES-16)

**레퍼런스대로 만든다.** 배치, 쪽 구성, 블록 순서, 색, 글꼴, 글자 크기, 여백, 장식을 레퍼런스에서 가져온다. 이 문서의 "디자인 시스템", "첫 페이지", "프로젝트 페이지", "작업의 이야기 모양", 대비·글자 범위·여백 상한은 적용하지 않는다. "레퍼런스와 다른 점"을 만들지 않고, 디자인을 다시 묻지 않는다(시안 고르기도 없다). 검사는 내용만 남는다(build 참고).

1. **사용자가 준 파일·URL만 연다.** 이미지·PDF는 `Read`(PDF는 모든 쪽), HTML은 파일을 읽어 CSS 값을 그대로 가져온다. 같은 폴더의 다른 파일을 찾아 읽지 않는다. URL을 못 가져오면 "열지 못했다"고 말하고 스크린샷이나 파일을 달라고 한다. 열지 못한 레퍼런스를 본 것처럼 정하지 않는다.
2. 쪽마다 무엇이 어디에 어떤 크기로 있는지 `style.referenceLayout`(쪽별 서술, 문자열 배열)에 적는다: 쪽 크기(A4·연속), 1쪽 구성, 프로젝트 쪽의 블록 순서와 배치(열 수, 이미지 위치·크기), 제목·본문·캡션 크기와 굵기, 색(면 색 포함), 글꼴, 구분선·라벨·칩 같은 장식, 여백. build가 이것과 원본을 보고 HTML을 쓴다.
3. `style`: `source: "reference"`, `reference`(경로·URL), `accent`·`colors`(레퍼런스 색 그대로, #rrggbb), `font`(`variants.json`에 같은 글꼴이 있으면 그 키, 없으면 `{"imports": [...], "body": "...", "display": ...}` — 한글 웹폰트. 못 구하면 가장 비슷한 것을 쓰고 끝 보고에 "OO 대신 OO" — 끝 보고에 적는 것은 이것뿐), `heading`(`plain`/`bar`/`rule` 중 가장 가까운 것, 실제 모양은 `extraCss`가 덮어도 된다), `fontScale`(레퍼런스 크기 그대로, 범위 제한 없음), `extraCss`(배치·장식을 `portfolio/theme/extra.css`에 제한 없이), `why`("레퍼런스 그대로").
4. `pagePlan`은 레퍼런스의 쪽 구성대로 쓴다. 레이아웃 키는 정하지 않아도 된다. `imageSlots`는 레퍼런스의 이미지 자리에 맞춘다(기록된 이미지는 비슷한 자리에, 레퍼런스에 자리가 없으면 쓰지 않아도 된다).
5. **내용은 바꾸지 않는다.** 레퍼런스에 있는 칸이 기록에 없으면 비우거나 칸을 뺀다. 기록에 있는데 레퍼런스에 자리가 없는 내용은 비슷한 블록 모양으로 넣는다.

## 1-B. 레퍼런스가 없을 때 — 첫 PDF용 기본값

`python3 <이 스킬 디렉터리>/scripts/make_theme.py --list`로 선택지를 본다. 첫 PDF는 묻지 않고 아래로 만들고, 사용자는 첫 PDF 뒤 1-C에서 바꾼다.
- `look`: `minimal`
- `accent`: 첫 프로젝트 로고(`Read`로 연다)의 주된 색에 가장 가까운 `accents` 값. 로고가 흑백·없음이면 `--auto <이름>`의 값.
- `font`·`heading`: `make_theme.py --auto <이름>`의 추천(이름 해시). 내용상 분명히 안 맞을 때만 바꾸고 `why`에 적는다.
- `source: "auto"`, `reference: null`, `why`: "로고 파란색 → blue" 같은 한 줄.

## 1-C. 디자인 고르기 — 첫 PDF 뒤 (D-DES-15)

build가 첫 PDF의 스크립트 검사를 통과시킨 뒤, 디자인 리뷰 루프 **전에** 부른다. `style.source`가 `user`이거나 `reference`면 하지 않는다(사용자가 "디자인 다시"라고 하면 다시 한다).

1. 사용자의 **실제 1·2쪽**으로 시안을 만든다.
   ```bash
   python3 <이 스킬 디렉터리>/scripts/make_previews.py portfolio --vary look
   python3 <이 스킬 디렉터리>/scripts/make_previews.py portfolio --vary font --pages 1
   python3 <이 스킬 디렉터리>/scripts/make_previews.py portfolio --vary accent --values <후보1>,<후보2>,<후보3> --pages 2
   ```
   강조색 후보는 로고에서 뽑은 색(대비 4.5:1이 안 되면 같은 색상에서 어둡게) 1~2개 + `accents`에서 1~2개. 마지막 실행이 `review/looks/index.html`을 덮으므로 사용자에게는 시안 폴더(`portfolio/review/looks/`)와 `page-N.png`를 알려준다.
2. **시안 PNG를 직접 연다.** 띠가 종이 끝에 닿는지, 띠 위·부품 안 글자가 보이는지(글자색=바탕색), 넘침이 없는지 보고 깨진 시안은 선택지에서 뺀다.
3. 채팅 본문에 시안 경로와 각 시안의 차이(한 줄씩)를 먼저 쓰고, `AskUserQuestion` 한 번(최대 4문항)으로 묻는다.
   - 전체 스타일: `looks` 4개 (label + 무엇이 달라 보이는지)
   - 강조색: 후보 2~3개 (이름·hex·어디서 뽑았는지). 직접 입력은 "기타"
   - 글꼴: 4개를 선택지로, 나머지는 설명에 적고 "기타"로
   - 서비스 화면 배치 `wide`(크게) / `side`(옆에): **세로형·정사각형 서비스 화면이 있을 때만** 묻는다(build 스킬의 `scripts/image_info.py`로 비율). 가로형은 어느 쪽이든 크게 둔다고 설명에 적는다
4. 답을 `style`에 쓴다: `source: "user"`, `look`, `accent`(대비만 통과하면 팔레트 밖 색도 된다), `font`, `why`("사용자 선택" + 이유). 배치는 `layoutPrefs.screen`. 제목 모양은 묻지 않고 look에 맞춰 정한다(editorial → `plain`, 나머지는 기존 값).
5. `make_theme.py`로 테마를 다시 만들고 build로 돌아간다.

| look | 모양 |
|---|---|
| `minimal` | 흰 종이, 선과 여백으로만 구분 |
| `editorial` | 굵은 제목과 검은 가는 선, 1쪽 머리·프로젝트 첫머리 아래를 선으로 닫음. 세리프·명조 제목과 잘 맞음 |
| `color-band` | 1쪽 머리와 프로젝트 첫머리를 강조색 띠로 (종이 위·좌우 끝까지) |
| `dark-header` | 같은 자리를 어두운 띠로 |

## 2. 테마 파일을 만든다

```bash
python3 <이 스킬 디렉터리>/scripts/make_theme.py portfolio/design.json portfolio/theme
```

"테마 검사 실패"가 나오면 그 항목(대비, 글자 범위, 허용 안 된 값)을 고쳐 다시 돌린다. 레퍼런스가 없을 때 기본 본문·보조·구분선 색은 `#16181d`·`#5b616e`·`#e2e8f0`이고, 대비만 따로 보려면 `scripts/contrast.py <색> #ffffff`.

# 디자인 시스템 (레퍼런스가 없을 때)

모든 look이 같이 지키는 **뼈대**(D-DES-1): A4 출력(D-DES-2), 프로젝트 블록 순서, 1쪽 구성, 세부 설명의 이야기 모양 키, 글자 역할과 크기 범위(D-DES-3, 값의 원본은 `theme/tokens.css` — 이 문서에 크기 표를 다시 쓰지 않는다), 8pt 하한, 마지막 쪽을 뺀 쪽의 여백 50% 상한(D-DES-4, 1쪽 포함), 흰 종이(고른 look의 머리 띠만 면 색), 본문·보조·강조색과 띠 위 글자의 대비 4.5:1, before → after 공용 부품과 측정 조건 표시.

본문 원칙 (look의 머리 띠·제목 장식을 뺀 부분은 모두 같다):
- **위계는 크기·굵기·여백으로.** 색으로 위계를 만들지 않는다. 모든 글을 크게·굵게 해서 중요도를 표현하지 않는다. 한 문단에서 여러 곳을 동시에 강조하지 않는다.
- **강조색은 좁게**: 측정된 개선 결과, 핵심 키워드, 링크. 같은 의미의 요소는 문서 전체에서 같은 색 규칙. 넓은 면의 배경은 고른 look의 머리 띠만. 색만으로 의미를 전달하지 않는다.
- **수치 강조**(D-DES-1): 측정된 before → after(측정 조건이 있는 것)는 개수 제한 없이 강조한다 — 그 쪽의 핵심 수치는 부제목 크기, 보조 수치는 본문 크기 굵게. 측정 결과가 아닌 수치(개수, 기간, 사용자 수)는 본문 크기 굵게까지만.
- **`style`에 정한 색·글꼴만 쓴다.** 페이지 CSS에서 다른 색·글꼴을 새로 쓰지 않는다(build).
- **장식 금지**: 의미 없는 도형·선·아이콘, 모든 내용을 카드에 넣기(상자는 채택한 결정처럼 의미가 있을 때만, 모서리 4px 이하, 그림자 없음), 장식 그라디언트, 빈 공간을 채우려는 요소. 시각 요소는 정보 전달·구분·시선 유도 중 하나의 목적이 있어야 한다.
- **기술 스택은 분류별 쉼표 목록.** 칩으로 나열하지 않는다.
- **정렬과 여백**: 왼쪽 정렬(양쪽 정렬 금지), 쪽마다 같은 좌우 기준선, 관련 요소는 가깝게·무관한 요소는 멀게, 글과 이미지가 겹치지 않게. 여백은 그룹을 나누는 도구지만 50%를 넘으면 실패다.
- **읽기**: 글자를 줄여서 쪽을 맞추지 않는다(내용을 옮기거나 쪽을 늘린다). 텍스트가 많다는 이유만으로 다단을 쓰지 않는다. 코드·표·이미지 속 글자는 인쇄 크기에서 읽혀야 한다(측정 화면은 예외).
- **일관성**: 글꼴·색·제목 위계·좌우 여백·구분선 방식·메타 정보 표현·쪽 번호(오른쪽 아래)는 문서 전체에서 같다. 열 수, 글과 이미지의 배치, 수치·도식의 크기, 밀도는 쪽의 목적에 따라 달라도 된다. 일관성은 모든 쪽이 같아 보이는 것이 아니다.

# 페이지 구성 (레퍼런스가 없을 때)

## 첫 페이지 (`profile`, D-P1-1, D-P1-4)

순서: 이름 → 한 줄 소개 → 자기소개 → 연락처 → 기술 스택 → 활동(교내·대회·기업 프로젝트·동아리 등) → 수상·자격증.
- 프로젝트 목록과 이미지를 두지 않는다. 프로젝트는 2쪽부터.
- 이름이 가장 먼저 보이고, 연락처는 쉽게 찾게, 모든 요소를 같은 크기로 두지 않는다.
- 활동·수상·자격증은 실제 기록만, 항목마다 날짜(기간)를 오른쪽에 맞춘다. 기록이 "활동 없음"이면 활동 줄을 두지 않는다.
- 내용이 적어도 여백 50%를 넘지 않게 한다: 블록 간격, 기술 분류별 나열, 수상·자격증의 기관·내용 한 줄. 그래도 모자라면 build가 사용자에게 1쪽에 넣을 내용을 묻는다. 채우려고 기록에 없는 정보를 만들지 않는다.

## 프로젝트 페이지 (D-PRJ-1~6, `export.py`가 순서를 검사)

| 순서 | 블록 | 내용 | 없을 때 |
|---|---|---|---|
| 1 | 로고·이름·기간 | 로고 → 이름, **같은 줄 오른쪽에 기간**("2026.03 ~ 운영 중") | 필수 |
| 2 | 한 줄 소개 | 무슨 서비스인지 한 문장 | 필수 |
| 3 | 팀원 | 팀 구성 + 본인 역할 | 필수 (개인이면 "개인 프로젝트") |
| 4 | 사용 기술 | 분류별 쉼표 목록 | 필수 |
| 5 | 기능 소개 | 주요 기능 3~5개, 서비스 화면을 옆이나 위에 | 기록에 없으면 생략 |
| 6 | 주요 성과 | 측정된 before → after(크게) + 측정 없는 성과(실사용 시작, 사용자 수 등, 본문 크기) | 기록에 없으면 생략 |
| 7 | 세부 설명 | 실제로 한 일. **작업마다** 이야기 모양 키 | 필수 |
| 8 | 전체 회고 | 작업별 회고를 모두 여기로, 작업 이름을 라벨로, 원문 그대로 | 회고가 없으면 생략 |

1~6은 프로젝트 첫 쪽(`project-overview`), 8은 마지막(`retrospective`). 순서는 고정이고 각 블록의 표현 형식(목록·표 등)은 내용에 맞게 정한다. 회고 포함 여부는 `sections`가 아니라 기록에 회고가 있는지로 정한다.

## 작업의 이야기 모양 (D-DES-13)

세부 설명의 **작업 하나하나**에 키를 정한다(쪽 단위가 아님). 키는 `design.base.json`의 `layouts`가 원본이고, 키마다 `components.css`의 부품으로 그린다. `layout_check.py`가 섹션 안에 그 부품이 있는지 검사한다 — 키만 바꾸고 모양이 그대로면 실패한다.

| 이야기 모양 | 기록의 신호 | 키 | 시각 구조 (부품) | 가장 먼저 보이는 것 |
|---|---|---|---|---|
| 수치가 단계적으로 바뀐 개선 | 측정된 before → after, 중간 단계("1차 600ms") | `metric-compare` | 맨 위 대표 수치 크게(`.ba.ba-lead`), 아래 단계 카드 가로(`.stage-cards`) | 개선 결과 수치 |
| 시간 순으로 벌어진 일 | 기간·날짜·"N일 동안", 발견 → 원인 → 수정, 장애·버그 | `timeline` | 왼쪽 세로 시간축 + 점, 시점 → 한 일 → 설명(`.timeline`), 해결 점만 채움 | 진행 과정 |
| 사람·업무 흐름을 바꾼 기능 | 기존 절차와 바뀐 절차, 역할별 행동 | `flow-compare` | 좌우 두 열, 같은 높이의 단계 상자 + 화살표(`.flow-compare`) | 무엇이 달라졌는지 |
| 처리 단계가 핵심인 기능 | 파이프라인, 요청 처리 순서 | `process-flow` | 번호 단계 상자를 가로로 잇기(`.process-flow`), 아래 설계 포인트 | 동작 순서 |
| 구조를 바꾼 작업 | 구성 요소를 없애거나 합침, 구조도 전·후 | `architecture` | 구조도를 본문 폭으로 먼저(전·후면 같은 크기 틀로 나란히), 설명은 아래 1~2열 | 구성 요소 관계 |
| 대안 중에 고른 선택 | 이유·대안·트레이드오프 | `decision` | 채택 카드(`.decision-card`): 선택 → 이유, 아래 흐린 글자로 대안. 여럿이면 한 섹션에 카드 여러 장 | 무엇을 왜 골랐는지 |
| 원인을 파고든 분석 | 가설·확인·원인이 중심이고 위 신호가 약함 | `problem-solving` | 라벨 단계 목록(`.steps`). 라벨은 일반적인 "상황·원인·해결·결과"가 **아니라** 기록의 실제 분석 단계("가설", "EXPLAIN 확인", "발견")로 — `layout_check.py`는 라벨 문구를 보지 않아 이 규칙은 문서뿐이다. 한 프로젝트에 한 번이 기본 | 원인을 찾은 방법 |
| 핵심 코드가 이야기인 구현 | 기록에 코드·알고리즘·쿼리 전·후가 있음 | `code` | 핵심 부분 코드 발췌(`<pre>`) + 바로 옆·아래 설명 | 무엇을 어떻게 구현했는지 |
| 결과물 화면이 이야기인 작업 | 서비스 화면·동작 화면·모니터링·테스트 결과 이미지가 기록에 있음 | `image-feature` | 큰 이미지(`<img>`) 먼저, 설명은 가까이 | 실제로 만든 결과물 |
| 위 어디에도 안 맞는 설명 | — | `text` | 단일 열 본문, 소제목 | — |

- **콘텐츠에 가장 맞는 키가 먼저**, 다양성은 그다음. 신호가 비슷하게 맞는 키가 둘이면 이미 쓴 키와 다른 쪽을 고른다.
- 같은 키가 맞으면 다시 써도 된다. 그 섹션에 `repeatReason` 한 줄(build가 `data-layout-repeat`로 옮김). 피하려고 맞지 않는 키를 고르지 않는다.
- **범용 형식 `problem-solving`과 `text`는 각각 세부 설명의 절반을 넘지 않는다**(세부 설명 3개 이상인 프로젝트, `layout_check.py`가 실패시킴). 2개 이하인 프로젝트도 둘 다 라벨 행으로 두지 않는다(검사는 없다). 다른 키의 섹션 안에 라벨 행을 넣어도 실패.
- 신호가 여럿이면 독자가 가장 먼저 봐야 할 것으로 고른다(성능 개선은 수치 먼저, 46일 반복 장애는 시간 흐름 먼저).
- **모양을 위해 기록에 없는 것을 만들지 않는다.** 타임라인의 시점, 흐름의 단계, 단계 카드의 수치는 기록에 있는 것만. 신호가 기록에 없으면 그 모양을 고르지 않는다.

**키별 주의** (나머지 키 포함)
| 키 | 주의 |
|---|---|
| `project-overview` | 이름·목적이 먼저, 기술·역할은 훑기 쉽게, 개요가 쪽을 다 차지하지 않게 |
| `metric-compare` | 비교 대상·기준·단위가 분명하게, 전·후가 헷갈리지 않게, 측정 조건을 같이. 실제 데이터 없는 그래프 금지, 과장하는 시각화 금지 |
| `architecture` | 기록에 있는 구성 요소·흐름만(AI가 덧붙인 다이어그램은 절반이 틀렸다). 화살표는 실제 흐름과 같게, 설명은 요소 가까이 |
| `decision` | 선택과 대안이 헷갈리지 않게. 근거 없는 장단점·비교를 만들지 않는다 |
| `code` | 핵심 부분만, 인쇄 크기에서 읽히게, 작게 줄여 한 쪽에 넣지 않는다. 기록에 코드가 없으면 쓰지 않는다 |
| `retrospective` | 원문 그대로, 항목끼리 구분. 인용구·장식 문구를 더하지 않는다 |
| `image-feature` | 이미지가 무엇을 보여주는지 분명하게, 설명은 가까이, 원본 비율 유지, 잘라내지 않는다(D-IMG-3) |

# 이미지 자리 (`imageSlots`)

필드는 `design.base.json`의 `schemas."imageSlots[]"`(`id`, `file`, `kind`, `project`, `placement`, `size`, `pair`)를 따른다.

- **프로젝트 필수 이미지**: 로고(`logo`, 첫머리 이름 왼쪽, 높이 약 28~36px, 비율 유지)와 서비스 화면(`screen`, 프로젝트 첫 쪽, 가로형은 본문 폭 60~100%, 세로형은 `side`일 때 오른쪽 열 45~60mm, 정사각형 70~85mm). 기록에 파일이 있으면 그 파일로, "로고 없음"·"서비스 화면 없음"이 있으면 그 자리만 만들지 않는다. 기록에 파일도 "없음"도 없으면 자리를 지어내지 않는다 — build가 사용자에게 요청한다.
- **기록에 있는 이미지만 쓴다.** 기록의 `## 이미지`에 사용자가 확인한 파일만 자리를 만든다. `portfolio/images/`에 파일이 있다는 것만으로 용도를 정하지 않는다(R-EVD-7). 레퍼런스가 없으면 기록된 이미지(종류 `사용 안 함` 제외)는 모두 자리에 넣는다(build가 빠진 것을 잡는다). 쓰지 않을 이미지는 사용자에게 확인받아 기록을 `사용 안 함`으로 바꾼다. 로고·서비스 화면 외 이미지를 새로 요구하지는 않는다.
- **파일이 없는 빈 자리는 만들지 않는다**(D-IMG-1). 넣으면 좋을 이미지는 `imageSlots`가 아니라 끝 보고에 적는다.
- **측정 화면**(`kind: measure`: Gatling·대시보드·EXPLAIN 결과)은 증빙이다. 개선 전·후 두 장은 같은 `pair`로 묶어 **같은 쪽에 나란히**, 각각 본문 폭의 절반 이하, 묶음 높이는 쪽의 30% 이하. 수치는 이미지가 아니라 위의 before → after 줄이 전달한다. 글자가 읽히게 키우거나 두 쪽으로 나누지 않는다(D-IMG-2).
- **전·후 이미지 짝**(D-IMG-4): 구조도·화면 캡처 등 종류와 상관없이 개선·전환 전·후 두 장은 같은 `pair`로 묶어 같은 쪽, 같은 크기 틀. 비율이 다르면 build가 `--pair-ratio`로 틀만 맞추고 자르지 않는다(design은 `pair`만 정한다).
- 장식·분위기·빈 공간을 채우려고 이미지를 쓰지 않는다. 내용이 불분명한 이미지에 의미를 붙이지 않는다.

# 페이지 계획 (`pagePlan`)

필드와 키는 `design.base.json`의 `schemas`와 `layouts`를 따른다. 키를 더하거나 빼면 그 파일, 이 문서의 이야기 모양 표, build "레이아웃 구현", `components.css` 부품, `layout_check.py`의 부품 표를 함께 고친다.

- 쪽마다 목적이 하나 있게 한다(가장 먼저 보여야 할 것이 무엇인지). 계획은 내용을 고치는 것이 아니라 순서와 레이아웃을 정하는 것이다.
- **세부 설명은 섹션마다 `sections[].layout`을 적는다.** 쪽 `layout`을 물려받게 두지 않는다.
- **쪽 수는 재료에 맞춘다.** build 스킬의 `scripts/facts_stats.py`가 센 완결된 작업 수를 기준으로 잡고, 판정이 `부족`이면 쪽을 적게 잡는다. 한 쪽에 내용이 너무 적게 배정되지 않게 한다(여백 50%). 모자라면 build가 블록을 당기거나 쪽을 합친다.
- 쪽을 나누는 경우: 문제와 해결이 한 쪽에서 구분되지 않음, 구조도와 설명을 같이 두기 어려움, 핵심 수치가 묻힘, 이미지·코드가 읽을 수 없을 만큼 작아짐, 다른 주제 둘이 한 쪽에서 경쟁함. 쪽 수를 늘리려고 짧은 내용을 쪼개지 않는다.
- 프로젝트끼리는 구분되게, 같은 프로젝트의 쪽은 이어 읽히게. 쪽을 구분하려고 배경색·장식을 바꾸지 않는다(고른 look의 머리 띠는 프로젝트 첫머리마다 같은 모양이라 예외).

# 절차

1. **기존 설정 확인**: `theme/design.base.json`, `theme/variants.json`, 기존 `portfolio/design.json`(특히 `style` — 있으면 레퍼런스를 다시 묻지 않는다), 기존 `portfolio/theme/`. 없는 파일을 있다고 가정하지 않는다.
2. **내용 파악**: 기록(facts), 구성안(outline), 이미지 기록, 기존 쪽 계획. 사실관계를 새로 판단하거나 본문을 고치지 않는다.
3. **테마**: 위 0 → 1-A 또는 1-B → 2.
4. **레이아웃·이미지·쪽 계획**: 레퍼런스가 있으면 1-A의 4. 없으면 위 "페이지 구성", "이미지 자리", "페이지 계획".
5. **`design.json` 작성**: `design.base.json`을 바탕으로 기존 필드와 구조를 유지하고 `style`·`imageSlots`·`pagePlan`·`updated`를 채운다.
6. **검증** (확인할 수 없는 것은 확인했다고 말하지 않는다)
   - JSON 문법, 기존 스키마 유지, `layout`이 모두 `layouts`의 키
   - 세부 설명 섹션마다 `layout`, 반복이면 `repeatReason`, 범용 형식이 절반 이하
   - 프로젝트마다 로고·서비스 화면 자리가 있거나 기록에 "없음", 파일 없는 빈 자리 없음, 자리마다 어느 블록의 무엇을 보여주는지(`placement`)가 실제 내용과 맞음
   - `make_theme.py --check portfolio/design.json portfolio/theme`가 "테마 최신: 일치"
   - 레퍼런스가 있으면 `referenceLayout`에 쪽별 배치가 적혀 있다
   - 본문·사실관계를 고치지 않았다

## 다시 할 때 (D-DES-13)

기존 설정을 지우고 처음부터 쓰지 않는다. 맞는 것은 두고 지금 내용과 안 맞는 것만 다시 정한다. 요청이 어느 층인지 먼저 가른다.

| 층 | 무엇 | 바꾸는 곳 |
|---|---|---|
| 테마 | 색, 글꼴, 제목 모양, 전체 스타일 | `style` → `make_theme.py` |
| 레이아웃 | 작업별 형식(이야기 모양 키), 쪽 나누기, 열 구성, 수치·이미지의 크기와 위치 | `pagePlan` → build |

- **"디자인 다시 해줘", "다르게 해줘", "비슷해 보여"** → 두 층을 다 본다. 겉모습이 같아 보이는 이유는 대개 레이아웃이다. 작업마다 키를 다시 고르고, 비슷하게 맞는 키가 둘이면 지난번과 다른 쪽을.
- **색·글꼴·제목 모양만** → 테마만(`accent`·`colors`·`font`·`heading` 중 요청한 것만 바꾸고 `make_theme.py`). 레퍼런스 테마면 `source`는 그대로.
- **특정 쪽·작업만** → 그 섹션의 키만. 한 쪽 요청을 전체 변경으로 추측하지 않는다.
