# 포트폴리오 만들기 (start)

> **먼저 읽는다** — 이 스킬을 불러오면 표시되는 기본 디렉터리(`Base directory for this skill`) 기준으로 `../../rules/principles.md`(제품 원칙)와 `../../rules/user-decisions.md`(사용자 결정 원본)를 읽는다. 이 문서의 규칙이 그 둘과 다르면 그 둘이 맞다. 같은 세션에서 이미 읽었으면 다시 읽지 않는다. **둘 중 하나라도 읽지 못하면(파일 없음·읽기 실패) 이 스킬의 작업을 시작하지 않는다** — 어떤 파일을 어느 경로로 찾았는지와 "원칙 문서를 읽지 못해 멈췄다"를 첫 줄에 알리고 끝낸다. 원칙 없이 기억이나 이 문서만으로 대신 진행하지 않는다.
>
> **한국어로 말한다** — 사용자에게 하는 모든 말(질문·선택지·중간 안내·끝 보고)은 한국어로 쓴다(원칙 → Target Users). 스크립트 출력·에이전트 보고·영어 자료를 옮길 때도 한국어로 풀어 쓴다. 기술 이름·코드·파일 경로·고유명사만 원래 표기. 사용자가 다른 언어를 요청했을 때만 바꾼다. 격리 실행(개인 설정 없음)에서 끝 보고가 영어로 나온 적이 있다(10-10).

사용자는 단계를 몰라도 된다. 이 스킬이 순서를 끌고 간다. 각 단계의 세부 규칙은 해당 스킬의 SKILL.md를 따른다.

## 진행 순서

| 순서 | 단계 | 건너뛰는 조건 |
|---|---|---|
| 0 | 환경 점검(항상) → 기존 상태 확인 | 기존 상태 확인만: `portfolio/`가 없거나 비어 있음 |
| 1 | `interview` | `portfolio/interview-state.md`의 stage가 `done` |
| 2 | `ingest` | 사용자가 자료를 주지 않음. 인터뷰 중 자료를 받으면 그 자리에서 처리한다. 프로필 단계에서 "기존 자료"를 적었으면 프로젝트 목록 전에 "자료 묶음"으로 먼저 훑는다. `portfolio/images/`에 이미지가 있으면 "이미지" 절차를 한다 |
| 3 | `design` (디자인 레퍼런스가 있는지 한 번만 묻는다 — 있으면 배치·색·글꼴까지 레퍼런스 그대로 만들고(D-DES-16), 없으면 첫 PDF는 미니멀 스타일에 로고 색·자동 추천 글꼴로 만들고 build의 디자인 고르기에서 사용자가 고른다. 쪽마다 콘텐츠에 맞는 레이아웃과 이미지 자리를 정함) | `design.json`이 있고 build의 "디자인 최신 여부" 검사를 통과함 |
| 4 | `build` (첫 PDF → **디자인 고르기**(실제 쪽 시안으로 전체 스타일·색·글꼴·화면 배치 선택) → 디자인 리뷰 루프) | 디자인 고르기는 `style.source`가 `user`·`reference`면 건너뜀. 레퍼런스면 디자인 리뷰 루프도 건너뛰고 내용 검사만 함(D-DES-16) |
| 5 | `audit` (기본 모드) | — |

audit에서 문장을 고쳤으면 build의 검증과 디자인 리뷰 루프를 한 번 더 돈다(레퍼런스 모드면 검증만).

**PDF 전송은 최종본만**(D-FLOW-8): build·audit는 start 안에서 각자 보내지 않는다. 끝 보고 직전에 build의 "PDF 전송"(`upload.py`)을 **한 번** 돌린다. 이미 갔으면 "이미 보냄"으로 끝나고, 설정이 없으면 건너뛴다. 출력 한 줄을 끝 보고 맨 끝에 옮긴다.

## 0. 환경 점검과 기존 상태 확인

**가장 먼저 환경을 점검한다.** `python3 <플러그인 루트>/skills/build/scripts/env_check.py` (이 스킬 기본 디렉터리 기준 `../build/scripts/env_check.py`). PDF는 마지막에 만들지만, 인터뷰를 다 하고 나서 Chrome이 없다는 걸 알게 되면 안 된다.
- 통과면 따로 말하지 않는다.
- 실패면 첫 메시지 맨 앞에 무엇이 없고 어떻게 설치하는지(출력의 설치 명령)를 그대로 알리고, "인터뷰는 그동안 진행할 수 있어. PDF를 만들기 전까지만 설치해 줘"라고 한 줄 덧붙인다. 묻지 않고 인터뷰를 계속한다. build가 시작할 때 다시 점검한다.


`portfolio/`에 이전 기록(인터뷰 상태, 기록 파일, 결과 PDF)이 있으면 **한 번만** 묻는다. 묻지 않고 이어가지 않는다. 사용자가 이전 세션에서 "처음부터"라고 했어도 그 말은 새 세션에 남지 않는다.

`AskUserQuestion` 한 문항:
- **이어서** — 지금 상태(어느 단계까지 했는지 한 줄)에서 계속
- **백업하고 새로** — `portfolio/`를 `portfolio.bak-<YYYYMMDD-HHMM>/`로 옮기고 빈 상태에서 시작. 옮긴 경로를 알려준다

질문 전에 지금 상태를 한두 줄로 보여준다(예: "프로필까지 받았고, 프로젝트 기록이 있고, 4쪽 PDF가 10/08에 만들어져 있어").

## 사용자에게 쓰는 말

하네스 안에서 쓰는 이름을 사용자에게 그대로 말하지 않는다. 채팅과 질문 선택지에서는 오른쪽 말을 쓴다.

| 내부 이름 | 사용자에게 |
|---|---|
| facts, 사실 파일 | 기록한 내용 (`portfolio/facts/`는 "기록 폴더") |
| sources | 받은 자료 원본 |
| outline | 구성안 |
| 슬롯, imageSlots | 이미지 자리 |
| 근거없음 / 모름 / 충돌 | 근거가 없는 값 / 기억 안 나는 값 / 자료끼리 다른 값 |
| data-fact, data-sparse-ok 등 속성 이름 | 말하지 않는다 |
| ingest, build, audit 같은 단계 이름 | "자료 정리", "PDF 만들기", "문장 검사", "디자인 검사" |
| 재료 점검 판정 부족/보통/충분 | "문제 해결 사례가 n개, 측정한 결과가 n개라서 내용이 얇아/보통이야/충분해" |

파일 경로를 알려줄 때는 경로를 그대로 써도 된다. 처음 한 번만 "여기에 네가 말한 내용을 출처와 함께 기록해 둬"처럼 무엇인지 설명한다.

## AI가 정하는 것과 묻는 것

사용자가 보기에 "이 정도는 알아서 해야지" 싶은 것은 묻지 않고 정한다. **판단 기준: 바꿔도 포트폴리오가 주장하는 내용(누가, 무엇을, 얼마나)이 달라지지 않으면 AI가 정한다.** 정한 것은 끝 보고에 한 줄씩 적어 사용자가 나중에 되돌릴 수 있게 한다.

| AI가 정한다 (묻지 않음) | 사용자에게 묻는다 |
|---|---|
| 쪽 수, 쪽 나누기, 넘칠 때 쪼갤지·옮길지·줄일지, 블록 순서와 배치 | 수치·사실의 값이 자료끼리 다름(어느 값이 맞는지) |
| 글자 크기·간격·이미지 크기(정해진 범위 안에서) | 기록에 없는 내용을 넣어야 하는 경우 |
| 표기 통일: 날짜(`2026.04.27`), 천 단위 쉼표, 문장 끝 마침표, 용어 표기 | 사용자가 직접 쓴 글(자기소개·회고)의 맞춤법 이상 수정 |
| 같은 문장·사실이 반복되면 한 곳만 남기기 | 주장의 강도가 바뀌는 수정(예: "줄였다" → "예상치로 줄였다") |
| 섹션 이름·라벨처럼 기록을 그대로 요약한 짧은 제목 | 개인정보가 보이는 이미지를 쓸지 |
| 지면이 모자랄 때 우선순위가 낮은 내용 빼기(보고에 빠진 목록을 남김) | 프로젝트·섹션을 통째로 빼는 것 |
| 오타 수정(사용자 원문 제외), 구성안 갱신 | 디자인 레퍼런스가 있는지(처음 한 번). 있으면 그대로 따르고 디자인은 더 묻지 않는다. 레퍼런스가 없으면 첫 PDF 뒤 실제 쪽 시안을 보여주고 전체 스타일·강조색·글꼴·서비스 화면 배치를 묻는다(D-DES-15) |
| 제목 모양(look에 맞춰), 첫 PDF의 기본 테마 | |

우선순위가 낮은 내용: 측정 결과가 없는 작업 서술 > 같은 내용을 다른 말로 한 문장 > 부가 설명 캡션 순으로 먼저 뺀다. 측정 결과, 문제 해결 사례의 원인·해결, 채택한 결정은 빼지 않는다.

## 원칙
- **시작할 때 현재 상태를 파일로 판단한다.** 진행 방식을 길게 설명하지 않는다. 한 줄이면 된다.
- **단계 사이에서 "다음으로 넘어갈까?"를 묻지 않는다.** 앞 단계가 끝나면 다음 단계로 바로 넘어간다.
- 사용자가 멈추게 되는 지점은 아래뿐이다.
  0. 기존 상태가 있을 때 이어서/새로
  1. 인터뷰 질문에 답할 때 (이미지 확인 포함). 프로젝트마다 로고·서비스 화면이 없으면 PDF를 만들기 전에 한 번 더 요청하고 기다린다
  2. 구성안 승인 (내용이 얇으면 "자료를 더 넣고 다시"도 이때 같이 묻는다). 구성안을 승인받은 뒤 쪽이 넘치거나 남아서 생기는 쪽 나누기·배치 변경은 다시 묻지 않는다
  3. 디자인 고르기 (레퍼런스가 없을 때만) — 첫 PDF가 검사를 통과한 뒤, 실제 1·2쪽 시안을 보고 전체 스타일·강조색·글꼴·서비스 화면 배치를 고를 때 (D-DES-15)
  4. 문장 검사 지적을 반영할지 고를 때
  (디자인 검사의 지적은 묻지 않고 고친다. 레퍼런스가 있으면 디자인 검사를 하지 않는다. 사실관계가 의심되는 지적은 문장 검사(audit)로 넘어가 4번에서 함께 묻는다)
- **`AskUserQuestion`은 그 화면만 보고 고를 수 있어야 한다.** 선택지가 앞의 표나 파일을 가리키면("1번", "3번 건") 그 내용을 반드시 같은 턴의 채팅 본문에 먼저 출력한다. 선택지 설명에는 무엇이 어떻게 바뀌는지를 적는다. 모든 단계에 적용한다.
- **단계는 자기 결과물만 쓴다.** design은 `design.json`·`theme/`(make_theme.py로 만든 CSS)만, build만 `out/index.html`을 쓴다. 디자인을 바꾼 뒤 HTML에 반영할 때는 build를 다시 돈다. HTML을 손으로 고치지 않는다.
- 사용자가 중간에 그만두면 다음에 이 스킬을 다시 부를 때 0단계부터 한다.
- **예전 결과물이 있는 경우**: 예전 결과물을 "기존 자료"로 받아 ingest한다. 예전에 있던 프로젝트·사례가 새 결과물에서 말없이 빠지면 안 된다.
- 읽지 못한 자료는 그 단계에서 바로 붙여넣기를 요청한다. 최종 보고에서 처음 알리지 않는다.
- **마지막 쪽을 뺀 모든 쪽은 여백 50% 이하**(사용자 결정 2026-10-09, 레퍼런스가 있으면 레퍼런스를 따른다). 맞추는 건 AI가 한다(쪽 나누기·블록 이동). 1쪽이 모자랄 때만 넣을 내용을 묻는다.
- 끝나면 한 번에 보고한다: PDF 경로, 디자인(레퍼런스를 그대로 따랐는지 — 구하지 못해 바꾼 글꼴만 적는다 — 또는 사용자가 시안에서 고른 전체 스타일·강조색·글꼴·화면 배치와 AI가 정한 제목 모양과 이유, 바꾸고 싶으면 말해 달라고 한 줄), 문장 검사 결과, 디자인 검사 결과(회차별 지적 수, 남은 지적. 레퍼런스 모드면 "하지 않음"), 넣으면 좋을 이미지, 근거가 없어 뺀 내용, 내용의 두께(문제 해결 사례·측정 결과 수)와 쪽별 채움. 내용이 얇았으면 결과물을 가장 크게 개선할 자료 종류 한 가지를 짚는다.
