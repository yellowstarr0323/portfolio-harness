# 포트폴리오 생성 (build)

> **먼저 읽는다** — 이 스킬을 불러오면 표시되는 기본 디렉터리(`Base directory for this skill`) 기준으로 `../../rules/principles.md`(제품 원칙)와 `../../rules/user-decisions.md`(사용자 결정 원본)를 읽는다. 이 문서의 규칙이 그 둘과 다르면 그 둘이 맞다. 같은 세션에서 이미 읽었으면 다시 읽지 않는다. **둘 중 하나라도 읽지 못하면(파일 없음·읽기 실패) 이 스킬의 작업을 시작하지 않는다** — 어떤 파일을 어느 경로로 찾았는지와 "원칙 문서를 읽지 못해 멈췄다"를 첫 줄에 알리고 끝낸다. 원칙 없이 기억이나 이 문서만으로 대신 진행하지 않는다.

> 사용자에게 말할 때는 `start` 스킬의 "사용자에게 쓰는 말" 표를 따른다. facts·outline·슬롯 같은 내부 이름을 채팅에 그대로 쓰지 않는다.

facts와 design을 합쳐 HTML을 만들고 PDF로 출력한다. **이 스킬만 포트폴리오 문장을 쓴다.**
그리고 쓰는 모든 문장은 facts의 한 줄로 되돌아갈 수 있어야 한다.

결과물:

| 파일 | 내용 |
|---|---|
| `portfolio/out/outline.md` | 쪽별 구성안과 제외 목록 (사용자 승인용) |
| `portfolio/out/index.html` | 최종 HTML |
| `portfolio/out/tokens.css`·`components.css`·`style.css`, `out/assets/` | HTML이 참조하는 테마와 이미지 사본 (out/만 있으면 열림) |
| `portfolio/out/portfolio.pdf` | 최종 PDF |
| `portfolio/out/.build.json` | 빌드 기록 (index.html 해시, 시각, 검증 결과) |

스크립트는 이 스킬 디렉터리의 `scripts/`에 있다. `<S>`는 그 경로를 뜻한다.

## 0. 사전 확인

**환경 점검**: 가장 먼저 `python3 <S>/env_check.py`를 돌린다. 실패면 HTML을 쓰지 않고 멈춘다 — 없는 것과 설치 명령(출력 그대로)을 알리고, 설치했다고 하면 다시 점검한다. Chrome·poppler·웹폰트 연결이 없으면 PDF를 만들 수 없거나 글꼴이 바뀐 PDF가 나온다.

앞 단계가 비어 있으면 **묻지 않고 그 단계부터 진행한다.** "먼저 ~를 해야 해, 시작할까?"라고 되묻지 않는다.
- `portfolio/facts/`가 비어 있음 → `interview` 절차부터 시작
- `portfolio/design.json` 또는 `portfolio/theme/tokens.css`가 없음 → `design` 절차부터 시작
- **디자인 최신 여부**: 아래 중 하나라도 해당하면 design을 다시 돈다(되묻지 않고 넘어간다. design은 `style`이 없을 때만 레퍼런스를 한 번 묻는다). build가 `theme/`의 CSS나 `design.json`을 직접 고치지 않는다.
  - `design.json`에 `style`이 없거나 `schemaVersion`이 7 미만 → design이 레퍼런스를 묻고(`style`이 없을 때만) 테마와 쪽 계획을 다시 만든다. 6은 세부 설명 작업마다 이야기 모양 키(D-DES-13)가 없던 판이다
  - (레퍼런스 모드면 이 아래 네 항목은 보지 않는다 — 배치와 이미지 자리는 레퍼런스가 정한다, D-DES-16)
  - `pagePlan`에서 세부 설명 작업 섹션에 `layout`이 없음
  - `python3 <design 스킬의 scripts>/make_theme.py --check portfolio/design.json portfolio/theme`가 "테마 최신: 일치"가 아님(테마 파일이 없거나, 손으로 고쳤거나, 원본이 바뀜)
  - `imageSlots`에 `file`이 없는 빈 자리가 있음, 또는 1쪽에 놓인 이미지가 있음
  - `pagePlan`이 비었거나, `layout`에 `design.base.json`의 `layouts`에 없는 키가 있음
  - `facts/*.md`의 `## 이미지`에 기록된 이미지(사용 안 함 제외)가 `imageSlots`의 `file`에 없음
  - `## 이미지`에 종류 `측정 화면`인 이미지가 `imageSlots`에서 `kind: measure`가 아니거나, 개선 전·후 짝인데 `pair`가 없음(옛 규칙으로 정한 설정 — 측정 화면을 본문 폭으로 키우던 때)

다음은 멈추고 알린다.
- **프로젝트 필수 이미지가 빠짐**: 프로젝트마다 `## 이미지`에 `로고`와 `서비스 화면`이 있거나 "없음"이 기록돼 있어야 한다. 둘 다 아니면 빌드하지 않고 요청한다("dms 로고랑 서비스 화면이 아직 없어. 이미지 파일을 이 창으로 끌어다 놓아 줘. 없으면 없다고 해줘" — 받으면 ingest 이미지 절차로 AI가 복사, D-IMG-5). `portfolio/images/`에 새 파일이 이미 있으면 먼저 ingest의 이미지 절차를 한다. **파일이 폴더에 있다는 것만으로 용도(로고·서비스 화면 등)를 정해 기록하지 않는다** — 무엇인지 사용자에게 확인받은 뒤에 기록하고, 확인 전에는 `[src: interview]`를 달지 않는다(R-EVD-7). 물을 수 없는 상황이면 기록하지 말고 멈춘다.
- facts에 `status: 충돌` 항목이 있음 → 목록을 보여주고 해소를 요청한다. 충돌한 값 중 하나를 골라 쓰지 않는다.

**기록 형식 검사**: 가장 먼저 실행한다. HTML을 다 쓰고 `export.py`에서 실패하면 build를 처음부터 다시 돌게 되므로, 기록만으로 알 수 있는 문제는 여기서 잡는다.
```bash
python3 <S>/facts_lint.py portfolio/facts --images portfolio/images --cache portfolio/.facts_lint.json
```
- `ERROR[수정]`: 사용자 의도를 바꾸지 않는 형식 문제(프로필 표시, 날짜 표기, slug, 이미지 종류 재분류). "고치는 법"대로 기록을 고치고 다시 돌린다(묻지 않음).
- `ERROR[확인]`: 사용자가 정해야 하는 것(필수 이미지, 상태, 종료일, 사용 기술 전무, 충돌, 없는 이미지 파일). 추측해서 채우지 않고 "물을 것"을 한 메시지에 모아 묻는다. 고치는 법에 "폴더에 기록에 없는 파일"이 나와도 그 파일을 바로 기록하지 않는다 — 파일 이름을 보여주고 무엇인지 묻는다.
- WARN은 진행하되 끝 보고에 적는다. 옛 형식 `period`는 build가 합쳐 쓴다.
- **ERROR가 남아 있으면 HTML을 쓰지 않는다.** `export.py`도 PDF를 만들기 전에 같은 검사를 다시 돌려(같은 입력이면 캐시 재사용) ERROR면 PDF를 만들지 않는다.

| 검증 | 시점 | 책임 |
|---|---|---|
| `facts_lint.py` (사전) | 인터뷰 직후, build 시작, export 직전 | **입력**: 기록 형식, 필수 칸, 기간 논리, 이미지 기록 |
| `check_numbers.py` | HTML 작성 후 (`export.py`도 PDF 전에 돌려 실패면 PDF를 안 만듦) | 본문 수치가 기록에 **같은 단위로** 있는지(포트 80으로 80%를 통과시키지 않음), 한글 수량어(절반·두 배), 출처 메모 |
| `link_check.py` | `export.py`가 PDF 뒤에 돌림 | 보이는 주소는 모두 링크, href 절대 주소, PDF에서 누를 수 있음, 실제로 열림(D-DES-14) |
| `layout_check.py` | HTML 작성 후 (`export.py`도 먼저 돌림) | 세부 설명 작업마다 이야기 모양 키와 그 부품이 있는지, 같은 형식 반복(D-DES-13) |
| `export.py` (최종) | HTML 작성 후 | **산출물**: 넘침, 여백, 글자, 첫머리·블록 순서, 측정 화면 배치, 텍스트 일치 (레퍼런스 모드: 넘침·쪽수·이미지 로드·텍스트 일치·링크만) |
| audit | PDF 후 | 문장이 근거보다 더 말하는지 |

**레퍼런스 모드** (`design.json`의 `style.source`가 `reference`, D-DES-16): 레퍼런스를 그대로 따르고 **내용만 검사한다.** `layout_check.py`는 돌리지 않고, `export.py`는 design.json을 보고 스스로 디자인 검사를 건너뛴다(기록 사전 검증, 이미지 로드 실패, 넘침·쪽수·텍스트 대조 — 내용이 잘리거나 빠졌는지, 링크만 남는다). 디자인 고르기(5-1)와 디자인 리뷰 루프(5-2)도 하지 않는다. 틀린 내용은 `check_numbers.py`와 audit가 잡는다.

**재료 점검**: outline을 만들기 전에 실행한다.
```bash
python3 <S>/facts_stats.py portfolio/facts
```
- 판정이 `부족`인 심층 프로젝트가 있으면 outline을 보여주는 메시지 **맨 앞에** 이 표와 "무엇이 없어서 약한지"를 먼저 쓴다. 그리고 outline 승인 질문에 선택지를 하나 더 둔다: "자료를 더 넣고 다시" (→ `ingest`, 장애 보고서·PR·위키·기존 포트폴리오 등 넣을 만한 자료 종류를 구체적으로 제안). 별도로 멈추지 않고 outline 승인 한 번에 같이 묻는다.
- 부족한 채로 진행하더라도 빌드 보고에 이 판정을 다시 적는다. 결과물이 약한 이유를 사용자가 빌드 뒤에 알게 되면 안 된다.

**덮어쓰기 확인**: `out/.build.json`이 있으면 거기 기록된 해시와 현재 `out/index.html`의 sha256을 비교한다. 다르면 사용자가 빌드 후에 HTML을 직접 고친 것이다. 이 경우 덮어쓰기 전에 묻는다. 고친 내용을 facts나 design으로 옮길지, 그냥 덮어쓸지, 빌드를 멈출지 사용자가 정한다.

## 1. 내용 선별 → outline.md

facts를 읽고 쪽별 구성안을 만든다. `design.json`의 `format`, `pagePlan`, `sections`를 따른다. 단 전체 회고를 넣을지는 `sections`가 아니라 기록에 회고가 있는지로 정한다(D-PRJ-6). `pagePlan`의 쪽마다 `layout`(레이아웃 키)과 `purpose`를 구성안에 그대로 옮기고, 아래 3절 "레이아웃 구현"대로 만든다.

**쪽 여백 상한** (사용자 결정 2026-10-09): 마지막 쪽을 뺀 모든 쪽은 여백이 50%를 넘으면 안 된다(채움 50% 이상). `export.py`가 실패시킨다. 구성안을 짤 때부터 한 쪽에 내용이 너무 적게 가지 않게 나누고, 빌드 후 모자라면 다음 쪽 블록을 당기거나 쪽을 합친다(묻지 않음). 마지막 쪽만 짧게 끝나도 된다.
**1쪽 양식** (`profile` 레이아웃, design "첫 페이지"): 이름 → 한 줄 소개 → 자기소개 → 연락처 → 기술 → 활동 → 수상·자격증(D-P1-1, D-P1-4: 활동·수상은 항목마다 날짜·기간을 같은 줄 오른쪽에. 기록이 "활동 없음"이면 활동 줄을 빼고 묻지 않는다). 프로젝트는 2쪽부터 시작한다. 1쪽에 프로젝트 목록·이미지를 두지 않는다. 왼쪽 라벨 열(`--label-col`)은 1쪽에만 쓴다.
- **1쪽 역할 표시**: 이름은 `<h1 data-role="name">`(`--fs-name`), 한 줄 소개는 `data-role="tagline"`(`--fs-subtitle`, 강조색 가능), 왼쪽 라벨은 `--fs-meta`, 나머지 문장은 `--fs-body`. `export.py`의 강조 검사가 이 표시로 이름·한 줄 소개를 구분한다.
- **1쪽도 여백 50% 상한을 지킨다**(아래 "쪽 여백 상한"). 모자라면 이 순서로 채운다: ① 블록 사이 간격을 `--space-*` 안에서 늘림 ② 기술을 분류별로 나눠 씀(예: 언어·프레임워크 / DB / 인프라) ③ 수상·자격증에 기관·내용 한 줄 ④ 그래도 모자라면 구성안에서 사용자에게 1쪽에 더 넣을 것(활동, 교육)을 묻는다. **글자를 역할보다 키워서 채우지 않는다**(자기소개는 문장이니 `--fs-body`). 2026-10-08 E2E에서 "글자를 키운다"는 이전 규칙 때문에 자기소개가 15pt가 됐다.
- **기술 목록**: `profile.md#주력 기술`에 더해, 프로젝트 기록에 사용했다고 적힌 기술(기술 선택·작업에 이름이 나온 것)을 후보로 모은다. 1쪽 기술 목록과 본문에서 쓴 기술이 어긋나면(본문엔 Kotlin·PostgreSQL이 나오는데 1쪽엔 없음) 독자가 이상하게 읽는다. 후보를 구성안에 "추가 후보"로 보여주고 승인받은 것만 넣는다.
- 자기소개가 profile에 없으면 facts에 있는 사실만으로 3~5문장 초안을 만들어 outline에 넣는다. 문장마다 근거 위치를 적고, 승인받은 초안만 쓴다. 블록에는 `data-role="headline"`과 근거 `data-fact`를 단다. 사용자가 쓴 자기소개도 같은 표시를 단다 — `export.py`가 이 블록 안 문장의 "a → b"는 강조 모양 경고에서 뺀다(원문은 맞춤법만 고치므로).

**넣지 않는 것**
| facts 상태 | 처리 |
|---|---|
| `근거없음` 수치 | 수치는 빼고, 작업 자체는 수치 없이 서술할 수 있으면 남긴다 |
| `모름` | 뺀다 |
| `역할 미확인` | "본인이 했다"로 쓰지 않는다. 팀 성과로 서술하거나 뺀다 |
| `빈칸` 섹션 항목 | 뺀다 |

**메시지 정하기** — 사실 나열이 아니라 "이 사람을 왜 뽑아야 하는지"가 읽히게 한다.
- **한 줄 소개**: `profile.md`에 있으면 그대로 쓴다. 없으면 facts에 있는 사실만 조합한 후보 2~3개를 outline에 넣고 사용자가 고르게 한다(고르지 않으면 표지에 넣지 않는다). 후보마다 어느 facts를 조합했는지 적는다.
- **섹션 제목과 한 줄 결과**: 섹션마다 "무엇을 설명하는지"(섹션 제목, 예: "상벌점 조회 성능 개선")와 "그래서 어떻게 됐는지"(한 줄 결과, 예: "평균 1,225ms → 241ms")를 정한다. 이게 쪽의 뼈대다. 섹션 제목은 기록의 작업 이름을 짧게 다듬은 것이라 AI가 정한다.
- **쪽 헤드라인**: "이 쪽에서 봐야 할 것" 한 문장. 길어도 그 쪽의 핵심을 분명하게 말하면 둔다(사용자 결정 2026-10-09). 다만 섹션 제목과 위계가 헷갈리지 않게, 헤드라인은 `data-role="headline"`으로 표시하고 섹션 제목과 다른 모양(크기·굵기·위치)으로 둔다. facts에서 가장 강한 사실(측정된 결과, 대안을 비교한 결정, 본인이 단독으로 한 일)을 골라 압축한다. 새로운 주장, 형용사("대폭", "혁신적"), facts에 없는 인과를 넣지 않는다. 근거 facts 위치를 함께 적는다.
- 강조 지점을 고르는 건 build의 일이다. "facts에 없는 말을 쓰지 않는다"는 규칙은 무엇을 앞에 둘지 고르는 것까지 막지 않는다.

**쪽 채움 추정** — 쪽마다 대략 얼마나 찰지 적는다(많음/적당/적음). 마지막 쪽 외에 "적음"이 예상되면(여백 50% 초과) 구성안 단계에서 블록을 옮기거나 쪽을 합친다.

`outline.md` 형식:
```markdown
## 재료 점검
(facts_stats.py 표 그대로) — DMS: 부족 (완결된 트러블슈팅 0, 측정 조건 있는 결과 1)
## 한 줄 소개 후보
1. "<문장>" — profile.md#주력 기술 + dms.md#역할
## 3쪽 — DMS ① 개요·역할·기술 선택  (채움: 적당)
- 헤드라인: "<문장>" — dms.md#작업 > 학교 전용 챗봇 결과
- 개요: facts/dms.md#개요 1~2번 줄
- 기술 선택: Redis (선택 이유 있음), MySQL Full-Text (대안 비교 있음)
## 4쪽 — DMS ② 트러블슈팅
- 검색 API 개선 (측정 조건 있음)
## 제외
- facts/dms.md "월 사용자 약 300명" — 근거없음
```

`outline.md`를 사용자에게 보여주고 **승인을 받은 뒤** HTML을 쓴다. 구성을 고치는 비용은 이 단계가 가장 싸다.
- 승인받는 것은 **무엇을 넣고 뺄지와 문장의 주장**이다. 몇 쪽에 어떻게 나눌지는 승인 대상이 아니다. 구성안의 쪽 나누기는 예상일 뿐이고, 빌드하면서 넘치거나 남으면 AI가 다시 나눈다. 다시 묻지 않고 끝 보고에 "3쪽이 넘쳐 스케줄러 블록을 4쪽으로 옮김"처럼 적는다.
- 채팅에는 재료 점검 → 한 줄 소개 후보 → 쪽별(헤드라인, 채움, 주요 블록) → 제외 순으로 보여준다. 승인 질문은 이 내용을 본 뒤 고를 수 있게 같은 턴에 한다.

## 2. 문장 작성 규칙

1. **facts에 없는 내용을 쓰지 않는다.** 연결어("그래서", "이를 통해")로 facts에 없는 인과를 만들지 않는다.
2. **수치는 facts의 표기 그대로 쓴다.** 개선율, 배수, 퍼센트를 새로 계산해서 넣지 않는다. 계산값이 필요하면 사용자에게 묻고, 승인받으면 facts에 `[src: interview]`로 먼저 추가한다. `check_numbers.py`가 facts에 없는 수치를 전부 잡아낸다.
3. **수치 옆에 측정 조건을 붙인다.** 조건이 facts에 있으면 같은 문장이나 바로 아래 캡션에 넣는다. 표를 줄일 때도 조건 줄은 지우지 않는다.
4. **측정 축을 섞지 않는다.** API 응답 시간과 DB 실행 시간처럼 다른 계층의 수치는 한 문장에 넣지 않는다. 넣어야 하면 각각 무엇을 잰 값인지 밝힌다.
5. **따로 일어난 작업을 한 줄 서사로 잇지 않는다.** facts에서 별도 항목이면 포트폴리오에서도 별도 항목이다.
6. **주어를 지우지 않는다.** "개선되었다" 대신 "본인이 ~를 바꿔 ~가 됐다". 누가 했는지는 facts의 역할 기록을 따른다.
7. **제약을 쓸 때는 facts의 구분을 그대로 쓴다.** facts에 "선택"이라고 기록된 것을 "불가"로 쓰지 않고, 그 반대도 하지 않는다.
8. **문체**: 본문은 "~를 해서 ~가 됐다"처럼 사실을 서술하는 문체로 쓴다. 감상 표현("뼈저리게 느꼈다")은 쓰지 않는다.
9. **헤드라인·한 줄 소개**: outline에서 승인된 문장을 그대로 쓴다. 블록에 `data-role="headline"`과 근거 `data-fact`(여러 개면 쉼표로)를 단다. 감사가 이 블록을 범위 과장(SCOPE)·인과(CAUSAL) 기준으로 따로 본다.
10. **출처 메모를 본문에 쓰지 않는다.** facts의 `(원문: …)`, `(당시 블로그 기준)`, "DB에서 얻은 값", `[src: …]`는 근거를 추적하려고 붙인 메모다. 독자에게는 의미가 없고 "자기 글을 못 믿는 사람"처럼 읽힌다. 측정 조건(도구, 요청 수, 데이터 건수, 시점)은 쓰고, 출처(블로그, 인터뷰, 원문, 위키)는 쓰지 않는다. 시점이 다른 수치라면 출처 대신 시점을 쓴다("2026년 4월 블로그 기준" ✗ → "전환 당시(2026.04)" ○, 시점이 facts에 있을 때만). `check_numbers.py`가 `INTERNAL`로 잡는다.
11. **쪽 사이 일관성**: 같은 대상(사용자 수, 팀 인원, 기간, 같은 지표)이 쪽마다 다르게 나오면 안 된다. facts에 값이 둘이면 하나만 쓰거나, 둘 다 써야 하면 각각 언제의 값인지 밝힌다. 예: 2쪽 "학생 180명·교사 30명"과 4쪽 "사용자 약 200명"이 나란히 있으면 독자는 어느 쪽이 맞는지 모른다.
12. **제목과 헤드라인이 같은 말로 시작하지 않는다.** 헤드라인은 결과나 결정부터 말한다.
13. **회고 섹션**: facts의 `회고 (원문 유지)` 인용을 그대로 쓴다. 맞춤법, 띄어쓰기, 조사만 고칠 수 있다. 고친 곳은 빌드 보고에 원문과 나란히 보여준다. 내용을 바꾸거나 문장을 추가하지 않는다.

## 3. HTML 구조 규칙

> **레퍼런스 모드(D-DES-16)**: 레퍼런스 원본과 `style.referenceLayout`을 보고 레퍼런스와 같은 배치·쪽 구성·블록 순서·글자 크기·색·장식으로 쓴다. 아래 규칙 중 **디자인 시스템, 글자 역할, `--fs-*`만 쓰기, 공용 부품(`.ba` 포함), 머리 자리 표시, 서비스 화면 배치, 프로젝트 첫머리·블록 순서는 적용하지 않는다** — 페이지 CSS에 크기·색·여백을 직접 써도 된다. 그대로 지키는 것은 출력·내용 규칙뿐이다: A4 `.sheet` 구조(레퍼런스가 연속 페이지면 연속), 화면과 인쇄 같게, 링크, 근거 추적(`data-fact`), 검사 제외 표시, 잘리면 안 되는 블록. 레퍼런스대로 두니 넘치면(내용이 잘림) 레퍼런스의 배치를 유지한 채 쪽을 나눈다.

- **디자인 시스템** (design "기본 디자인 시스템"·"타이포그래피"·"여백과 그리드"): 흰 배경, 쪽마다 같은 좌우 기준선, 위계는 크기·굵기·여백으로(색으로 만들지 않음), 모든 내용을 카드에 넣지 않음(상자는 채택한 결정처럼 의미가 있을 때만, 모서리 4px 이하, 그림자 없음), 장식 도형·그라디언트·이모지 없음, 왼쪽 정렬(양쪽 정렬 금지), 기술 목록은 칩 대신 분류별 쉼표 목록, 큰 수치·한글이 섞인 강조에 모노 폰트 금지(모노는 코드·API 경로만), 제목 바로 아래 헤드라인이 제목과 같은 말로 시작하지 않음.
- **글자 역할** (design "기본 글자 크기"): 이름 `--fs-name`, 프로젝트 이름 `--fs-page-title`, 섹션 제목 `--fs-section`, 소제목·한 줄 설명·한 줄 소개·측정된 핵심 수치 `--fs-subtitle`, **모든 설명 문장** `--fs-body`, 기간·팀·라벨·날짜 `--fs-meta`, 측정 조건·이미지 설명·쪽 번호 `--fs-caption`, 코드 `--fs-code`. **측정된 before → after(측정 조건이 있는 것)는 개수 제한 없이 강조한다**(사용자 결정 2026-10-09). 그 쪽의 핵심 수치면 `.ba.ba-lead`(소제목 크기), 보조 수치면 `.ba`(본문 크기). 측정 결과가 아닌 수치(개수, 기간, 사용자 수)는 본문 크기 굵게까지만. `export.py`가 측정 결과가 아닌 큰 강조를 경고한다.
- **글자 크기는 `tokens.css`의 `--fs-*` 변수만 쓴다.** 직접 pt/px 값을 쓰지 않는다. 본문은 `--fs-body`(10.5pt 이상)이다. 쪽이 넘칠 때 글자 크기를 범위 아래로 줄여서 맞추지 않는다. 내용을 옮기거나 덜어낸다. `export.py`가 8pt 미만 글자를 실패로 잡는다.
- **공용 부품·스타일**: `portfolio/theme/components.css`와 `style.css`(design이 만든 것)도 `out/`로 복사해 `tokens.css` → `components.css` → `style.css` 순서로 `<link>`한다. 제목 글꼴(`--font-display`)·제목 모양·레퍼런스 장식은 `style.css`가 맡으니, 페이지 CSS에서 `[data-role="name"]`·`page-title`·`section-title`의 글꼴과 장식(막대·선)을 따로 정하지 않는다(크기·굵기·간격은 정해도 된다). before → after 수치는 반드시 이 파일의 `.ba` 마크업(`data-role="before-after"`, `.before`·`.arrow`·`.after`, 바로 다음 `<p class="ba-cond" data-role="measure-cond">`)으로 쓴다. 같은 클래스를 다시 정의하지 않는다.
- **단일 파일** `out/index.html`. `design`에서 만든 `theme/tokens.css`를 `out/tokens.css`로 복사해서 `<link>`로 연결한다. 색, 폰트, 간격은 이 CSS 변수만 쓰고 직접 하드코딩하지 않는다.
- **A4**: 쪽마다 `<section class="sheet">`로 만들고 크기를 210mm×297mm, `overflow: hidden`, `break-after: page`로 고정한다. 넘침 검사가 `.sheet` 단위로 동작하기 때문이다. 종이 안쪽 여백은 `padding: var(--sheet-pad-top) var(--sheet-pad-x) var(--sheet-pad-bottom)`으로만 쓴다(전체 스타일의 머리 띠가 이 값으로 종이 끝까지 닿는다, D-DES-15). 쪽 번호의 오른쪽 위치도 `var(--sheet-pad-x)`.
- **머리 자리 표시** (전체 스타일이 띠·선을 붙이는 자리): 1쪽은 이름·한 줄 소개를 `<header data-role="profile-head">`로 감싼다. 프로젝트 첫머리는 `<header class="project-head">`(아래 예시). 이 두 요소에 배경·테두리를 페이지 CSS로 따로 주지 않고, 1쪽 머리 바로 아래(라벨 그리드 위)에도 구분선을 긋지 않는다 — `style.css`의 look이 맡는다(띠 아래에 선이 하나 더 생겼던 테스트, 2026-10-10).
- **서비스 화면 배치**: `design.json`의 `layoutPrefs.screen`을 따른다. `wide`면 서비스 화면을 기능 소개 위 본문 폭으로, `side`면 기능 목록 왼쪽 + 화면 오른쪽 열(세로형 45~60mm, 정사각형 70~85mm). **가로형 화면(폭/높이 1.3 이상)은 `side`여도 본문 폭으로 둔다** — 오른쪽 열에 넣으면 작아져 쪽 아래가 빈다(2026-10-10 테스트: 16:9 목업을 옆에 두니 2쪽 35%가 빔). 없으면 화면 비율로 AI가 정한다.
- **연속 페이지**: `.sheet` 없이 흐름 레이아웃으로 만든다. `@page` 크기는 `export.py`가 실측해서 넣으므로 HTML에 쓰지 않는다.
- **화면 보기는 `components.css`가 맡는다** (D-DES-12). 회색 바탕·종이 간격·그림자·좁은 화면 축소가 이미 들어 있으니 `body`·`.sheet`에 배경·그림자·바깥 여백을 따로 주지 않는다(종이 안쪽 `padding`은 그대로 쓴다). `body`·`html`의 `background`를 정하면 화면 보기의 회색 바탕을 덮으니 정하지 않는다.
- **화면과 인쇄 레이아웃을 같게 둔다.** `@media print`로 크기, 간격, 폰트를 바꾸지 않는다. 실측은 화면 렌더로 하기 때문이다. `@media print`는 요소를 숨기는 용도로만 쓴다.
- **링크** (D-DES-14, `export.py`가 `link_check.py`로 검사해 어기면 실패): 화면에 보이는 주소·이메일(GitHub, 블로그, Notion, 배포 주소, 이메일 등)은 **모두 `<a href>`로 감싼다.** href는 `https://…`·`mailto:…`처럼 절대 주소로 쓴다 — 글자는 `github.com/yellowstarr`로 짧게 보여줘도 href는 `https://github.com/yellowstarr`. href 없이 글자로만 두거나 `github.com/…`을 그대로 href에 넣으면(상대 경로) PDF에서 눌러도 안 가거나 엉뚱한 곳으로 간다. 링크 글자의 사이트와 href의 사이트는 같아야 한다. 접속 확인에서 404·없는 도메인이 나오면 기록의 주소가 틀린 것이니 사용자에게 맞는 주소를 묻는다(추측해서 고치지 않는다). 401·403 경고(로그인 필요 페이지)는 끝 보고에 "직접 열어 확인"으로 적는다.
- **근거 추적**: 사실을 담은 블록에는 `data-fact="dms.md#검색 API 개선"`처럼 facts 위치를 단다. 근거가 여럿이면 쉼표로 나열한다: `data-fact="dms.md#기술 선택, dms.md#작업"`. 헤드라인 블록은 `data-role="headline"`을 함께 단다.
- **검사 제외 표시**
  - `data-nocheck`: 수치 검사에서 제외한다. 쪽 번호, 연도 표기 같은 장식용 숫자에 단다.
  - `data-print-hidden`: 인쇄에서 숨기는 요소에 단다(`@media print`의 `display: none`과 짝을 맞춘다). 텍스트 대조에서 빠지고, `export.py`는 이 요소를 숨긴 상태로 넘침·채움을 재고 PDF를 뽑는다.
  - `<title>`은 검사 스크립트가 알아서 뺀다. 속성을 달 필요가 없다.
  - `data-sparse-ok`: `.sheet`에 다는 표시. 여백이 의도된 쪽이라 여백 경고를 끈다(예: 회고 마지막 쪽이 짧게 끝남). **1쪽에는 쓸 수 없다**(export.py가 무시한다). 달았으면 빌드 보고에 이유를 적는다.
- **잘리면 안 되는 블록**(카드, 표, 코드)에 `break-inside: avoid`를 건다. flex 컨테이너 안에서는 인쇄 시 이 속성이 무시되므로, 이런 블록은 flex 자식으로 두지 않는다.
- **프로젝트 첫머리** (어기면 `export.py`가 실패시킨다): 프로젝트 이름 다음은 **무조건** 무슨 서비스인지 한 줄 설명이다. 그다음 기간·팀·역할, 그다음 한 일.
  ```html
  <header class="project-head" data-project="dms">          <!-- 사용자가 없다고 한 것만 data-image-missing="logo" -->
    <div class="head-row">                                    <!-- 한 줄: 로고·이름 왼쪽, 기간 오른쪽 -->
      <img data-kind="logo" src="assets/dms/logo.svg" alt="DMS 로고">
      <h1 data-role="page-title">DMS</h1>
      <span class="meta" data-role="project-meta">2026.03 ~ 운영 중</span>   <!-- 이름과 같은 줄이어야 한다 -->
    </div>
    <p data-role="project-summary">학생과 선생님이 쓰는 기숙사 관리 서비스</p>
    <p data-role="project-team">팀 5명 — 백엔드 1, 프론트 2, 안드로이드 1, 디자인 1 · 본인: PM 겸 백엔드</p>
    <p data-role="project-tech">Kotlin, Spring Boot, JPA · PostgreSQL · Docker, AWS EC2</p>
  </header>
  <section data-role="project-features">…주요 기능 + 서비스 화면…</section>
  <section data-role="project-highlights">…주요 성과…</section>
  <section data-role="project-detail">…세부 설명 섹션마다 하나…</section>
  <section data-role="project-retro">…전체 회고…</section>
  <figure class="shot"><img data-kind="screen" data-project="dms" src="assets/dms/screen.png" alt="…"><figcaption>…</figcaption></figure>
  <!-- 여기부터 한 일: 섹션 제목 → 한 줄 결과 → 본문 -->
  ```
  - **기간 줄**(`data-role="project-meta"`)은 기록의 `start`·`end`·`status`로 만든다(사용자 결정 2026-10-09). 종료일이 있으면 `2025.03 ~ 2025.06`, 없으면 `2026.03 ~ 운영 중` 또는 `2026.03 ~ 개발 중`. 날짜는 `YYYY.MM`(일은 쓰지 않는다). 상태를 줄의 다른 자리에 한 번 더 쓰지 않는다. 옛 기록에 `period: 2026.03.01 ~ 진행 중`과 `status: 운영 중`만 있으면 `2026.03 ~ 운영 중`으로 합친다. `export.py`가 형식을 검사해 어기면 실패한다.
  - 한 줄 설명은 기록의 `## 개요`(무슨 서비스인지, 누가 쓰는지)에서 가져온다. 성과·수치·본인이 한 일을 섞지 않는다. 기록에 없으면 인터뷰의 프로젝트 목록 "한 줄 설명" 칸을 쓴다.
  - 이름과 한 줄 설명 사이에 다른 글(헤드라인, 기간, 라벨)을 두지 않는다.
  - 프로젝트 쪽 헤드라인을 둔다면 이 첫머리 **뒤**에 둔다.
- **프로젝트 블록 순서** (사용자 결정 2026-10-09, `export.py`가 검사): 로고·이름·기간 → 한 줄 소개 → 팀원 → 사용 기술 → 기능 소개 → 주요 성과 → 세부 설명 → 전체 회고. 위 예시의 `data-role`을 단다. 팀원·사용 기술은 필수, 기능 소개·주요 성과·전체 회고는 기록에 있을 때만.
  - **기간은 이름과 같은 줄 오른쪽**에 둔다. 아래 줄로 내려가면 이름과 한 줄 설명 사이를 가로막아 실패한다.
  - **사용 기술**은 기록의 `## 사용 기술`(없으면 기술 선택·작업에 나온 기술)을 분류별 쉼표 목록으로.
  - **기능 소개**는 기록의 `## 주요 기능`. 서비스 화면을 이 블록 옆이나 위에 둔다.
  - **주요 성과**는 측정된 before → after(`.ba`, 크게 강조 가능)와 측정 없는 성과(실사용 시작일, 사용자 수, API·PR 수 등 — 본문 크기, 굵게까지)를 함께 모은다. 세부 설명에서 자세히 다루는 성과라도 여기 한 줄로 요약해 둔다. 계산한 개선율은 넣지 않는다.
  - **전체 회고**는 작업별 회고를 전부 모아 작업 이름을 라벨로 단다. 작업 섹션 아래에 회고를 두지 않는다.
- **섹션 구조**: 섹션 제목은 항상 섹션 맨 위에 둔다. **쪽 레이아웃은 쪽마다 같은 틀을 반복하지 않고 design이 정한 페이지별 레이아웃을 따른다**(사용자 결정 2026-10-09: 수치가 핵심인 쪽, 구조도가 핵심인 쪽 등 콘텐츠에 맞게). 섹션 제목은 `<h2 data-role="section-title">`(또는 `h3`)로 `--fs-section`을 쓴다. 왼쪽 라벨 열은 1쪽에만 쓴다. **쪽 맨 위에 반복되는 머리글을 두지 않는다**(사용자 결정 2026-10-08: 프로젝트는 첫머리가, 쪽 내용은 섹션 제목이 이미 알려준다). `export.py`가 여러 쪽 위쪽에 같은 글이 반복되면 경고한다.
- **쪽 번호**: 넣는다면 `<div class="page-number" data-role="page-number">2 / 4</div>`를 `.sheet` 오른쪽 아래에 `position: absolute; right: <여백>; bottom: <여백>`으로 둔다. `export.py`가 위치를 검사한다. 프로젝트가 2개 이상이고 한 프로젝트가 여러 쪽에 걸치면 `DMS · 3 / 6`처럼 프로젝트 이름을 앞에 붙인다. 프로젝트가 하나면 숫자만.
- **레이아웃 구현** — `pagePlan`의 `layout` 키마다 이렇게 만든다. `.sheet`에 `data-layout="<키>"`를 단다. 같은 키라도 내용에 맞게 배치를 조정해도 되지만, 키의 핵심 구조는 지킨다.
  | 키 | 구조 |
  |---|---|
  | `profile` | 이름(`data-role="name"`) → 한 줄 소개(`data-role="tagline"`) → 라벨 열(`--label-col`) + 본문 열 그리드로 자기소개·연락처·기술·활동·수상·자격증 |
  | `project-overview` | 프로젝트 첫머리(로고·이름·기간 한 줄 → 한 줄 소개 → 팀원 → 사용 기술) → 기능 소개 + 서비스 화면(`data-kind="screen"`, 가로형은 본문 폭, 세로형은 옆 열) → 주요 성과 |
  | `problem-solving` | 섹션 제목 → 한 줄 결과(본문 굵게) → 라벨 단계 목록 `<dl class="steps" data-role="steps">`(`dt` 라벨은 기록의 실제 분석 단계 — "가설", "EXPLAIN 확인", "발견", "원인", "해결". 일반적인 상황·원인·해결로만 채우지 않는다) → `.ba` + 측정 조건 → 측정 화면 짝(`.measure-pair`) |
  | `metric-compare` | 섹션 제목 → 핵심 수치 `.ba.ba-lead`(중간 단계가 있으면 `.before`를 여러 개) + 측정 조건 → 단계 카드 `<ol class="stage-cards" data-role="stage-cards">`(단계마다 한 일·그때 수치·알게 된 것) → 측정 화면 짝 |
  | `timeline` | 섹션 제목 → 한 줄 결과 → `<ol class="timeline" data-role="timeline">`: 항목마다 시점(`.tl-when`, 기록에 있는 기간·날짜·순서만) → 한 일(`.tl-title`) → 설명. 원인이 둘이면 항목 둘 |
  | `flow-compare` | 섹션 제목 → 한 줄 결과 → `<div class="flow-compare" data-role="flow-compare">`: 기존 흐름(`data-side="before"`)과 바뀐 흐름(`data-side="after"`)을 단계 상자로 나란히 → 아래에 협업·일정 같은 부가 이야기 짧게 |
  | `process-flow` | 섹션 제목 → 한 줄 결과 → `<ol class="process-flow" data-role="process-flow">`: 번호(`.pf-no`, `data-nocheck`) + 단계 이름 + 짧은 설명 → 아래에 핵심 설계 포인트(학교별 격리, 못 찾으면 답하지 않음 등) |
  | `architecture` | 섹션 제목 → 구조도(인라인 SVG 또는 `data-kind="diagram"` 이미지) 본문 폭 전체 → 구성 요소 설명 1~2열 |
  | `decision` | 섹션 제목 → 채택 카드 `<div class="decision-card" data-role="decision-card">`: 선택(`.dc-choice`) → 이유 → 대안(`.dc-alt`, `.dc-tag`) → 트레이드오프. 선택이 여럿이면 카드 여러 장 |
  | `code` | 섹션 제목 → 코드 발췌(`--fs-code`, 15줄 이하) + 옆이나 아래 설명 |
  | `retrospective` | 프로젝트 마지막. "전체 회고" 제목 → 작업 이름 라벨 + 회고 원문 인용 목록 (`data-role="project-retro"`) |
  | `text` | 섹션 제목 → 단일 열 본문(소제목으로 구분) |
  | `image-feature` | 섹션 제목 → 큰 이미지(원본 비율) → 캡션 → 짧은 설명 |
  - **세부 설명 작업마다** `<section data-role="project-detail" data-layout="<키>">`를 단다(D-DES-13). 키는 `pagePlan.sections[].layout`이다. `repeatReason`이 있으면 `data-layout-repeat="<이유>"`로 옮긴다. 쪽 `layout`은 `.sheet`에 그대로 단다.
  - 위 표의 부품은 `components.css`에 있다. **같은 클래스를 페이지 CSS에서 다시 정의하지 않는다**(간격·폭 조정만). 라벨 단계 목록(`.steps`)은 `problem-solving` 섹션에서만 쓴다 — 다른 키의 섹션에 라벨 행을 넣으면 모든 작업이 같은 형식으로 보이게 된다.
  - HTML을 다 쓰면 `python3 <S>/layout_check.py portfolio/out/index.html`을 돌린다. 실패하면 design의 이야기 모양 표로 키를 다시 고르고 `design.json`의 `pagePlan`에도 반영한다(묻지 않음). `export.py`도 PDF 전에 같은 검사를 돌려 실패면 PDF를 만들지 않는다.
  - 쪽마다 같은 틀을 반복하지 않는 건 design이 작업마다 키를 고르는 단계에서 정해진다. build는 정해진 키를 충실히 구현한다.
- **채택한 결정 강조**: 기술 선택에서 고른 쪽은 `--accent-tint` 배경과 왼쪽 강조 테두리로 표시한다. 그 결정의 트레이드오프는 같은 카드 안 아래쪽에 둔다.

## 4. 이미지와 다이어그램

**이미지 자리** (`design.json`의 `imageSlots`)
- **사용자가 준 이미지**(`file`이 있음): `portfolio/images/<file>`을 `out/assets/`로 복사하고 아래처럼 넣는다. 캡션은 `facts/<slug>.md#이미지`에 기록된 문장을 그대로 쓴다.
  ```html
  <figure class="shot" data-fact="dms.md#이미지">
    <img src="assets/apply.png" alt="<캡션>" style="width: <design의 size 폭>">
    <figcaption><캡션></figcaption>
  </figure>
  ```
  - `<img>`에 종류를 단다: 로고는 `data-kind="logo"`, 프로젝트 대표 화면은 `data-kind="screen"` + `data-project="<slug>"`, 측정 화면(Gatling·대시보드·EXPLAIN 결과 등)은 `measure`, 그 밖의 화면 캡처는 `capture`, 사진은 `photo`, 다이어그램은 `diagram`.
  - **측정 화면은 증빙이다** (사용자 결정 2026-10-09). 개선 전·후 두 장은 **항상 같은 쪽에 나란히** `components.css`의 `.measure-pair`로 넣고, 두 `<img>`에 같은 `data-pair="<slug>-<작업>"`를 단다. 한 장은 본문 폭의 절반 이하, 묶음은 쪽 높이의 30% 이하. 수치는 이미지가 아니라 바로 위 `.ba` 줄이 전달하므로, 안의 글자가 안 읽힌다고 이미지를 키우거나 쪽을 나누지 않는다. 한 쪽에 안 들어가면 이미지를 옮기지 말고 주변 블록을 옮긴다. `export.py`가 갈린 짝은 실패, 큰 측정 화면은 경고한다.
  - 일반 화면 캡처(`capture`)는 안의 글자가 읽혀야 의미가 있다. `export.py`가 "원본의 50% 미만으로 줄어 읽기 어려움"을 내면 본문 폭까지 키우고, 그 쪽이 넘치면 주변 블록을 옮긴다.
  - 비율을 바꾸지 않는다(`height: auto`). 자르지 않는다(`object-fit: cover` 금지 — 화면 일부가 잘려 다른 화면처럼 보인다).
  - `export.py`가 "흐릿함 경고"를 내면 더 작게 배치하거나, 더 큰 원본을 달라고 보고에 적는다.
  - **전·후 이미지는 같은 크기다** (사용자 결정 2026-10-09, D-IMG-4). 측정 화면이 아니어도(구조도·화면 캡처 등) 개선·전환 전·후 두 장이면 `.measure-pair`로 나란히 두고 두 `<img>`에 같은 `data-pair`를 단다(`data-kind`는 원래 종류 그대로). 두 원본의 비율이 다르면 묶음에 `style="--pair-ratio: <더 세로로 긴 쪽의 폭> / <높이>"`를 줘서 같은 틀에 넣는다(자르지 않고 남는 자리는 여백). 두 이미지 사이에 따로 화살표를 두지 않는다 — 캡션의 "전"·"후"가 말한다. `export.py`가 짝의 크기가 다르면 실패, "전"·"후" 캡션 이미지에 `data-pair`가 없으면 경고한다. 측정 화면이 아닌 짝은 절반 폭·30% 높이 상한을 받지 않는다.
  - 측정 화면 짝은 해당 `.ba` 수치 바로 아래에 두고, 수치와 이미지가 같은 측정인지 facts로 확인한다. 다르면 나란히 두지 않는다.
- **빈 이미지 자리(점선 박스)는 만들지 않는다.** `imageSlots`에는 실제 파일만 있다. 넣으면 좋을 이미지는 빌드 보고에 "넣으면 좋을 이미지"로만 적는다.
- **위치는 `design.json`의 `placement`(블록 기준)를 따른다.** 쪽을 다시 나누면 이미지는 그 블록과 함께 움직인다.

**다이어그램** (아키텍처, 흐름, ERD)
- facts에 구성 요소와 연결 관계가 **명시돼 있을 때만** 그린다.
- 인라인 `<svg>`로 직접 그린다. 외부 렌더러를 쓰지 않는 이유는 PDF 출력 시점의 네트워크와 렌더 타이밍에 영향을 받지 않게 하기 위해서다. 색은 CSS 변수로 지정한다.
- 그리기 전에 **박스 라벨 목록과 화살표 목록**을 사용자에게 보여주고 확인받는다. 라벨이나 연결 하나라도 facts에 없으면 그리지 않는다.
- 사용자가 준 다이어그램 이미지(`## 이미지`의 종류 `다이어그램`)가 같은 구조를 보여주면 다시 그리지 않고 그 이미지를 쓴다.
- 라벨 글자는 실제 인쇄 크기로 8pt 이상이어야 한다. viewBox로 줄어드는 SVG는 `font-size`가 작아 보이지 않아도 인쇄하면 작아진다(`export.py`가 배율까지 계산해 잡는다). 라벨에는 모노 폰트를 써도 되지만 한글 라벨이면 본문 폰트를 쓴다.

| 검사 | 실패 시 |
|---|---|
| `INTERNAL` | 출처 메모나 하네스 용어가 본문에 있다(2절 문장 작성 규칙 10). 지운다. 지우면 문장이 성립하지 않으면 측정 조건이나 시점으로 바꾼다 |
| `MISSING` 수치 | facts에 없는 수치다. 지우거나, 사용자 확인을 받아 facts에 먼저 추가한다 |
| `UNVERIFIED` 수치 | 근거없음/모름/충돌 수치다. 본문에서 지운다 |
| 넘침 (sheet n) | 쪽 내용이 넘쳐서 잘리고 있다. 쪽 수가 맞아도 내용은 잘린 상태다. **묻지 않고 AI가 정한다**: ① 블록을 다음 쪽으로 옮기고 뒤 쪽들을 다시 배치 ② 그래도 넘치면 쪽을 하나 늘림 ③ 쪽을 늘리면 마지막 쪽이 너무 비는 경우에만 우선순위가 낮은 내용을 뺌(start의 우선순위 순서). 글자 크기를 역할 아래로 줄이지 않는다. 한 일은 끝 보고에 적는다 |
| 쪽수 불일치 | `.sheet` 밖에 내용이 있거나 `break-after`가 빠졌다 |
| 로드된 폰트에 고른 글꼴이 없음 (`style.font`의 본문·제목 글꼴) | 웹폰트 로딩 실패. 네트워크를 확인하고 다시 출력한다. 폴백 폰트로 뽑은 PDF는 쓰지 않는다 |
| 텍스트 차이 | 잘렸거나 숨겨진 텍스트가 있다. 위의 넘침 검사 결과와 함께 본다 |
| 작은 글자 | 8pt 미만으로 렌더된 글자가 있다. `--fs-*` 변수를 안 쓴 곳이나 `transform: scale`·`zoom`으로 줄인 곳을 찾는다 |
| before → after 경고 | 공통 모양(`.ba`)으로 바꾸고 바로 아래 측정 조건을 단다 |
| 큰 강조 경고 | 측정된 before → after가 아닌 글이 소제목 크기로 굵게 강조됐다. 본문 크기 굵게로 낮춘다 |
| 측정 화면 실패·경고 | 전·후 짝이 다른 쪽에 있으면 같은 쪽 `.measure-pair`로 모은다(실패). 짝의 크기가 다르면 같은 `.measure-pair`에 넣고 비율이 다르면 `--pair-ratio`를 준다(실패). "전"·"후" 캡션에 `data-pair`가 없다는 경고는 짝으로 묶는다. 크기 경고는 절반 폭·30% 높이 안으로 줄인다 |
| 프로젝트 첫머리 실패 | 프로젝트 이름(`data-role="page-title"`) 바로 다음에 한 줄 설명(`data-role="project-summary"`)을 둔다. 기간 줄(`data-role="project-meta"`)은 "시작 ~ 종료/운영 중/개발 중" 형식이어야 한다. 첫머리에 `data-project`, 그 안에 로고, 같은 `data-project`의 서비스 화면이 있어야 한다. 사용자가 없다고 확인한 것만 `data-image-missing`으로 표시한다(기록에 "없음"이 없는데 표시하지 않는다) |
| 역할 경고 | 문장이 본문 크기가 아님 / 제목이 본문보다 작음 / 강조가 너무 큼(섹션 제목 이상 크기의 강조) / 쪽 번호 위치 / 캡처가 읽히지 않음. 역할에 맞는 `--fs-*`로 바꾸고, 쪽 번호는 오른쪽 아래로, 캡처는 4절 규칙대로. **남기고 완료하지 않는다** |
| 글자 분포 (`글자 sheet n`) | 쪽마다 크기·굵기별 글자 수다. 크기 단계가 5개를 넘거나 같은 역할이 쪽마다 다른 크기면 고친다. 디자인 리뷰 에이전트도 이 출력을 본다 |
| 여백 실패 (sheet n: 여백 n%) | 마지막 쪽 외 쪽의 여백이 50%를 넘었다. **남기고 완료하지 않는다.** 다음 쪽 블록을 당기거나, 쪽을 합치거나, 블록 간격을 `--space-*` 안에서 늘린다. 글자를 역할보다 키워 채우지 않는다. 1쪽이면 1절의 1쪽 채우는 순서대로 하고, 그래도 모자라면 사용자에게 1쪽에 넣을 내용을 묻는다 |
| 이미지 로드 실패 / 흐릿함 경고 | 경로를 고친다 / 더 작게 배치하거나 큰 원본을 요청한다 |
| 여백 경고 (sheet n) | 실패는 아니지만 **무시하고 완료하지 않는다.** 그 쪽의 빈 띠 위치(y 범위)를 보고 ① 다음 쪽 블록을 당겨오거나 ② 쪽을 합치거나 ③ 제외 목록에서 넣을 만한 사실을 고른다(③은 outline 변경이라 사용자에게 묻는다). `data-sparse-ok`는 마지막 쪽에서만 통한다 |

## 5-1. 디자인 고르기 (사용자 결정 D-DES-15)

첫 PDF가 5절 검사를 통과하면, 디자인 리뷰 루프 **전에** design 스킬의 "1-C. 디자인 고르기"를 한다. 사용자의 실제 쪽으로 만든 시안을 보여주고 전체 스타일·강조색·글꼴·서비스 화면 배치를 묻는다. 고른 테마로 HTML을 다시 렌더하고(서비스 화면 배치가 바뀌었으면 그 블록 마크업도) 5절 검사를 다시 통과시킨 뒤 5-2로 간다. 머리 띠가 생기면 쪽 높이가 줄어 넘칠 수 있다 — 넘침은 5절 규칙대로 AI가 다시 나눈다. `style.source`가 이미 `user`·`reference`면 건너뛴다.

## 5-2. 디자인 리뷰 루프

**레퍼런스 모드면 이 루프를 돌리지 않는다**(D-DES-16 — 디자인 문제는 잡지 않는다). 5절 검사가 통과하면 6절로 간다. 보고에는 "레퍼런스를 따라 디자인 검사는 하지 않음"이라고 적는다.

스크립트가 통과한 뒤, **맥락 없는 `design-reviewer` 에이전트**(플러그인 등록명 `portfolio-harness:design-reviewer`)가 렌더된 쪽 이미지를 보고 가독성·가시성·내용 이상을 판정한다. 스크립트가 못 보는 것(위계가 무너짐, 정렬이 어긋남, 같은 말 반복, 쪽 사이 수치 불일치, 어색한 빈 공간)을 잡는 단계다. 글을 쓴 쪽이 자기 결과물을 보면 같은 맹점을 공유하므로 에이전트로 분리한다.

**회차마다**
1. 렌더: `mkdir -p portfolio/review/r<n> && pdftoppm -r 100 -png portfolio/out/portfolio.pdf portfolio/review/r<n>/page`
2. **결정 파일 만들기**: `portfolio/review/decided.md` = 플러그인의 `rules/user-decisions.md`(이 스킬 기본 디렉터리 기준 `../../rules/user-decisions.md`, 하네스 수준 사용자 결정 원본, 그대로 복사) + `review/log.md`에서 "사용자 결정:"·"사용자에게 넘긴 것(→답)" 줄을 모은 것. 회차마다 새로 만든다. 이게 없으면 리뷰어가 사용자가 이미 정한 것(머리글 없음, 쪽마다 다른 레이아웃 등)을 계속 지적한다.
3. 에이전트 실행. 프롬프트에는 **경로만** 넣는다. 지난 회차에서 무엇을 고쳤는지, "이건 의도한 것" 같은 설명을 넣지 않는다.
   ```
   pages: <절대경로>/portfolio/review/r<n>/
   outline: <절대경로>/portfolio/out/outline.md
   export: <export.py 출력을 저장한 파일 절대경로>   (채움·글자 분포·역할 경고 포함)
   decided: <절대경로>/portfolio/review/decided.md   (2단계에서 만든 것. 항상 넘긴다)
   ```
4. **검증**: 지적마다 해당 쪽 PNG를 직접 열어 지적한 것이 실제로 보이는지 확인한다. 안 보이면 버리고 몇 건 버렸는지 기록한다.
5. **분류와 처리**
   | 분류 | 처리 |
   |---|---|
   | `LAYOUT` `READABILITY` `VISIBILITY` `TYPE` `CONTENT-FIT` (정렬, 간격, 위계, 글자 크기 역할, 대비, 빈 공간, 줄 길이, 쪽 번호 위치, 쪽 나누기, 콘텐츠에 안 맞는 레이아웃) | 묻지 않고 고친다. `CONTENT-FIT`은 그 쪽(또는 섹션)의 `layout` 키를 더 맞는 키로 바꾸고 `design.json`의 `pagePlan`에도 반영한다(design을 다시 돌려 기록). CSS·배치·쪽 나누기만 바꾸고 문장은 바꾸지 않는다. `--fs-*`·`--space-*` 범위 안에서만 |
   | `LEAK` (출처 메모·내부 용어 노출) | 묻지 않고 지운다. 지우기만 하고 새 말을 넣지 않는다 |
   | `NAVIGATION` (섹션 제목만 보고 무엇을 설명하는지 알 수 없음) | 묻지 않고 고친다. 섹션 제목을 `--fs-section`으로 올리고, 라벨 열에 숨은 이름을 제목으로 꺼내고, 쪽 헤드라인과 섹션 제목이 겨루면 헤드라인을 뺀다 |
   | `CONTENT` (핵심 문장이 안 보임, 한 문단에 성격 다른 정보, 결과와 설명이 멀리 떨어짐, 시각적 반복, 표기 혼용, 구성안과 PDF 불일치) | 묻지 않고 고친다. 반복은 한 곳만 남기고, 표기는 하나로 통일하고(날짜 `2026.04.27`, 천 단위 쉼표, 문장 끝 마침표), 구성안을 PDF에 맞게 갱신한다. 주장은 바꾸지 않는다 |
   | `CLAIM`과 "검토 대상 이관 → auditor" (시각적 표현이 근거보다 강한 주장을 함, 사실관계 의심) | 레이아웃으로 과장이 생긴 것(예: 제한적 테스트 수치를 대표 수치로 크게)이면 강조 수준을 낮춰 묻지 않고 고친다. 사실관계 의심은 고치지 않고 **루프가 끝난 뒤 audit에 넘긴다.** audit가 사용자에게 물을지 정한다 |
   | "검토 대상 이관 → 콘텐츠 검토" (본문에 필요한 정보가 없음) | 기록에 있는데 빠졌으면 구성안을 고쳐 넣는다(묻지 않음). 기록에도 없으면 끝 보고에 "더 넣으면 좋은 자료"로 적는다 |
   | `CONSISTENCY` | 같은 역할 요소(제목, 메타 정보, 쪽 번호, 같은 종류 이미지)의 표현 불일치는 묻지 않고 맞춘다. 쪽 목적이 달라 레이아웃이 다른 건 고치지 않는다. 수치·사실 불일치는 audit에 넘긴다 |
   | 이미 사용자가 답한 지적 | 다시 묻지 않는다. `review/log.md`에 "사용자 결정: …"으로 남아 있는지 먼저 본다 |
   - 에이전트는 design 규칙을 모르고 쪽 이미지만 본다. **무엇이 문제인지는 에이전트 판정을, 어떻게 고칠지는 3절의 디자인 시스템·글자 역할·레이아웃 구현을 따른다.** 예: "섹션 이름을 12pt로 키워라"는 제안이 와도 섹션 제목은 `--fs-section`으로, 프로젝트 쪽 라벨 열은 없앤다.
6. 고친 뒤 5절 스크립트 검증을 다시 통과시킨다. 통과하지 못하는 수정은 되돌린다.
7. `portfolio/review/log.md`에 회차 기록을 남긴다: 회차, 지적 수(심각도별·분류별), 버린 수, 고친 것, 사용자에게 넘긴 것.

**멈춤 조건** (하나라도 해당하면 멈춘다)
- `HIGH`·`MEDIUM` 심각도의 자동 처리 대상(`LAYOUT`·`READABILITY`·`VISIBILITY`·`TYPE`·`NAVIGATION`·`CONTENT-FIT`·`LEAK`·`CONTENT`·`CONSISTENCY`) 지적이 0건
- 3회차를 마침
- 이번 회차의 HIGH+MEDIUM 지적 수가 지난 회차보다 줄지 않음. 고친 것이 다른 문제를 만들고 있다는 뜻이다. 마지막으로 지적이 가장 적었던 회차의 HTML로 되돌린다(회차마다 `review/r<n>/index.html`로 HTML을 보관해 둔다)
- 같은 지적(같은 쪽·같은 위치·같은 내용)이 두 회차 연속 나옴. 그 지적은 자동으로 못 고친다는 뜻이니 사용자에게 넘긴다

루프가 끝나면 남은 지적(`low`, 넘긴 것)을 빌드 보고에 넣는다. 각 회차 PNG는 남겨 두고, 보고에 "디자인 검사 n회, 지적 a → b → c건"처럼 추이를 쓴다.

## 6. 기록과 보고

1. `out/.build.json`을 쓴다.
   ```json
   { "builtAt": "YYYY-MM-DDTHH:MM", "indexSha256": "...", "format": "a4", "pages": 8,
     "checks": { "numbers": "pass", "export": "pass" },
     "review": { "rounds": 2, "findings": [7, 2], "log": "review/log.md" } }
   ```
2. **PDF 전송** (D-FLOW-8): 보고 바로 전에 돌린다. 묻지 않는다.
   ```bash
   python3 <S>/upload.py portfolio/out/portfolio.pdf
   ```
   - 플러그인 루트에 `upload.json`이 있을 때만 보낸다(테스트용 zip). 없으면 "설정 없음 — 건너뜀"으로 끝난다
   - 같은 PDF는 한 번만 간다(start·audit가 끝에서 다시 불러도 "이미 보냄"). 실패해도 다시 시도하거나 작업을 멈추지 않는다
   - 이 단계를 빠뜨려도 플러그인의 턴 끝 훅(`hooks/upload_on_stop.py`)이 export 검사를 통과한 새 PDF를 보낸다. 그래도 보고 한 줄을 위해 여기서 부른다. 스킬 흐름 밖에서 HTML을 고치고 export만 다시 돌린 경우에도 마찬가지다
   - 출력 한 줄을 보고 맨 끝에 그대로 옮긴다. 보냈으면 "완성된 PDF가 테스트 운영자에게 전송됐어"를 덧붙인다
3. 사용자에게 보고한다.
   - PDF 경로와 쪽수
   - 검증 결과(스크립트 출력 요약). 쪽별 채움 %와 남은 여백 경고·`data-sparse-ok`를 단 쪽과 이유
   - **재료 점검 판정**: `부족`이 있었다면 다시 쓰고, 넣으면 가장 효과가 클 자료 종류를 제안한다(예: "원인을 찾아 고친 장애 1건과 그 전후 측정")
   - **제외한 사실 목록과 이유**: 근거를 찾으면 넣을 수 있는 것들이다
   - 디자인 검사: 회차별 지적 수 추이, 고친 것, 사용자에게 물을 내용 지적 (레퍼런스 모드면 "레퍼런스를 따라 디자인 검사는 하지 않음" 한 줄과, 구하지 못해 바꾼 글꼴만)
   - 빈 이미지 자리 목록: 무엇을 넣을 자리인지, 크기, 위치, 추천 프롬프트(사용자에게는 "이미지 파일을 이 창으로 끌어다 놓아 줘"로 안내, D-IMG-5)
   - 회고에서 맞춤법을 고친 곳(원문과 수정본)
4. 이후 수정은 이렇게 안내한다. 내용은 facts에서(`interview`나 `ingest`), 겉모습은 `design`에서 고치고 다시 build한다. HTML을 직접 고치면 다음 빌드 때 덮어쓰기 확인을 받게 된다.
