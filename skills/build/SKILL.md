# 포트폴리오 생성 (build)

> **먼저 읽는다** — 이 스킬을 불러오면 표시되는 기본 디렉터리(`Base directory for this skill`) 기준으로 `../../rules/principles.md`(제품 원칙)와 `../../rules/user-decisions.md`(사용자 결정 원본)를 읽는다. 이 문서의 규칙이 그 둘과 다르면 그 둘이 맞다. 같은 세션에서 이미 읽었으면 다시 읽지 않는다. **둘 중 하나라도 읽지 못하면(파일 없음·읽기 실패) 이 스킬의 작업을 시작하지 않는다** — 어떤 파일을 어느 경로로 찾았는지와 "원칙 문서를 읽지 못해 멈췄다"를 첫 줄에 알리고 끝낸다. 원칙 없이 기억이나 이 문서만으로 대신 진행하지 않는다.
>
> **한국어로 말한다** — 사용자에게 하는 모든 말(질문·선택지·중간 안내·끝 보고)은 한국어로 쓴다(원칙 → Target Users). 스크립트 출력·에이전트 보고·영어 자료를 옮길 때도 한국어로 풀어 쓴다. 기술 이름·코드·파일 경로·고유명사만 원래 표기. 사용자가 다른 언어를 요청했을 때만 바꾼다. 격리 실행(개인 설정 없음)에서 끝 보고가 영어로 나온 적이 있다(10-10).

> 사용자에게 말할 때는 `start` 스킬의 "사용자에게 쓰는 말" 표를 따른다. facts·outline·슬롯 같은 내부 이름을 채팅에 그대로 쓰지 않는다.

facts와 design을 합쳐 HTML을 만들고 PDF로 출력한다. **이 스킬만 포트폴리오 문장을 쓰고**, 모든 문장은 facts의 한 줄로 되돌아갈 수 있어야 한다. `theme/` CSS와 `design.json`은 고치지 않는다 — 바꿀 일이 생기면 design을 다시 돈다(D-FLOW-6).

## 결과물

`portfolio/out/`에 `outline.md`(쪽별 구성안·제외 목록, 승인용), `index.html`, `tokens.css`·`components.css`·`style.css`와 `assets/`(out/만 있으면 열림), `portfolio.pdf`, `.build.json`(해시·시각·검증 결과). 스크립트는 이 스킬의 `scripts/`, `<S>`는 그 경로다.

## 0. 사전 확인

순서대로 한다.
1. **환경 점검**: `python3 <S>/env_check.py`. 실패면 HTML을 쓰지 않고 멈춘다 — 없는 것과 설치 명령(출력 그대로)을 알리고, 설치했다고 하면 다시 점검한다.
2. **기록 형식 검사** (`facts/`가 비었으면 3부터. export에서 실패하면 처음부터 다시 돌게 되므로 여기서 잡는다):
   `python3 <S>/facts_lint.py portfolio/facts --images portfolio/images --cache portfolio/.facts_lint.json`
   - `ERROR[수정]`(프로필 표시, 날짜 표기, slug, 이미지 종류 재분류, 출처 태그): "고치는 법"대로 고치고 다시 돌린다(묻지 않음).
   - `ERROR[확인]`(필수 이미지, 상태, 종료일, 사용 기술 전무, 충돌, 없는 이미지 파일, 사용자 말·자료에 없는 수치): 추측해서 채우지 않고 한 메시지에 모아 묻는다. "폴더에 기록에 없는 파일"이 나와도 바로 기록하지 않고 파일 이름을 보여주며 무엇인지 묻는다.
   - `WARN`: 진행하고 끝 보고에 적는다. 옛 형식 `period`는 build가 합쳐 쓴다.
   - **ERROR가 남아 있으면 HTML을 쓰지 않는다.**
3. **앞 단계가 비어 있으면 묻지 않고 그 단계부터** 한다("먼저 ~해야 해, 시작할까?" 금지): `facts/`가 비면 `interview`, `design.json`·`theme/tokens.css`가 없으면 `design`.
4. **디자인 최신 여부**: 하나라도 해당하면 design을 다시 돈다(되묻지 않음, design은 `style`이 없을 때만 레퍼런스를 묻는다). `--check` 외에는 스크립트가 없으니 직접 본다.
   - `style`이 없거나 `schemaVersion` 7 미만(6은 이야기 모양 키가 없던 판)
   - (레퍼런스 모드면 아래는 보지 않는다 — 배치와 이미지 자리는 레퍼런스가 정한다)
   - `pagePlan`이 비었거나, 세부 설명 섹션에 `layout`이 없거나, `design.base.json`의 `layouts`에 없는 키
   - `python3 <design 스킬의 scripts>/make_theme.py --check portfolio/design.json portfolio/theme`가 "테마 최신: 일치"가 아님
   - `imageSlots`에 `file` 없는 빈 자리, 또는 1쪽에 놓인 이미지
   - `## 이미지`에 기록된 이미지(사용 안 함 제외)가 `imageSlots`의 `file`에 없음
   - 종류 `측정 화면`이 `kind: measure`가 아니거나, 개선 전·후 짝인데 `pair`가 없음
5. **멈추고 알린다**
   - **필수 이미지가 빠짐**: 프로젝트마다 `## 이미지`에 `로고`·`서비스 화면` 파일이나 "없음"이 있어야 한다. 아니면 빌드하지 않고 요청한다("dms 로고랑 서비스 화면이 아직 없어. 이미지 파일을 이 창으로 끌어다 놓아 줘. 없으면 없다고 해줘" — 받으면 ingest 이미지 절차로 AI가 복사, D-IMG-5). `portfolio/images/`에 새 파일이 있으면 먼저 ingest 이미지 절차를 한다. **폴더에 있다는 것만으로 용도를 정해 기록하지 않는다** — 확인 전에는 기록하지 않고 `[src: interview]`를 달지 않는다(R-EVD-7). 물을 수 없으면 기록하지 말고 멈춘다.
   - `status: 충돌` 항목: 목록을 보여주고 해소를 요청한다. 충돌한 값 중 하나를 골라 쓰지 않는다.
6. **재료 점검**: `python3 <S>/facts_stats.py portfolio/facts`. `부족`인 심층 프로젝트가 있으면 구성안 메시지 **맨 앞에** 표와 "무엇이 없어서 약한지"를 쓰고, 승인 질문에 "자료를 더 넣고 다시"(→ `ingest`, 장애 보고서·PR·위키·기존 포트폴리오 등 구체적으로)를 더한다. 따로 멈추지 않는다. 그대로 진행해도 빌드 보고에 판정을 다시 적는다.
7. **덮어쓰기 확인**: `.build.json`의 해시와 현재 `index.html`의 sha256이 다르면 사용자가 HTML을 고친 것이다. 덮어쓰기 전에 묻는다: facts·design으로 옮길지, 덮어쓸지, 멈출지.

**레퍼런스 모드** (`style.source`가 `reference`, D-DES-16): 레퍼런스를 그대로 따르고 **내용만 검사한다.** `layout_check.py`, 디자인 고르기(5-1), 디자인 리뷰 루프(5-2)를 하지 않는다. export는 스스로 디자인 검사를 건너뛰고 기록·수치 사전 검증, 이미지 로드, 넘침·쪽수·텍스트 대조, 1쪽 직무명, 안 보이는 글자, 링크만 본다.

## 1. 내용 선별 → outline.md

`design.json`의 `format`, `pagePlan`, `sections`를 따라 쪽별 구성안을 만든다. 단 전체 회고는 `sections`가 아니라 기록에 회고가 있는지로 정한다(D-PRJ-6). 쪽마다 `layout`과 `purpose`를 옮긴다.

**쪽 여백 상한** (D-DES-4): 마지막 쪽 외 모든 쪽(1쪽 포함) 여백 50% 이하. 구성안에서 쪽마다 채움(많음/적당/적음)을 추정하고, 마지막 쪽 외에 "적음"이면 블록을 옮기거나 쪽을 합친다. 빌드 후 모자라도 묻지 않고 당기거나 합친다.

**1쪽 양식** (`profile`, design "첫 페이지"): 순서 D-P1-1, 활동·수상은 항목마다 날짜를 같은 줄 오른쪽에(D-P1-4), "활동 없음"이면 활동 줄을 빼고 묻지 않는다. 프로젝트는 2쪽부터, 1쪽에 프로젝트 목록·이미지를 두지 않는다. 라벨 열(`--label-col`)은 1쪽에만.
- **역할 표시** (이 순서가 아니면 export 실패): 이름 `<h1 data-role="name">`(`--fs-name`) → 바로 아래 직무명 `data-role="job-title"`(기록의 `직무명:` 그대로, `--fs-subtitle`, 없으면 export 실패, D-P1-5) → 한 줄 소개 `data-role="tagline"`(`--fs-subtitle`, 강조색 가능). 라벨 `--fs-meta`, 나머지 문장 `--fs-body`. export의 강조 검사가 이 표시로 이름·한 줄 소개를 구분한다.
- **1쪽 채우는 순서**: ① 블록 간격을 `--space-*` 안에서 늘림 ② 기술을 분류별로(언어·프레임워크 / DB / 인프라) ③ 수상·자격증에 기관·내용 한 줄 ④ 그래도 모자라면 1쪽에 더 넣을 것(활동, 교육)을 묻는다. **글자를 역할보다 키워서 채우지 않는다**(자기소개도 `--fs-body`). 기록에 없는 정보를 만들지 않는다.
- **기술 목록**: `profile.md#주력 기술` + 프로젝트 기록에 사용했다고 적힌 기술(기술 선택·작업에 이름이 나온 것)을 "추가 후보"로 구성안에 보여주고 승인받은 것만 넣는다(본문엔 Kotlin이 나오는데 1쪽엔 없으면 이상하게 읽힌다).
- **자기소개**: profile에 없으면 facts만으로 3~5문장 초안을 구성안에 넣고(문장마다 근거 위치), 승인받은 것만 쓴다. 성과는 임팩트가 큰 것부터 — 본문 프로젝트 순서와 맞추지 않는다(D-P1-7). 사용자가 쓴 자기소개든 초안이든 블록에 `data-role="headline"`과 `data-fact`를 단다(export가 이 안의 "a → b"는 강조 모양 경고에서 뺀다).

**넣지 않는 것**: `근거없음` 수치는 빼되 작업은 수치 없이 서술할 수 있으면 남긴다. `모름`·`빈칸` 항목은 뺀다. `역할 미확인`은 "본인이 했다"로 쓰지 않고 팀 성과로 쓰거나 뺀다.

**메시지 정하기** — "이 사람을 왜 뽑아야 하는지"가 읽히게 한다. 무엇을 앞에 둘지 고르는 것은 build의 일이다("facts에 없는 말 금지"가 그것까지 막지 않는다).
- **한 줄 소개**: `profile.md`에 있으면 그대로. 없으면 facts만 조합한 후보 2~3개(조합한 위치 표시)를 구성안에 넣고 고르게 한다. 고르지 않으면 넣지 않는다.
- **섹션 제목과 한 줄 결과**: "무엇을 설명하는지"(예: "상벌점 조회 성능 개선")와 "그래서 어떻게 됐는지"(예: "평균 1,225ms → 241ms"). 섹션 제목은 기록의 작업 이름을 다듬어 AI가 정한다.
- **쪽 헤드라인**: "이 쪽에서 봐야 할 것" 한 문장. 길어도 핵심을 분명히 말하면 둔다(D-DES-8). `data-role="headline"`으로 표시하고 섹션 제목과 다른 모양(크기·굵기·위치)으로. 가장 강한 사실(측정된 결과, 대안을 비교한 결정, 본인이 단독으로 한 일)을 압축하고 근거 위치를 적는다. 새 주장, 형용사("대폭", "혁신적"), facts에 없는 인과를 넣지 않는다.

`outline.md` 형식:
```markdown
## 재료 점검
(facts_stats.py 표 그대로) — DMS: 부족 (완결된 트러블슈팅 0, 측정 조건 있는 결과 1)
## 한 줄 소개 후보
1. "<문장>" — profile.md#주력 기술 + dms.md#역할
## 3쪽 — DMS ① 개요·역할·기술 선택  (채움: 적당)
- 헤드라인: "<문장>" — dms.md#작업 > 학교 전용 챗봇 결과
- 기술 선택: Redis (선택 이유 있음), MySQL Full-Text (대안 비교 있음)
## 제외
- facts/dms.md "월 사용자 약 300명" — 근거없음
```

구성안을 채팅에 재료 점검 → 한 줄 소개 후보 → 쪽별(헤드라인, 채움, 주요 블록) → 제외 순으로 보여주고, 같은 턴에 묻는다. **승인받은 뒤** HTML을 쓴다. 승인 대상은 **무엇을 넣고 뺄지와 문장의 주장**이다. 쪽 나누기는 예상일 뿐이라, 빌드 중 넘치거나 남으면 묻지 않고 다시 나누고 끝 보고에 적는다("3쪽이 넘쳐 스케줄러 블록을 4쪽으로 옮김").

## 2. 문장 작성 규칙

번호는 다른 문서가 가리키므로 바꾸지 않는다.

1. **facts에 없는 내용을 쓰지 않는다.** 연결어("그래서", "이를 통해")로 facts에 없는 인과를 만들지 않는다.
2. **수치는 facts의 표기 그대로.** 개선율·배수·퍼센트를 새로 계산하지 않는다. 기록에 나열된 것을 세어 쓴 개수("DB 2개")도 계산값이다. 필요하면 묻고, 승인받은 값을 facts에 `[src: interview]`로 먼저 추가한다(질문 도구 선택지에 값을 넣어 고르게 해야 근거 원문에 남는다, D-TXT-6). `check_numbers.py` `MISSING`.
3. **수치 옆에 측정 조건**을 같은 문장이나 바로 아래 캡션에 붙인다(facts에 있을 때). 지표 이름(평균·p95 등)은 기록에 있을 때만 — 없으면 묻지도 추측해 넣지도 않는다(D-TXT-8). 표를 줄여도 조건 줄은 지우지 않는다.
4. **측정 축을 섞지 않는다.** API 응답 시간과 DB 실행 시간처럼 다른 계층의 수치를 한 문장에 넣지 않는다. 넣어야 하면 각각 무엇을 잰 값인지 밝힌다.
5. **따로 일어난 작업을 한 줄 서사로 잇지 않는다.** facts에서 별도 항목이면 여기서도 별도다.
6. **주어를 지우지 않는다.** "개선되었다" ✗ → "본인이 ~를 바꿔 ~가 됐다" ○. 누가 했는지는 facts의 역할 기록대로.
7. **제약은 facts의 구분 그대로.** "선택"을 "불가"로 쓰지 않고, 그 반대도 하지 않는다.
8. **문체**: "~를 해서 ~가 됐다"처럼 사실을 서술한다. 감상 표현("뼈저리게 느꼈다")은 쓰지 않는다.
9. **헤드라인·한 줄 소개**: 구성안에서 승인된 문장 그대로. 블록에 `data-role="headline"`과 `data-fact`(여러 개면 쉼표). 감사가 SCOPE·CAUSAL로 따로 본다.
10. **출처 메모를 본문에 쓰지 않는다.** `(원문: …)`, `(당시 블로그 기준)`, "DB에서 얻은 값", `[src: …]`는 근거 추적용이라 독자에겐 "자기 글을 못 믿는 사람"처럼 읽힌다. 측정 조건(도구, 요청 수, 데이터 건수, 시점)은 쓰고 출처(블로그, 인터뷰, 원문, 위키)는 쓰지 않는다. "2026년 4월 블로그 기준" ✗ → "전환 당시(2026.04)" ○ (시점이 facts에 있을 때만). `check_numbers.py` `INTERNAL`.
11. **쪽 사이 일관성**: 같은 대상(사용자 수, 팀 인원, 기간, 같은 지표)이 쪽마다 다르면 안 된다. 값이 둘이면 하나만 쓰거나 각각 언제의 값인지 밝힌다. 2쪽 "학생 180명·교사 30명"과 4쪽 "사용자 약 200명"이 나란히 있으면 독자는 어느 쪽이 맞는지 모른다.
12. **제목과 헤드라인이 같은 말로 시작하지 않는다**(D-DES-11). 헤드라인은 결과나 결정부터.
13. **회고**: `회고 (원문 유지)` 인용을 그대로. 맞춤법·띄어쓰기·조사만 고치고(D-TXT-3) 고친 곳은 보고에 원문과 나란히. 내용을 바꾸거나 문장을 더하지 않는다. **문장 단위**로만 줄인다 — 문장 중간을 "…"로 자르지 않고, 길면 어느 문장을 쓸지 구성안에서 묻는다(D-TXT-7, `CUT`). 상투구·비문이어도 다시 쓰자고 묻지 않는다(U-5).

## 3. HTML 구조 규칙

> **레퍼런스 모드**: 레퍼런스 원본과 `style.referenceLayout`대로 배치·쪽 구성·블록 순서·글자 크기·색·장식을 쓴다(페이지 CSS에 직접 값을 써도 된다). 이 절에서 **"디자인과 글자", 공용 부품, 머리 자리, 서비스 화면 배치, 첫머리·블록 순서, 레이아웃 구현은 적용하지 않는다.** 출력·내용 규칙(`zoom`·`transform`·CSS `content`로 글자를 바꾸거나 넣지 않기, `.sheet` 구조 — 레퍼런스가 연속이면 연속, 화면=인쇄, 링크, 근거 추적, 검사 제외 표시, 잘리면 안 되는 블록, 1쪽 직무명)만 지킨다. 넘치면 배치를 유지한 채 쪽을 나눈다.

**디자인과 글자** (원본: design "디자인 시스템", D-DES-3·9·10)
- 흰 바탕, 쪽마다 같은 좌우 기준선, 위계는 크기·굵기·여백으로(색 ✗). 모든 내용을 카드에 넣지 않는다(상자는 채택한 결정처럼 의미가 있을 때만, 모서리 4px 이하, 그림자 없음). 장식 도형·그라디언트·이모지 없음. 왼쪽 정렬(양쪽 정렬 금지). 기술 목록은 칩 ✗ → 분류별 쉼표 목록 ○. 큰 수치·한글이 섞인 강조에 모노 폰트 금지(모노는 코드·API 경로만. export는 `.ba` 수치만 경고하고 나머지 강조는 문서뿐). 색·글꼴은 `style`에 정한 것만.
- **글자 역할**(값은 `tokens.css`): 이름 `--fs-name`, 프로젝트 이름 `--fs-page-title`, 섹션 제목 `--fs-section`, 소제목·한 줄 설명·한 줄 소개·측정된 핵심 수치 `--fs-subtitle`, **모든 설명 문장** `--fs-body`, 기간·팀·라벨·날짜 `--fs-meta`, 측정 조건·이미지 설명·쪽 번호 `--fs-caption`, 코드 `--fs-code`.
- **글자 크기는 `--fs-*`만**(본문 `--fs-body`는 10.5pt 이상). pt/px 직접 금지. 넘쳐도 범위 아래로 줄이지 않고 내용을 옮기거나 덜어낸다. `zoom`·`transform: scale`로 줄이지 않는다.
- **수치 강조**: 측정된 before → after(측정 조건 있음)는 개수 제한 없이 — 그 쪽의 핵심이면 `.ba.ba-lead`(소제목 크기), 보조면 `.ba`(본문 크기). 측정 결과가 아닌 수치(개수, 기간, 사용자 수)는 본문 크기 굵게까지.

**파일과 쪽**
- **단일 파일** `out/index.html`. `portfolio/theme/`의 `tokens.css` → `components.css` → `style.css`를 `out/`로 복사해 이 순서로 `<link>`. 색·폰트·간격은 CSS 변수만.
- **공용 부품**: 제목 글꼴(`--font-display`)·제목 모양·장식은 `style.css`가 맡는다 — 페이지 CSS에서 `name`·`page-title`·`section-title`의 글꼴과 장식(막대·선)을 정하지 않는다(크기·굵기·간격은 된다). before → after는 반드시 `.ba`: `data-role="before-after"` 안에 `.before`·`.arrow`·`.after`, 바로 다음 `<p class="ba-cond" data-role="measure-cond">`. `components.css` 클래스를 다시 정의하지 않는다(간격·폭 조정만). 화살표 같은 글자를 CSS `content`로 넣지 않는다(PDF 텍스트에만 생긴다).
- **A4**: 쪽마다 `<section class="sheet">`, 210mm×297mm, `overflow: hidden`, `break-after: page`. 안쪽 여백은 `padding: var(--sheet-pad-top) var(--sheet-pad-x) var(--sheet-pad-bottom)`으로만(머리 띠가 이 값으로 종이 끝까지 닿는다). **연속 페이지**는 `.sheet` 없이 흐름 레이아웃, `@page`는 export가 넣으니 쓰지 않는다.
- **화면 보기는 `components.css`가 맡는다**(D-DES-12): `body`·`html`의 `background`, `.sheet`의 배경·그림자·바깥 여백을 정하지 않는다.
- **화면과 인쇄를 같게**: `@media print`는 요소 숨기기에만(크기·간격·폰트 변경 금지 — 실측은 화면 렌더).
- **잘리면 안 되는 블록**(카드, 표, 코드)에 `break-inside: avoid`. 인쇄 때 flex 안에서는 무시되므로 flex 자식으로 두지 않는다.
- **머리 자리 표시**: 1쪽 이름·한 줄 소개는 `<header data-role="profile-head">`, 프로젝트 첫머리는 `<header class="project-head">`. 여기에 배경·테두리를 주지 않고, 1쪽 머리 바로 아래(라벨 그리드 위)에 선을 긋지 않는다 — look이 맡는다.
- **쪽 맨 위에 반복되는 머리글을 두지 않는다**(D-DES-6). 섹션 제목은 섹션 맨 위 `<h2 data-role="section-title">`(또는 `h3`).
- **쪽 번호**(넣는다면): `<div class="page-number" data-role="page-number">2 / 4</div>`를 `.sheet` 오른쪽 아래 `position: absolute; right: var(--sheet-pad-x); bottom: <여백>`. 프로젝트가 2개 이상이고 한 프로젝트가 여러 쪽이면 `DMS · 3 / 6`, 하나면 숫자만(D-DES-5).

**링크** (D-DES-14, `link_check.py` 실패): 보이는 주소·이메일은 **모두 `<a href>`**. href는 `https://…`·`mailto:…` 절대 주소 — 글자는 `github.com/yellowstarr`로 짧아도 href는 `https://github.com/yellowstarr`. 글자로만 두거나 `github.com/…`을 href에 그대로 넣으면(상대 경로) PDF에서 안 가거나 엉뚱한 곳으로 간다. 글자와 href의 사이트는 같아야 한다. 404·없는 도메인이면 주소를 추측해 고치지 말고 사용자에게 묻는다. 401·403은 끝 보고에 "직접 열어 확인".

**근거 추적과 검사 제외**
- 사실을 담은 블록에 `data-fact="dms.md#검색 API 개선"`(facts의 실제 제목). 여럿이면 쉼표: `data-fact="dms.md#기술 선택, dms.md#작업"`.
- `data-nocheck`: 수치 검사 제외(쪽 번호·연도 같은 장식 숫자). `data-print-hidden`: 인쇄에서 숨김(`@media print`의 `display: none`과 짝) — 텍스트 대조에서 빠지고, export는 숨긴 상태로 재고 뽑는다. `<title>`은 스크립트가 뺀다(속성 불필요).
- `data-sparse-ok`(`.sheet`): 의도한 여백. **마지막 쪽에서만 통한다**. 달았으면 보고에 이유를 적는다.

- **기간 줄**: 기록의 `start`·`end`·`status`로 `2025.03 ~ 2025.06` 또는 `2026.03 ~ 운영 중`/`개발 중`(`YYYY.MM`, 일 없음). 상태를 다른 자리에 또 쓰지 않는다. 옛 `period: 2026.03.01 ~ 진행 중` + `status: 운영 중`은 `2026.03 ~ 운영 중`. **이름과 같은 줄 오른쪽** — 아래 줄이면 이름과 한 줄 설명 사이를 막아 실패한다.
- **한 줄 설명**: 기록의 `## 개요`(무슨 서비스, 누가 쓰는지), 없으면 인터뷰 프로젝트 목록의 "한 줄 설명". 성과·수치·본인이 한 일을 섞지 않는다. 이름과 한 줄 설명 사이에 헤드라인·기간·라벨을 두지 않는다. 쪽 헤드라인은 첫머리 **뒤**에.

**프로젝트 블록 순서** (D-PRJ-2, export 실패): 로고·이름·기간 → 한 줄 소개 → 팀원 → 사용 기술 → 기능 소개 → 주요 성과 → 세부 설명 → 전체 회고(위 `data-role`). 팀원·사용 기술 필수, 기능 소개·주요 성과·전체 회고는 기록에 있을 때만.
- **사용 기술**: `## 사용 기술`(없으면 기술 선택·작업에 나온 기술)을 분류별 쉼표 목록으로. **기능 소개**: `## 주요 기능`, 서비스 화면을 옆이나 위에.
- **서비스 화면 배치**: `layoutPrefs.screen`이 `wide`면 기능 소개 위 본문 폭, `side`면 기능 목록 왼쪽 + 화면 오른쪽 열(세로형 45~60mm, 정사각형 70~85mm). **가로형(폭/높이 1.3 이상)은 `side`여도 본문 폭.** 값이 없으면 비율로 AI가 정한다.
- **주요 성과**: 측정된 before → after(`.ba`)와 측정 없는 성과(실사용 시작일, 사용자 수, API·PR 수 — 본문 크기 굵게까지)를 함께(D-PRJ-5). 세부 설명에서 다루는 성과도 한 줄 요약. 계산한 개선율 금지.
- **전체 회고**: 작업별 회고를 모두 모아 작업 이름 라벨로(D-PRJ-6). 작업 섹션 아래에 회고를 두지 않는다(검사 없음).

**레이아웃 구현** (D-DES-7·13): 쪽 `layout`은 `.sheet`에 `data-layout="<키>"`, **세부 설명 작업마다** `<section data-role="project-detail" data-layout="<키>">`(키는 `pagePlan.sections[].layout`), `repeatReason`이 있으면 `data-layout-repeat="<이유>"`. 키는 design이 골랐다 — build는 충실히 구현한다(배치 조정은 되지만 키의 핵심 구조는 지킨다). 부품은 `components.css`.

## 4. 이미지와 다이어그램

**이미지 자리** (`imageSlots`)
- `file`이 있는 자리: `portfolio/images/<file>`을 `out/assets/`로 복사. 캡션은 `facts/<slug>.md#이미지`의 문장 그대로.
  `<figure class="shot" data-fact="dms.md#이미지"><img src="assets/apply.png" alt="<캡션>" style="width: <size 폭>"><figcaption><캡션></figcaption></figure>`
- `data-kind`: 로고 `logo`, 대표 화면 `screen` + `data-project="<slug>"`, 측정 화면(Gatling·대시보드·EXPLAIN 결과) `measure`, 그 밖의 화면 캡처 `capture`, 사진 `photo`, 다이어그램 `diagram`.
- **전·후 짝**(D-IMG-2·4): 개선·전환 전·후 두 장은 종류와 상관없이 **같은 쪽에 나란히** `<div class="measure-pair" data-role="measure-pair">`, 두 `<img>`에 같은 `data-pair="<slug>-<작업>"`(`data-kind`는 원래 종류). 비율이 다르면 묶음에 `style="--pair-ratio: <더 세로로 긴 쪽의 폭> / <높이>"`(자르지 않고 남는 자리는 여백). 사이에 화살표를 두지 않는다 — 캡션의 "전"·"후"가 말한다.
- **측정 화면은 증빙**: 한 장은 본문 폭 절반 이하, 묶음은 쪽 높이 30% 이하(측정 화면이 아닌 짝은 상한 없음). 수치는 바로 위 `.ba`가 전달하니 안의 글자가 안 읽힌다고 키우거나 쪽을 나누지 않는다. 안 들어가면 이미지 대신 주변 블록을 옮긴다. 짝은 해당 `.ba` 바로 아래에 두되, 같은 측정인지 facts로 확인하고 다르면 나란히 두지 않는다.
- `capture`는 안의 글자가 읽혀야 한다. "원본의 50% 미만으로 줄어 읽기 어려움"이면 본문 폭까지 키우고, 넘치면 주변 블록을 옮긴다.
- 비율 유지(`height: auto`), 자르지 않는다(`object-fit: cover` 금지 — 일부가 잘려 다른 화면처럼 보인다, D-IMG-3).
- **빈 이미지 자리(점선 박스)를 만들지 않는다**(D-IMG-1). 넣으면 좋을 이미지는 보고에만. 위치는 `placement`(블록 기준) — 쪽을 다시 나누면 블록과 함께 움직인다.

**다이어그램** (아키텍처, 흐름, ERD)
- facts에 구성 요소와 연결이 **명시돼 있을 때만**. 사용자가 준 다이어그램 이미지가 같은 구조면 다시 그리지 않고 쓴다.
- 그리기 전에 **박스 라벨 목록과 화살표 목록**을 보여주고 확인받는다. 하나라도 facts에 없으면 그리지 않는다.
- 인라인 `<svg>`(외부 렌더러는 출력 시점 네트워크·타이밍에 흔들린다), 색은 CSS 변수. 라벨은 인쇄 크기 8pt 이상 — viewBox로 줄면 `font-size`가 커 보여도 작게 찍힌다. 한글 라벨은 본문 폰트(모노는 영문 라벨만).

| 작은 글자(8pt 미만) | `--fs-*`를 안 쓴 곳, `transform: scale`·`zoom` |

| 글자 분포 (`글자 sheet n`) | 크기 단계가 5개 초과이거나 같은 역할이 쪽마다 다른 크기면 고친다(리뷰 에이전트도 본다) |
| 쪽 수 경고 (D-DES-17) | 막지 않는다. 줄일 후보(우선순위 낮은 세부 설명)를 끝 보고에. 쪽 수는 묻지 않는다 |
| 이미지 로드 실패 / 흐릿함 경고 | 경로 수정 / 더 작게 두거나 큰 원본을 달라고 보고에 |

## 5-1. 디자인 고르기 (사용자 결정 D-DES-15)

첫 PDF가 5절을 통과하면 디자인 리뷰 루프 **전에** design의 "1-C. 디자인 고르기"를 한다(실제 쪽 시안으로 전체 스타일·강조색·글꼴·서비스 화면 배치를 묻는다). 고른 테마로 다시 렌더하고(화면 배치가 바뀌면 그 블록 마크업도) 5절을 다시 통과시킨 뒤 5-2로. 머리 띠로 쪽 높이가 줄어 넘치면 5절대로 다시 나눈다. `style.source`가 이미 `user`·`reference`면 건너뛴다.

## 5-2. 디자인 리뷰 루프

**레퍼런스 모드면 돌리지 않는다**(D-DES-16). 보고에 "레퍼런스를 따라 디자인 검사는 하지 않음".

스크립트가 통과한 뒤 **맥락 없는 `design-reviewer`**(`portfolio-harness:design-reviewer`)가 쪽 이미지로 가독성·가시성·내용 이상을 판정한다(D-CHK-1). 스크립트가 못 보는 것(위계 무너짐, 정렬 어긋남, 같은 말 반복, 쪽 사이 수치 불일치, 어색한 빈 공간)을 잡는다. 쓴 쪽이 보면 같은 맹점을 공유하므로 에이전트로 분리한다.

**회차마다**
1. 렌더: `mkdir -p portfolio/review/r<n> && pdftoppm -r 100 -png portfolio/out/portfolio.pdf portfolio/review/r<n>/page`. 그 회차 HTML을 `review/r<n>/index.html`로 보관.
2. **결정 파일**: `portfolio/review/decided.md` = `../../rules/user-decisions.md` 그대로 + `review/log.md`의 "사용자 결정:"·"사용자에게 넘긴 것(→답)" 줄. 회차마다 새로. 없으면 리뷰어가 이미 정한 것(머리글 없음, 쪽마다 다른 레이아웃)을 계속 지적한다.
3. 에이전트 프롬프트에는 **경로만**. 지난 회차에 고친 것, "이건 의도한 것" 같은 설명을 넣지 않는다.
   ```
   pages: <절대경로>/portfolio/review/r<n>/
   outline: <절대경로>/portfolio/out/outline.md
   export: <export.py 출력을 저장한 파일 절대경로>   (채움·글자 분포·역할 경고 포함)
   decided: <절대경로>/portfolio/review/decided.md   (항상 넘긴다)
   ```
4. **검증**: 지적마다 해당 쪽 PNG를 직접 열어 실제로 보이는지 확인한다. 안 보이면 버리고 수를 기록한다.
5. **분류와 처리** — 무엇이 문제인지는 에이전트 판정을, 어떻게 고칠지는 3절을 따른다(에이전트는 design 규칙을 모른다. "섹션 이름을 12pt로" → 섹션 제목은 `--fs-section`으로, 프로젝트 쪽 라벨 열은 없앤다).
   | 분류 | 처리 |
   |---|---|
   | `LAYOUT` `READABILITY` `VISIBILITY` `TYPE` `CONTENT-FIT` | 묻지 않고 고친다. CSS·배치·쪽 나누기만, 문장은 그대로, `--fs-*`·`--space-*` 범위 안. `CONTENT-FIT`은 더 맞는 `layout` 키로 바꾸고 design을 다시 돌려 `pagePlan`에 기록 |
   | `LEAK` (출처 메모·내부 용어) | 묻지 않고 지운다. 새 말을 넣지 않는다 |
   | `NAVIGATION` (제목만 보고 무엇인지 모름) | 묻지 않고: 섹션 제목을 `--fs-section`으로, 라벨 열에 숨은 이름을 제목으로, 헤드라인과 섹션 제목이 겨루면 헤드라인을 뺀다 |
   | `CONTENT` (핵심 문장이 안 보임, 성격 다른 정보가 한 문단, 결과와 설명이 멂, 반복, 표기 혼용, 구성안과 불일치) | 묻지 않고: 반복은 한 곳만, 표기 통일(날짜 `2026.04.27`, 천 단위 쉼표, 문장 끝 마침표), 구성안 갱신. 주장은 바꾸지 않는다 |
   | `CLAIM`, "→ auditor" | 레이아웃이 만든 과장(제한적 테스트 수치를 대표처럼 크게)은 강조를 낮춘다. 사실관계 의심은 고치지 않고 **루프 뒤 audit에**(audit가 물을지 정한다) |
   | "→ 콘텐츠 검토" (정보 없음) | 기록에 있으면 구성안을 고쳐 넣는다(묻지 않음). 없으면 끝 보고에 "더 넣으면 좋은 자료" |
   | `CONSISTENCY` | 같은 역할 요소(제목, 메타, 쪽 번호, 같은 종류 이미지)는 묻지 않고 맞춘다. 목적이 달라 레이아웃이 다른 건 두고, 수치·사실 불일치는 audit에 |
   | 이미 사용자가 답한 것 | 다시 묻지 않는다(`review/log.md` 먼저 확인) |
6. 고친 뒤 5절을 다시 통과시킨다. 통과 못 하는 수정은 되돌린다.
7. `portfolio/review/log.md`에: 회차, 지적 수(심각도별·분류별), 버린 수, 고친 것, 사용자에게 넘긴 것.

**멈춤 조건** (하나라도)
- `HIGH`·`MEDIUM`의 자동 처리 대상(위 표 `LAYOUT`~`CONSISTENCY`) 지적이 0건
- 3회차를 마침
- HIGH+MEDIUM 수가 지난 회차보다 줄지 않음 — 수정이 다른 문제를 만든다는 뜻. 가장 적었던 회차의 HTML로 되돌린다
- 같은 지적(같은 쪽·위치·내용)이 두 회차 연속 — 사용자에게 넘긴다

끝나면 남은 지적(`low`, 넘긴 것)을 보고에 넣고, PNG는 남겨 두고, "디자인 검사 n회, 지적 a → b → c건"처럼 추이를 쓴다.

## 6. 기록과 보고

1. `out/.build.json`:
   ```json
   { "builtAt": "YYYY-MM-DDTHH:MM", "indexSha256": "...", "format": "a4", "pages": 8,
     "checks": { "numbers": "pass", "export": "pass" },
     "review": { "rounds": 2, "findings": [7, 2], "log": "review/log.md" } }
   ```
2. **PDF 전송** (D-FLOW-8): **최종본만 보낸다.** build를 단독으로 불렀을 때만 보고 바로 전에 돌린다. `start` 흐름 안이면 돌리지 않는다 — 아직 감사 전 중간본이고, start가 끝 보고 직전에 한 번 보낸다. 묻지 않는다.
   `python3 <S>/upload.py portfolio/out/portfolio.pdf`
   - 플러그인 루트에 `upload.json`이 있을 때만 간다(없으면 "설정 없음 — 건너뜀"). 같은 PDF는 한 번만. 실패해도 재시도하거나 멈추지 않는다.
   - 디자인 고르기·리뷰 회차의 중간 PDF로는 부르지 않는다. 턴 끝 훅(`hooks/upload_on_stop.py`)은 감사가 끝난 HTML의 PDF만 보낸다(`.build.json`의 `audit` + 같은 `indexSha256`) — 단독 build 결과는 이 단계에서만 간다.
   - 출력 한 줄을 보고 맨 끝에 옮기고, 보냈으면 "완성된 PDF가 테스트 운영자에게 전송됐어"를 덧붙인다.
3. 보고:
   - PDF 경로와 쪽수, 검증 요약(쪽별 채움 %, 남은 여백 경고, `data-sparse-ok` 쪽과 이유, 옮기거나 뺀 블록, 쪽 수 경고면 줄일 후보, 링크 401·403, WARN)
   - **재료 점검 판정**: `부족`이 있었으면 다시 쓰고, 가장 효과가 클 자료 종류를 제안(예: "원인을 찾아 고친 장애 1건과 그 전후 측정")
   - **제외한 사실과 이유** — 근거를 찾으면 넣을 수 있는 것들
   - 디자인 검사: 회차별 지적 추이, 고친 것, 사용자에게 물을 지적(레퍼런스 모드면 "레퍼런스를 따라 디자인 검사는 하지 않음"과 구하지 못해 바꾼 글꼴만)
   - 넣으면 좋을 이미지: 무엇을 어디에(안내는 "이미지 파일을 이 창으로 끌어다 놓아 줘", D-IMG-5)
   - 회고·자기소개에서 맞춤법을 고친 곳(원문과 수정본)
4. 이후 수정 안내: 내용은 facts에서(`interview`·`ingest`), 겉모습은 `design`에서 고치고 다시 build. HTML을 직접 고치면 다음 빌드 때 덮어쓰기 확인을 받는다.
