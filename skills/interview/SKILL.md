# 포트폴리오 인터뷰

> **먼저 읽는다** — 이 스킬을 불러오면 표시되는 기본 디렉터리(`Base directory for this skill`) 기준으로 `../../rules/principles.md`(제품 원칙)와 `../../rules/user-decisions.md`(사용자 결정 원본)를 읽는다. 이 문서의 규칙이 그 둘과 다르면 그 둘이 맞다. 같은 세션에서 이미 읽었으면 다시 읽지 않는다. **둘 중 하나라도 읽지 못하면(파일 없음·읽기 실패) 이 스킬의 작업을 시작하지 않는다** — 어떤 파일을 어느 경로로 찾았는지와 "원칙 문서를 읽지 못해 멈췄다"를 첫 줄에 알리고 끝낸다. 원칙 없이 기억이나 이 문서만으로 대신 진행하지 않는다.

> 사용자에게 말할 때는 `start` 스킬의 "사용자에게 쓰는 말" 표를 따른다. facts·outline·슬롯 같은 내부 이름을 채팅에 그대로 쓰지 않는다.

사용자에게 질문해서 **포트폴리오에 쓸 사실**을 모은다. 결과물은 문장이 아니라 사실 파일이다.
본문 작성은 build 단계가 이 파일만 보고 한다. 그러니 여기서 기록되지 않은 것은 포트폴리오에 들어가지 않는다.

## 절대 규칙

1. **지어내지 않는다.** 사용자가 말하지 않은 수치·인과·기술·역할은 기록하지 않는다. 추측으로 빈칸을 채우지 않는다.
2. **수치는 사용자가 말한 그대로 기록한다.** 반올림, 단위 변환, 배수·퍼센트 계산 결과를 대신 적지 않는다. 계산이 필요하면 원 수치만 남긴다.
3. **따로 일어난 일을 하나로 합치지 않는다.** 서로 다른 이슈나 작업은 각각 별도 항목으로 남긴다. "1차 개선 → 2차 개선"처럼 사용자가 직접 연결하지 않은 서사를 만들지 않는다.
4. **인과는 사용자가 말한 만큼만 기록한다.** "A를 했고 B가 됐다"를 "A 때문에 B가 됐다"로 바꾸지 않는다.
5. **회고·느낀 점·동기는 사용자 표현을 그대로 둔다.** 다듬거나 대신 써주지 않는다.
6. **이 단계에서는 포트폴리오 문장을 쓰지 않는다.**
7. **근거 원문은 훅이 쓴다(D-TXT-6).** 플러그인 훅이 사용자가 보낸 메시지와 질문 도구 답을 `portfolio/sources/interview-log.md`에 그대로 남긴다. 이 파일을 만들거나 고치거나 지우지 않는다. 기록의 수치는 이 원문이나 받은 자료에 있어야 하고, `facts_lint`가 대조한다. 모델이 채팅에 쓴 수치나 질문 문장의 수치는 근거가 아니다 — 사용자가 계산값·환산값을 승인해야 하면(R-EVD-1) **질문 도구 선택지에 그 값을 그대로 넣어** 고르게 한다(고른 답이 원문에 남는다). 채팅으로 "이렇게 쓸게, 괜찮아?"라고 묻고 "응"을 받으면 원문에 수치가 남지 않아 검사를 통과하지 못한다.

## 진행 원칙 — 턴을 아낀다

사용자가 답하는 횟수가 곧 비용이다. **프로필은 1~2턴, 프로젝트 하나는 3~4턴 안에 끝내는 것**을 목표로 한다. 단, 이건 묶어 묻는 방식의 목표이지 멈추는 기준이 아니다. **부족하거나 이상한 부분은 답을 받을 때까지 묻는다**(아래 "끝까지 묻는다", D-FLOW-9). 턴 수를 아끼려고 빈칸을 남기고 넘어가지 않는다.

- **묶어서 묻는다.** 선택형은 `AskUserQuestion` 한 번에 최대 4문항까지 넣는다. 서술형은 **빈칸 템플릿 하나**로 한꺼번에 받는다. 질문 하나 보내고 답 받고 또 하나 보내는 식으로 하지 않는다.
- **번호 목록으로 묻지 않는다.** "1. … 2. …"로 물으면 사용자가 "2번"처럼 답해서 오히려 되묻게 된다. 템플릿의 `항목:` 칸을 채우게 한다.
- **먼저 쏟아내게 하고, 빈 곳만 묻는다.** 프로젝트는 항목별로 하나씩 묻지 않는다. 자유롭게 다 말하게(또는 문서를 붙여넣게) 한 다음, 거기서 사실을 뽑고 **빠진 핵심만** 한 번에 묻는다.
- **기록 확인 멘트를 하지 않는다.** "~로 기록했어"를 매 턴 말하지 않는다. 파일에는 바로 저장하고, 단계가 끝날 때 요약 한 번만 보여준다.
- **선택 항목은 한 번만 묻는다.** 연락처, 링크, 한 줄 소개는 템플릿에 넣어 한 번 묻고, 비워서 보내면 생략으로 처리한다. 다시 확인하지 않는다. (수상·자격증·활동의 날짜, 프로젝트 내용의 빈 곳은 선택 항목이 아니다 — 끝까지 묻는다.)
- **다음 단계로는 묻지 않고 넘어간다.** "시작할까?"를 묻지 않는다.
- 사용자가 문서·스크린샷·링크를 주면 `ingest` 절차로 처리한다.
- 이전 진행 상태(`portfolio/interview-state.md`)가 있으면 읽고 다음 단계부터 이어간다. 없으면 `portfolio/facts/`를 만들고 바로 1단계 질문을 보낸다. 진행 방식 설명은 한 줄이면 된다.

## 1단계 — 프로필 (1~2턴)

**턴 1**: `AskUserQuestion` 한 번에 묻는다.
- 직군: 백엔드 / 프론트엔드 / 모바일 / 풀스택·인프라
- 경력 단계: 학생·취준 / 신입(1년 미만) / 1~3년 / 3년 이상

지원 목표는 묻지 않는다. **스타트업으로 고정**이다(사용자 결정 2026-10-09, `CLAUDE.md` "Target Hiring Market"). `profile.md`의 `## 직군·경력`에 `지원 목표: 스타트업 (하네스 고정)`으로 적는다.

같은 메시지에 서술형 템플릿을 붙인다.
```
이름:
한 줄 소개: (비우면 facts로 후보를 만들어 줄게)
자기소개: (3~5문장, 지금까지 한 일 중심. 비우면 facts로 초안을 만들어 줄게)
전화번호: (비우면 생략)
이메일: (비우면 생략)
링크: (LinkedIn, GitHub, 블로그 등. 비우면 생략)
주로 쓰는 기술: (예: Spring Boot, JPA, MySQL, Redis)
수상·자격증: (한 줄에 하나씩 "이름 | 날짜 | 수여 기관". 날짜는 꼭 적어줘. 기관은 몰라도 돼. 없으면 "없음")
  예) OO 해커톤 2위 | 2025.08.22 | OO재단
활동: (교내 활동, 대회 참가, 기업 연계 프로젝트, 동아리, 대외활동, 교육 프로그램 등 전부. 한 줄에 하나씩
       "이름 | 종류 | 기간 또는 날짜 | 한 일 한 줄". 기간이나 날짜는 꼭 적어줘. 없으면 "없음")
  예) 교내 해커톤 운영진 | 교내 | 2025.03 ~ 2025.06 | 참가자 접수 페이지 개발
  예) OO기업 연계 프로젝트 | 기업 프로젝트 | 2025.11.02 | 사내 대시보드 API 구현
기존 자료: (비우면 생략) 이미 정리해 둔 문서나 링크가 있으면 꼭 적어줘. 그걸 먼저 읽고 질문을 줄일게.
  예) Notion 페이지, 블로그 글, GitHub, 기존 포트폴리오·이력서 파일, 개인 위키·노트 폴더, 발표 자료
```
- 숙련도 점수(별점, 퍼센트)는 묻지 않는다. 기술을 어디에 썼는지는 프로젝트 단계에서 자연스럽게 채운다.
- 답을 `portfolio/facts/profile.md`에 저장한다. 파일 맨 위에 frontmatter `---\nkind: profile\n---`를 둔다(재료 점검이 프로젝트와 구분한다). 섹션은 `## 기본 정보`, `## 한 줄 소개`, `## 자기소개 (원문 유지)`, `## 연락처`, `## 주력 기술`, `## 활동`, `## 수상·자격증`으로 나눈다. 1쪽(표지)이 이 순서로 만들어진다.
- **수상·자격증과 활동은 날짜가 필수다**(D-P1-4). 날짜가 빠진 줄이 있으면 그 줄들만 모아 "언제였는지 알려줘"로 다시 묻고, 받을 때까지 넘어가지 않는다. 날을 모르면 연·월까지만 받는다. "날짜는 안 적어도 돼"라고 말하지 않는다. 기록 형식:
  - `- <이름> | <날짜 또는 기간> | <수여 기관 또는 "(기관 미기재)"> [src: interview]` (수상·자격증)
  - `- <이름> | <종류> | <YYYY.MM ~ YYYY.MM 또는 YYYY.MM.DD> | <한 일> [src: interview]` (활동)
  - 없다고 하면 `- 수상·자격증 없음` / `- 활동 없음`. 기간이 있는 교육·연수 프로그램을 수상 칸에 적었으면 활동으로 옮길지 한 번 묻는다
- **활동은 빠뜨리지 않는다.** 비워서 보냈으면 "교내 활동, 대회, 기업 프로젝트, 동아리 같은 것도 없어?"를 한 번 묻고, 없다고 하면 `- 활동 없음`으로 기록한다. `facts_lint`가 `## 활동`이 없으면 오류를 낸다.
- 자기소개를 직접 썼으면 회고처럼 **원문 그대로** 인용으로 저장한다. build는 맞춤법·띄어쓰기만 고칠 수 있다.
- 수상·자격증·활동은 사용자가 적은 이름·기관·날짜 그대로 기록한다. 등급·순위·역할이 없으면 지어내지 않는다.
- 한 줄 소개·자기소개를 비웠어도 다시 묻지 않는다. build가 outline 단계에서 facts로 만든 후보(한 줄 소개)와 초안(자기소개)을 제시한다.
- **기존 자료를 적었으면 2단계로 가기 전에 `ingest`의 "자료 묶음" 절차로 훑는다.** 이미 정리된 자료가 있는데 처음부터 기억으로 답하게 하면, 사용자가 이미 기록해 둔 장애·측정 사례가 빠진다. 훑은 결과는 2단계 프로젝트 목록과 3단계 턴 A를 미리 채우는 데 쓴다.

## 2단계 — 프로젝트 목록 (1턴)

템플릿 하나로 전부 받는다. **여러 개를 받는다는 것을 템플릿 위에 문장으로 먼저 쓴다.** 예시가 한 줄뿐이면 사용자는 프로젝트 하나만 쓰는 칸으로 읽는다(2026-10-08 E2E에서 실제로 그렇게 읽혔다).
```
포트폴리오에 넣고 싶은 프로젝트를 전부 적어줘. 한 줄에 하나씩, 몇 개든 괜찮아.
(어떤 걸 깊게 다룰지는 다음에 같이 골라.)
프로젝트마다 정리해 둔 문서나 링크(Notion, 블로그 글, GitHub, 발표 자료, 회고 문서 등)가 있으면 꼭 같이 줘.
그걸 먼저 읽고 내가 이미 아는 건 다시 묻지 않을게.

이름 | 시작 | 종료 (운영·개발 중이면 비워) | 상태 (운영 중/개발 중/종료) | 한 줄 설명 | 개인/팀/회사 | 팀 구성 | 링크(선택)
예) 쇼핑몰 API | 2025.03 | 2025.06 | 종료 | 중고거래 서비스 | 팀 | 백엔드2 프론트2 |
예) 주소 검색 | 2025.07 |  | 운영 중 | 우편번호 자동완성 | 개인 | 혼자 | github.com/...
예) 동아리 출석 앱 | 2024.09 |  | 개발 중 | 출석 체크 | 동아리·대회 | 백엔드1 앱1 |
```
- 예시는 사용자의 실제 프로젝트와 겹치지 않는 가상 예시로 둔다. 기존 자료에서 찾은 실제 프로젝트는 예시가 아니라 "미리 채운 줄"로 따로 보여준다.
- 사용자가 한 줄만 보냈으면 "다른 프로젝트는 없어? 없으면 이것만으로 갈게"를 **한 번만** 묻는다.
- 기존 자료에서 프로젝트를 찾았으면 템플릿에 **미리 채워서** 보여주고, 고칠 것만 고치게 한다. 기존 포트폴리오에 있던 프로젝트가 목록에서 빠지면 "이번엔 뺄 건지" 한 줄로 확인한다. 말없이 빠지게 두지 않는다.
- 받은 즉시 프로젝트마다 `portfolio/facts/<slug>.md`를 만든다. slug는 영문 소문자와 하이픈만 쓴다.
- **프로젝트 이미지 요청 (필수)**: 목록을 받은 같은 응답 끝에, 프로젝트마다 **두 장**을 요청한다(사용자 지시 2026-10-08). **사용자가 폴더에 넣게 하지 않는다. 이 채팅으로 직접 받는다**(D-IMG-5). 기다리지 않고 바로 3단계로 간다.
  ```
  프로젝트마다 이미지 두 장이 꼭 필요해: ① 로고 ② 서비스 화면(실제 캡처든 목업이든 괜찮아).
  이미지 파일을 이 터미널 창으로 끌어다 놓아 줘. 어느 프로젝트의 무엇인지 한 마디만 붙여 주면 돼.
    예) [파일 끌어다 놓기] dms 로고, [파일 끌어다 놓기] dms 서비스 화면
  이미지 링크(URL)를 줘도 돼. 성능 측정 화면(Gatling 결과 등)이나 구조도가 있으면 같이 줘.
  로고가 없거나 화면을 보여줄 수 없는 프로젝트면 "dms 로고 없음"처럼 말해줘.
  ```
  - 로고는 svg·png 모두 받는다. 서비스 화면은 실제 캡처, 디자인 툴 목업, 휴대폰 화면 모두 된다.
  - 받은 이미지는 AI가 `portfolio/images/<slug>/`로 **직접 복사한다**: 경로면 `cp`, URL이면 `curl -L -o`. 원본 파일 이름을 유지하고, 같은 이름이 있으면 뒤에 `-2`를 붙인다. 그다음 `ingest`의 "이미지" 절차(열어 보고 종류·캡션 확인)를 한다.
  - **클립보드로 붙여넣은 이미지**(캡처 후 Ctrl+V, 채팅에 `[Image #1]`로만 보임)는 화면에서 볼 수는 있어도 파일이 없어 PDF에 넣을 수 없다. "보이긴 하는데 파일로 저장할 수가 없어. 캡처를 파일로 저장해서 끌어다 놓아 줘"라고 다시 요청한다. 본 내용을 기록에 쓰는 것은 괜찮다(무엇을 보여주는지 캡션 확인 등).
  - 사용자가 "없음"이라고 하면 해당 프로젝트 `## 이미지`에 `- 로고 없음 [src: interview]`(또는 `서비스 화면 없음`)으로 기록한다. 그 뒤로는 다시 요청하지 않는다.
  - 3단계 중에도 사용자가 이미지를 주면 그 자리에서 복사하고 이미지 절차를 한다. 4단계 마무리까지 로고·서비스 화면이 없는 프로젝트가 있으면 그것만 다시 요청한다.
- 프로젝트가 2개 이하면 전부 심층으로 다룬다. 3개 이상일 때만 `AskUserQuestion`(multiSelect)으로 심층 대상을 고르게 한다. 스타트업 채용 관점(실제로 만들고 운영한 것, 문제를 찾아 해결한 경험, 본인 기여도)과 트러블슈팅 유무로 추천을 붙인다.

## 3단계 — 프로젝트 심층 (프로젝트당 3~4턴)

### 턴 A — 쏟아내기
기존 자료에서 이 프로젝트의 사실을 이미 가져왔으면, 가져온 것을 짧게 보여주고 "여기에 없는 것만" 적게 한다.
아래 안내를 보내고 자유롭게 답하게 한다. 항목별로 쪼개 묻지 않는다.
```
<프로젝트명>에 대해 생각나는 대로 다 적어줘.
정리해 둔 문서나 링크(Notion, 블로그, PR, 회고·장애 보고서, 발표 자료)가 있으면 꼭 줘. 그걸 먼저 읽고 빈 곳만 물을게.
- 무슨 서비스고 누가 쓰는지
- 주요 기능 3~5개 (사용자가 이 서비스로 할 수 있는 것)
- 이 프로젝트에서 쓴 기술 (언어, 프레임워크, DB, 인프라 등)
- 본인이 맡은 부분
- 기술을 고른 이유 (다른 후보가 있었다면 그것도)
- 기억에 남는 작업이나 트러블슈팅 (무슨 일 → 원인 → 해결 → 결과)
- 다시 한다면 다르게 할 점
```

### 턴 B — 빈 곳만 한 번에
턴 A의 답을 facts에 기록한 뒤, 아래 **핵심 빈칸**만 골라 한 메시지에 묻는다. 템플릿 형식으로 보낸다.

| 우선순위 | 핵심 빈칸 | 묻는 이유 |
|---|---|---|
| 필수 | 사용 기술, 주요 기능 (턴 A 답에 없을 때) | PDF의 프로젝트 구조(사용 기술 → 기능 소개)에 들어가는 칸이다. 사용 기술이 없으면 PDF 만들기가 실패한다 |
| 0 | **트러블슈팅이 하나도 없음** (상황→원인→해결→결과가 다 있는 작업 0개) | 개발자 포트폴리오(특히 백엔드)에서 면접관이 가장 오래 보는 부분이다. 없으면 결과물이 작업 목록이 된다 |
| 1 | 수치의 측정 방법 (도구, 조건, 전후 같은 환경인지) | 면접 1순위 질문. 없으면 본문에서 빠진다 |
| 2 | "우리가"라고 한 부분 중 본인 몫 | 역할 부풀리기 방지 |
| 3 | 원인을 어떻게 확인했는지 | 인과를 단정한 경우 |
| 4 | 붙어서 말한 작업들이 같은 이슈인지 | 다른 작업을 한 줄로 이으면 안 된다 |
| 5 | 안 쓴 대안이 "못 써서"인지 "안 골라서"인지 | 면접에서 방어 방향이 반대다 |
| 6 | 무용담("새벽까지") 뒤에 바꾼 구조 | 열정담을 개선담으로 |

- 한 번에 **최대 5개**까지 묻는다. 우선순위가 낮은 건 버리지 않고 **다음 턴에 이어서** 묻는다.
- 위 표 말고도 다음은 모두 빈칸으로 본다: 앞뒤가 안 맞는 내용(날짜·인원·수치가 서로 다름), 뜻이 애매한 문장("최적화했다", "개선했다"만 있고 무엇을 어떻게 했는지 없음), 기능·기술이 개요와 안 맞음, 역할이 불분명함, 결과 없이 끝난 작업.
- 0번은 이렇게 묻는다. 템플릿으로 하나만 받으면 된다.
  ```
  면접에서 제일 오래 보는 게 "문제를 어떻게 찾아서 고쳤는지"야. 아래 중 하나라도 있으면 적어줘. 장애 보고서·PR·위키 글이 있으면 그걸 줘도 돼.
  (장애·버그·느린 API·비용·배포 문제 중 원인을 찾아서 고친 것)
  무슨 일:
  원인과 어떻게 확인했는지:
  해결:
  결과와 잰 방법:
  ```
  없다고 하면 `빈칸`에 "트러블슈팅 없음"으로 남기고 넘어간다.
- 질문은 추궁이 아니라 면접 대비로 들리게 쓴다. 예: "면접에서 이 숫자를 어떻게 쟀는지 물어볼 가능성이 높아. 측정 도구랑 조건 기억나?"
- 링크처럼 없어도 내용이 달라지지 않는 것만 한 번 묻고 `빈칸`에 남긴다. 날짜·기간은 빈칸으로 두지 않는다.

### 턴 C~ — 끝까지 묻는다 (D-FLOW-9)
턴 B의 답에도 부족하거나 이상한 부분이 남았으면 **답을 받을 때까지 계속 묻는다.** 한 턴에 최대 5개, 남은 것은 다음 턴에.
- **끝나는 조건은 사용자의 말뿐이다.** 사용자가 "모름", "기억 안 나", "없어", "그건 넘어가"처럼 직접 말한 항목만 `모름`·`근거없음`·`없음`으로 기록하고 그 항목을 닫는다. AI가 "이 정도면 됐다", "턴이 많아졌다"고 판단해 넘기지 않는다.
- 같은 걸 같은 말로 반복해서 묻지 않는다. 앞 답이 어디가 부족했는지 짚고, 답하기 쉬운 형태(예시, 선택지, 범위)로 바꿔 묻는다. 예: "1,225ms를 어떻게 쟀는지 기억 안 나면, 도구 이름(Gatling·k6·JMeter·직접 측정)만이라도 알려줘."
- 답이 앞서 말한 것과 다르면 둘을 나란히 보여주고 어느 쪽이 맞는지 묻는다(`충돌`로 남겨 두지 않는다).
- 매 턴 끝에 남은 항목 수를 한 줄로 보여준다(예: "DMS에서 남은 질문 3개"). 사용자가 언제 끝나는지 알 수 있게.

### 턴 D — 프로젝트 요약
해당 프로젝트의 facts를 짧은 표로 보여준다(작업 n개, 근거없음 n개, 빈칸). 그리고 같은 메시지에서 다음 프로젝트의 턴 A 안내를 바로 보낸다.

### 기록 규칙
- 답을 받을 때마다 facts 파일에 바로 저장한다. 말로 확인하지 않는다.
- 한 답에 작업이 여러 개 섞여 있으면 이슈·날짜·대상 기준으로 나눠 별도 항목으로 기록한다. 같은 작업인지 애매하면 턴 B의 4번 질문으로 확인한다.
- 회고·다시 한다면 답은 `## 회고 (원문 유지)`에 원문 그대로 인용한다.

## 사실 파일 형식

`portfolio/facts/<slug>.md`:

```markdown
---
project: <이름>
slug: <slug>
start: <YYYY.MM>
end: <YYYY.MM | 비움>          # 운영 중·개발 중이면 비운다
status: 운영 중 | 개발 중 | 종료   # PDF 기간 줄은 "start ~ end" 또는 "start ~ status"로 만들어진다
type: 개인 | 팀 | 회사 | 동아리·대회
team: <예: 백엔드 2, 프론트 2, 디자인 1>
links: [<url>, ...]
depth: deep | shallow
---

## 개요
- <사실> `[src: interview]`
- 월 사용자 약 300명 `[src: interview] [status: 근거없음 — 측정 방법 모름]`

## 역할
- 본인: <...> `[src: interview]`
- 팀: <...> `[src: interview]`

## 사용 기술
- 언어·프레임워크: <...> / DB: <...> / 인프라: <...> `[src: interview]`

## 주요 기능
- <사용자가 이 서비스로 할 수 있는 것> `[src: interview]`

## 기술 선택
### <기술>
- 이유: <...> `[src: interview]`
- 대안: <...> / 안 고른 이유: 선택 | 불가 — <근거>

## 작업
### <짧은 제목>
- 상황: ...
- 발견: ...
- 원인: ... / 확인 방법: ...
- 해결: ...
- 결과: ... / 측정: <도구, 조건, 전후 동일 환경 여부>
- 근거: <PR/이슈/파일>
`[src: interview, doc:incident-0812.md]`

## 이미지
- <images/ 안의 파일명> | <로고 | 서비스 화면 | 화면 캡처 | 사진 | 측정 화면 | 다이어그램> | <캡션: 무엇을 보여주는지, 사용자가 확인한 문장> `[src: interview]`
- 로고 없음 `[src: interview]`   ← 사용자가 없다고 확인한 경우만

## 회고 (원문 유지)
> <사용자 답 그대로>

## 빈칸
- [ ] <아직 못 채운 항목과 이유>
```

**출처 태그**: `interview`(인터뷰 답), `doc:<portfolio/sources/ 안의 파일명>`(받은 자료, `ingest`가 보관), `link:<url>`(사용자가 준 링크, 내용은 읽지 않음)
**상태 태그** (확인됨이면 생략):
- `근거없음`: 수치나 주장은 있는데 측정이나 확인 방법이 없음
- `모름`: 사용자가 기억하지 못함
- `충돌`: 인터뷰 답과 문서 내용이 다름. 두 값을 모두 적고 사용자에게 확인한다

## 진행 상태 파일

`portfolio/interview-state.md`:

```markdown
- stage: profile | projects | deep:<slug> | wrapup | done
- deep_targets: [<slug>, ...]
- done: [<slug>, ...]
- updated: <YYYY-MM-DD>
```

## 4단계 — 마무리 (1턴)

0. **기록 형식 검사**: `python3 <build 스킬의 scripts>/facts_lint.py portfolio/facts --images portfolio/images --cache portfolio/.facts_lint.json`. `ERROR[수정]`은 "고치는 법"대로 이 자리에서 고친다(묻지 않음). `ERROR[확인]`(로고·서비스 화면 없음, 상태·종료일, 사용 기술 전무, 자료끼리 다른 값, 사용자가 한 말·받은 자료에 없는 수치)은 추측해서 채우지 않고 2번 질문과 같은 메시지에서 묻는다. WARN 중 `사용 기술`·`주요 기능`이 비었으면 한 번 묻는다.
1. 재료 점검 표를 보여준다: `python3 <build 스킬의 scripts>/facts_stats.py portfolio/facts`의 출력 그대로.
   - `부족` 판정 프로젝트가 있으면 무엇이 비었는지(세부 줄)를 보여주고 그 빈 곳을 3단계 "끝까지 묻는다"대로 다시 묻는다. 넣으면 좋을 자료 종류도 함께 제안한다. 사용자가 자료를 주면 `ingest`로 처리한다. 사용자가 "없어", "넘어가"라고 한 항목만 그대로 진행한다. 이 질문은 같은 메시지에서 2번 충돌 질문과 함께 한다.
2. `충돌`이 있으면 이 자리에서 한 번에 묻는다.
3. `근거없음` 수치는 build 때 본문에서 빠진다고 한 줄로 알린다.
4. `interview-state.md`의 stage를 `done`으로 바꾸고, **묻지 않고 바로 `design`으로 넘어간다.**
