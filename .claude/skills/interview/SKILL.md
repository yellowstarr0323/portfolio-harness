# 인터뷰 (interview)

**먼저 읽는다**: `../../../rules/principles.md`. 같은 세션에서 읽었으면 다시 읽지 않는다.

말투는 존댓말(…해요). 질문은 **빈칸 템플릿 하나**로 한꺼번에 받는다. 한 칸씩 따로 묻지 않는다. 비운 선택 항목은 생략으로 처리하고 다시 묻지 않는다.

`portfolio/reference.md`가 있으면(레퍼런스 있음) 아래 템플릿 대신 **reference.md의 "인터뷰에서 받을 항목"**으로 같은 순서(개인 정보 → 프로젝트 목록 → 프로젝트 상세)의 템플릿을 만든다. 레퍼런스에 없는 항목은 묻지 않는다.

## 1. 개인 정보 (1턴)

```
이름:
직무 분야: (프론트엔드 / 백엔드 / DevOps / 앱 / 임베디드 / AI / 풀스택 / 게임 중 하나)
전화번호: (비우면 생략)
이메일: (비우면 생략)
링크: (GitHub, 블로그, LinkedIn 등. 비우면 생략)
한 줄 소개: (비우면 인터뷰 내용으로 제가 초안을 써 드려요)
학력: (비우면 생략)
수상·자격증: 이름 | 날짜 | 주최·발급 기관 (비우면 생략)
활동: 이름 | 기간 | 한 일 (동아리·대외활동·교육 등, 비우면 생략)
```

저장: `portfolio/profile.md`

직무 분야는 위 8개 중 하나로 받는다. 목록에 없는 답(예: "서버 개발", "iOS")이면 가장 가까운 분야를 제안하고 맞는지 한 번 확인한다. 포트폴리오 1쪽에는 "<분야> 개발자"(예: 백엔드 개발자)로 쓴다.

## 2. 프로젝트 목록 (1턴)

```
포트폴리오에 넣을 프로젝트를 한 줄에 하나씩 적어 주세요.
이름 | 한 줄 소개 | 팀 구성 | 기간 | 기술 스택 | 링크(GitHub·배포 주소, 선택)
예) 스터디 매칭 | 관심사가 같은 스터디원을 찾아주는 웹 서비스 | 개인 | 2025.07 ~ 운영 중 | TypeScript, Next.js, Supabase | github.com/...
예) 동아리 출석 앱 | 출석 체크 앱 | 백엔드 1, 앱 1 | 2024.09 ~ 2024.12 | Java, Spring, Flutter |
```

저장: 프로젝트마다 `portfolio/projects/<영문-슬러그>.md`

## 3. 프로젝트 상세 (프로젝트마다 1턴, 여러 개를 한 번에 받아도 된다)

```
<프로젝트 이름>에서 맡은 역할과 직접 수행한 작업을 자유롭게 설명해 주세요.
- 맡은 역할:
- 수행한 작업: (기능 개발, 문제를 해결한 경험, 성능 개선, 설계 등 기억나는 대로)
정리해 둔 자료가 있으면 링크로 주셔도 괜찮아요. Notion, velog, 블로그 글, GitHub README·PR 모두 돼요.

이미지도 꼭 필요해요(프로젝트마다).
- 프로젝트 로고: 1장
- 프로젝트 화면 또는 동작 화면: 1장 이상 (스크린샷, 동작 GIF 등)
이미지 파일을 이 창으로 끌어다 놓거나 파일 경로를 적어 주세요. 이미지 주소(URL)도 돼요.
```

## 프로젝트 이미지 (필수)

프로젝트마다 **로고 1장 + 프로젝트 화면(또는 동작 화면) 1장 이상**, 합쳐서 2장 이상을 사용자에게 받는다. 사용자가 준 이미지만 쓴다. 저장소 README나 웹에서 찾아 대신 쓰지 않는다.
- 받으면 바로 복사한다: `portfolio/images/<슬러그>/logo.<확장자>`, `screen-1.<확장자>`, `screen-2.<확장자>` … (경로면 `cp`, URL이면 `curl -L -o`). 로고는 하나만 둔다. 화면마다 무엇을 보여주는지 기록 파일 `## 이미지`에 한 줄씩 적는다.
- 받은 파일을 Read로 열어 이미지가 맞는지(로고인지, 화면인지) 확인한다. 열리지 않거나 다른 이미지면 그 턴에 알린다.
- 대화창에 붙여넣은(Ctrl+V) 이미지는 파일로 저장할 수 없다. 그렇게 받았으면 "붙여넣은 이미지는 파일로 저장되지 않아요. 파일을 이 창으로 끌어다 놓거나 경로를 적어 주세요"라고 다시 부탁한다.
- **필수다.** 빠진 프로젝트가 있으면 4단계 질문과 같이 계속 부탁한다. "모르겠어요"로 넘어가는 항목이 아니다. 로고가 없다고 하면 "서비스 아이콘, 앱 아이콘, 팀에서 쓰던 대표 이미지도 괜찮아요"라고 안내한다.
- 확인: `python3 <이 스킬 디렉터리>/scripts/check_images.py portfolio` — `모두 있음`이 나와야 인터뷰를 끝낼 수 있다.

## 4. 이해될 때까지 묻기

받은 설명과 자료를 **다 읽은 뒤** 묻는다. 읽기 전에 묻지 않는다.

- **레퍼런스 없음**: 이해되지 않는 부분이 남아 있는 동안 **계속 묻는다.** 다 이해되면 design으로 간다.
  - 매 턴 남은 질문을 프로젝트별로 묶어서 한 번에 보낸다. 한 턴에 하나씩 묻지 않는다.
  - 답을 받으면 기록을 고치고, 그 답 때문에 새로 생긴 모호한 점만 다음 턴에 묻는다. 이미 답한 것을 다시 묻지 않는다.
  - 사용자가 "모르겠어요"·"기억 안 나요"·"넘어가 주세요"라고 한 항목은 `(모름)`으로 적고 더 묻지 않는다.
  - 이해되지 않는 부분의 예: 무슨 서비스인지·누가 쓰는지 불분명, 본인이 한 일과 팀이 한 일이 섞임, 기술 용어나 줄임말의 뜻, 작업 순서·인과(무엇 때문에 무엇을 했는지), 자료와 설명이 서로 다름, 아래 목록의 빈 곳
- **레퍼런스 있음**: 아래가 비어 있으면 **한 번에 묶어서 한 번만** 묻는다. 답하지 않은 칸은 비운 채로 진행하고 다시 묻지 않는다.

빈 곳 목록(프로젝트마다):
- 문제를 해결한 경험이 있는데 **원인**이나 **결과**가 없음
- 개선했다는데 **수치**(전·후 값)가 없음. 있으면 측정 조건(도구·환경)도 같이
- 실제 사용 여부·사용자 수·반응
- 기술이나 설계를 고른 **이유**
- 이 프로젝트에서 배운 점

질문은 구체적으로: "응답 속도를 개선했다고 하셨는데, 개선 전·후 값이 기억나세요? 어떤 도구로 쟀는지도 알려 주세요."

## 링크와 자료

링크를 받으면 **그 턴에** 연다(WebFetch, GitHub 저장소는 `git clone --depth 1`이나 raw 파일).
- 읽었으면 원문을 `portfolio/sources/<이름>.md`에 저장하고(첫 줄에 출처 URL), 거기서 사실을 뽑는다. 사용자에게 "읽었어요"를 따로 말하지 않는다.
- **열리지 않거나 내용을 읽을 수 없으면**(404, 로그인 필요, 비공개, 빈 페이지, 내용이 렌더링되지 않음) 그 턴의 다음 질문과 같이 바로 알린다:
  "`<주소>`는 <이유>로 열리지 않아 읽지 못했어요. 주소나 공개 설정을 확인해 주세요. 어려우면 내용을 복사해서 붙여넣어 주셔도 돼요."
- 주소를 추측해서 고치거나, 비슷한 다른 페이지를 대신 읽지 않는다.
- 포트폴리오에 넣을 링크(프로필·프로젝트 링크)가 열리지 않으면 같은 방식으로 알리고, 사용자가 그대로 두라고 하면 둔다.

## 기록 형식

사실마다 출처를 붙인다: `(출처: 사용자)` 또는 `(출처: <sources 파일명>)`. 사용자 말을 문어체로 정리해도 되지만 사실(누가·무엇을·얼마나)은 바꾸지 않는다. 모르는 값은 비우고 `(모름)`이라고 적는다.

```markdown
# <프로젝트 이름>
- 한 줄 소개: … (출처: 사용자)
- 팀 구성: … / 기간: … / 기술 스택: … / 링크: …

## 역할
- …

## 작업
### <짧은 제목>
- 무엇을: …
- 문제·원인: … (있으면)
- 해결: …
- 결과: … (수치는 측정 조건과 함께)
- 출처: …

```

## 끝나면
`check_images.py`가 `모두 있음`이어야 끝난다. 그다음 `portfolio/state.md`의 `interview: done`, `stage`를 다음 단계로 바꾼다(레퍼런스 있음 → build, 없음 → design). 인터뷰 요약을 3~5줄로 한 번 보여주고 바로 다음 단계로 간다.
