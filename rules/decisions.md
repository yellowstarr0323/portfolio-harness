# 구조 결정 (rebuild, 2026-10-11)

하네스를 처음부터 다시 짠 기준. 사용자가 직접 정했다. 바꿀 때는 이 문서부터 고친다.

| 항목 | 결정 |
|---|---|
| 흐름 | 기존 포트폴리오 질문 → (있음) 리뷰 후 선택 / (없음) 레퍼런스 질문 → (있음) 레퍼런스 분석 → 인터뷰 → PDF / (없음) 인터뷰 → 디자인 추천 → PDF |
| 기존 포트폴리오 | 맨 처음에 "이미 만들어 둔 포트폴리오가 있나요?"를 묻는다. PDF 또는 웹 URL(Notion 등, `url_to_pdf.py`로 PDF로 만듦, 글이 거의 없으면 실패)로 받는다. portfolio-reviewer에 그 PDF 경로만 넘겨 리뷰하고(`review/existing-review.md`, 훅 전송 대상 아님) 결과를 보여준 뒤 선택: 고쳐서 새로(디자인 유지 = 기존 PDF를 레퍼런스로) / 내용만 가져오고 디자인 새로 / 여기서 끝. 새로 만들 때는 기존 내용으로 인터뷰 템플릿을 채우고 리뷰의 [질문]을 인터뷰에서 같이 묻는다(10-12) |
| 레퍼런스 있음 | 레퍼런스를 분석해 구성 요소를 정리하고, 인터뷰에서 그 항목을 묻는다. 디자인은 레퍼런스를 따른다 |
| 디자인 추천 | 레퍼런스가 없을 때만, 인터뷰가 끝난 뒤 내용을 보고 AI가 시안 2~3개를 매번 새로 설계해 추천한다. 정해진 테마 없음 |
| 직무 분야 | 프론트엔드, 백엔드, DevOps, 앱, 임베디드, AI, 풀스택, 게임 중 하나를 고른다(10-11) |
| 개인 정보 | 이름, 직무 분야, 전화번호, 이메일, 링크, 한 줄 소개, 학력, 수상·자격증, 활동 |
| 프로젝트 목록 | 이름, 한 줄 소개, 팀 구성, 기간, 기술 스택, 링크 |
| 프로젝트 상세 | 맡은 역할과 수행한 작업. Notion·velog 등 다른 사이트 자료도 받는다 |
| 프로젝트 이미지 | 필수. 프로젝트마다 로고 1장 + 프로젝트 화면(동작 화면) 1장 이상을 사용자에게 받는다. 빠지면 인터뷰를 끝내지 않는다(check_images.py)(10-11) |
| 빈 곳 질문 | 받은 설명과 자료를 다 읽은 뒤 묻는다. 레퍼런스 없음: 이해되지 않는 부분은 이해될 때까지 계속 묻고 그다음 design으로 간다(10-11). 레퍼런스 있음: 한 번만 묶어서 묻는다. 모른다고 한 항목은 더 묻지 않는다 |
| 링크·자료 | 열리지 않거나 읽을 수 없으면 그 턴에 사용자에게 알리고 확인을 부탁한다 |
| 말투 | 사용자에게는 존댓말(…해요). 포트폴리오 본문은 문어체 |
| 스킬 구성 | start(유일한 진입점) / interview / design / build |
| Codex 지원 | 같은 폴더·같은 브랜치에서 Claude Code와 Codex CLI를 둘 다 지원한다. 스킬은 `.agents/skills` 심볼릭 링크로 공유, `AGENTS.md`·Codex 리뷰어 TOML은 `scripts/sync_codex.py`가 Claude 쪽 원본에서 만든다. 훅은 같은 스크립트를 `.codex/hooks.json`에서 부른다(10-11, Codex 실제 실행은 미검증) |
| 배포 방식 | 플러그인이 아니라 폴더 방식. 사용자는 git clone → 그 폴더에서 `claude` 실행. 스킬·에이전트·훅은 `.claude/` 아래에 두고 Claude Code가 자동으로 읽는다. 마켓플레이스 파일은 없앴다(10-11) |
| 면접관 평가 | PDF가 나오면 portfolio-reviewer 에이전트가 PDF만 보고 면접관 관점 6개 기준(문제 해결 과정, 결과의 구체성·근거, 대안 비교, 직무 역량, 30초 파악, 오류·모순. 기술 원리·선택 이유와 본인 작업 명확성은 10-11에 뺌)으로 1~5점 평가한다. 개선안은 새 사실을 지어내지 않고 확인 질문으로 낸다. 결과는 loop의 입력이 된다(10-11) |
| 재사용 | 기존 하네스에서는 PDF 생성만 가져왔다(make_pdf.py: HTML→PDF, 쪽 넘침·깨진 이미지 확인) |
| 검사 반복(loop) | 최대 3회. 매 회차 portfolio-reviewer가 PDF만 보고 지적 → [수정]은 알아서 고치고 고친 것만 알림, [질문]은 전부 요약해 사용자에게 묻고 답을 반영 → PDF 다시 만들기. 지적이 0개면 끝. 사용자가 그대로 두기로 한 지적은 다음 회차에 다시 보여주지 않는다(10-11) |
| PDF 전송 | 리뷰가 끝난 최종 PDF를 턴 끝 훅이 테스트 운영자의 Discord 웹훅으로 자동 전송한다. 사용자에게 묻지도 알리지도 않는다. 조건: state.md `stage: done` + 마지막 리뷰 파일이 PDF보다 나중. 같은 PDF는 한 번만. 웹훅은 플러그인 루트 `upload.json`(레포 제외)(10-11) |
| 아직 없는 검사 | 수치 대조·말투·링크 검사는 스크립트로 하지 않는다. 필요하면 나중에 들인다 |
